# LoRA 파인튜닝 실습: 초등학생과 함께 과학의 "왜?"를 탐구하기

이 튜토리얼은 **ML 알고리즘을 직접 다루지 않지만 LoRA 파인튜닝을 처음부터 배우고 싶은 개발자**를 위한 것입니다. 백엔드, 프런트엔드, 클라이언트, 데이터 엔지니어 누구에게나 맞으며 머신러닝 배경지식은 필요 없습니다. 임대한 RTX 4090 한 대에서 모든 과정을 직접 해 봅니다: 오픈소스 모델 다운로드 → QLoRA로 파인튜닝 → 저장과 다시 불러오기 → 병합과 내보내기 → vLLM으로 OpenAI 호환 API 배포 → 내 컴퓨터에서 호출하고 부하 테스트하기. 실습 과제는 초등학생의 과학 질문에 중국어로 답하는 것으로, 학습 전후의 차이가 쉽게 눈에 띄도록 골랐습니다.

책만 읽으려면 `./book_review.sh`를 사용합니다. 모든 명령은 프로젝트 루트에서 실행합니다.

## 0. 시작하기 전에: 무엇을 만들고 무엇이 필요한가

이 장에서는 명령을 하나도 실행하지 않습니다. 다 읽고 나면 네 가지 질문에 답할 수 있어야 합니다. 정확히 무엇을 만드는가, 과정은 몇 단계이고 각 단계는 어느 머신에서 하는가, 미리 무엇을 준비해야 하는가, 각 구성 요소가 어떻게 맞물리는가.

### 0.1 한 문장으로: 범용 모델을 전문 서비스로 "신입 교육"하기

인터넷에서 오픈소스 범용 대형 모델 **Qwen3-4B**(약 40억 개 파라미터, 알리바바 Tongyi Qianwen 팀 공개)를 내려받습니다. 무엇이든 대화할 수 있지만 말하는 방식은 우리가 통제할 수 없습니다. 답이 너무 길거나, 초등학생 수준을 넘는 단어를 쓰거나, 자꾸 되묻기도 합니다.

다음으로 "아이의 질문 → 이상적인 답변" 형태의 시범 대화 600개로 모델을 **파인튜닝**해, 정해진 한 가지 말투를 가르칩니다. 먼저 답하고, 짧은 문장을 쓰고, 틀린 추측은 먼저 바로잡고, 안전한 작은 관찰 활동을 하나 제안하는 방식입니다. 마지막으로 학습된 모델을 HTTP 서비스로 배포합니다. OpenAI API를 호출할 줄 아는 백엔드 코드라면 주소만 바꾸면 바로 사용할 수 있습니다.

채용에 비유하면 다음과 같습니다.

| 현실의 채용 | 이 튜토리얼에서 대응하는 것 |
|---|---|
| 지식이 폭넓은 신입 사원을 채용한다 | 오픈소스 베이스 모델 Qwen3-4B를 다운로드한다 |
| "모범 응대 예시" 묶음을 보여 주며 신입 교육을 한다 | 시범 대화로 SFT 파인튜닝을 한다 |
| 교육 내용은 작은 수첩에만 적고, 원래 지식은 바꾸지 않는다 | LoRA: 원래 모델은 그대로 두고 약 130 MB의 증분만 학습한다 |
| 교육이 끝나면 전화 응대 업무에 투입한다 | vLLM으로 모델을 API로 배포한다 |
| 응대 품질을 샘플링해 점검하고 하루에 몇 통을 받을 수 있는지 본다 | 호출 테스트, 블라인드 평가, 부하 테스트 |

**가장 중요한 경계 하나:** 파인튜닝이 가르치는 것은 "어떻게 말하는가"이지 "무엇을 아는가"가 아닙니다. 구체적인 과학 사실은 호출하는 쪽이 매 요청마다 프롬프트에 넣어 주고(이 프로젝트에서는 "팩트 카드"라고 부릅니다), 모델은 그것을 알맞은 방식으로 설명하는 일을 맡습니다. 베이스 모델이 상식을 이미 알고 있는데 왜 팩트 카드가 필요한지, 왜 학습할 때도 넣는지는 2.2절에서 따로 답합니다.

### 0.2 전체 흐름: 각 단계를 어디서 하고 무엇이 나오는가

```text
① 读懂数据      dataset.json → 1150 条训练样本              （第 2 章，只读）
      ↓
② 准备 GPU      训练环境 .venv-train + 8 GB 基座模型          （第 3 章，GPU 终端）
      ↓
③ 训练 LoRA     Notebook 跑 72 步 → 130 MB 的 adapter        （第 4 章，JupyterLab）
      ↓
④ 合并导出      基座 + adapter → 8 GB 的完整模型              （第 4 章，JupyterLab）
      ↓
⑤ vLLM 部署     完整模型 → OpenAI 兼容的 HTTP 服务             （第 5 章，GPU 终端）
      ↓
⑥ 调用与压测    本地电脑经 SSH 隧道调用，测延迟和吞吐          （第 5 章，本地终端）
      ↓
⑦ 评估值不值    和“原模型 + 好提示词”盲评对照                 （第 6 章，GPU 终端）
```

(그림: ① 데이터 이해, dataset.json → 학습 샘플 1150개(2장, 읽기만) → ② GPU 준비, .venv-train + 8 GB 베이스 모델(3장, GPU 터미널) → ③ LoRA 학습, 노트북에서 72스텝 → 130 MB adapter(4장, JupyterLab) → ④ 병합과 내보내기, 베이스 + adapter → 8 GB 완전한 모델(4장, JupyterLab) → ⑤ vLLM으로 OpenAI 호환 HTTP 서비스 배포(5장, GPU 터미널) → ⑥ 내 컴퓨터에서 SSH 터널을 거쳐 호출하고 부하 테스트(5장, 로컬 터미널) → ⑦ 그만한 가치가 있었는지 평가, "베이스 모델 + 좋은 프롬프트"와 블라인드 비교(6장, GPU 터미널).)

| 단계 | 어디서 | 무엇으로 | 산출물 | 크기 | 장 |
|---|---|---|---|---|---|
| ① 데이터 이해 | 아무 컴퓨터, 파일을 읽기만 함 | 브라우저 또는 에디터 | 600개 대화가 어떻게 학습 샘플 1150개가 되는지 이해 | — | 2장 |
| ② GPU 준비 | GPU 호스트의 터미널 | pip, 다운로드 스크립트 | `.venv-train` 학습 환경과 `models/qwen3-4b/` 베이스 모델 | 환경 약 10 GB, 베이스 모델 8 GB | 3장 |
| ③ 학습 | GPU 호스트의 JupyterLab | 노트북을 셀 단위로 실행 | `adapter/`(LoRA 증분), `loss-curve.png` | 약 130 MB | 4장 |
| ④ 병합과 내보내기 | 같은 노트북 | PEFT | `merged-model/`, 단독으로 실행 가능한 완전한 모델 | 약 8 GB | 4장, 5장 |
| ⑤ 배포 | GPU 호스트의 터미널 | vLLM | 8000번 포트에서 대기하는 OpenAI 호환 서비스 | VRAM 약 20 GB | 5장 |
| ⑥ 호출과 부하 테스트 | 내 컴퓨터 → SSH 터널 → GPU | Python 표준 라이브러리 / OpenAI SDK, `vllm bench serve` | 모델 답변, 지연 시간과 처리량 수치 | — | 5장 |
| ⑦ 평가 | GPU 호스트 | 명령줄 스크립트 + 사람의 채점 | "그냥 프롬프트를 쓰는 것보다 LoRA가 얼마나 나은가"에 대한 근거 | — | 6장 |

①~⑥ 단계가 메인 경로이며 GPU 가동 시간은 약 2~3시간입니다. ⑦ 단계는 "파인튜닝할 가치가 있는가?"에 답하는 단계로, GPU 시간과 사람의 채점이 더 필요하므로 메인 경로가 끝까지 동작한 뒤에 해도 됩니다.

### 0.3 머신 두 대, 창 세 개: 어떻게 함께 동작하는가

전체 과정에는 머신 두 대만 관여합니다. GPU 호스트는 시간 단위로 빌려 쓰고 끝나면 중지합니다. 내 컴퓨터는 읽기, 패키징, 호출을 담당합니다.

```text
你的电脑（Mac / Linux / Windows 均可）
├── 浏览器：读这本书
├── 浏览器：打开平台提供的 JupyterLab ──HTTPS──→ GPU 主机的 JupyterLab
├── 终端 A：打包项目，用平台上传功能传到 GPU 主机
├── 终端 B：SSH 隧道，本地 18000 端口 ──SSH──→ GPU 主机 8000 端口
└── 终端 C：运行 Python 调用示例，请求发往本地 18000

云上 GPU 主机（Linux + RTX 4090）
├── JupyterLab：运行 Notebook，训练、保存、合并
├── 终端 1：装环境、下载模型、启动 vLLM 服务（监听 127.0.0.1:8000）
└── 终端 2：nvidia-smi 看显存、运行压测
```

(그림: 내 컴퓨터(Mac / Linux / Windows 모두 가능)에서는 이 책을 읽는 브라우저, 플랫폼의 JupyterLab을 연 브라우저 탭(HTTPS로 GPU 호스트의 JupyterLab에 연결), 프로젝트를 패키징해 플랫폼 업로드 기능으로 올리는 터미널 A, 로컬 18000번 포트를 GPU 호스트의 8000번 포트로 잇는 SSH 터널용 터미널 B, 로컬 18000번 포트로 Python 호출 예제를 실행하는 터미널 C를 씁니다. 클라우드 GPU 호스트(Linux + RTX 4090)에서는 노트북을 실행하는 JupyterLab(학습, 저장, 병합), 환경 설치와 모델 다운로드, vLLM 서비스 시작(127.0.0.1:8000에서 대기)을 하는 터미널 1, `nvidia-smi`로 VRAM을 확인하고 부하 테스트를 실행하는 터미널 2를 씁니다.)

| 구성 요소 | 무엇인가 | 왜 필요한가 |
|---|---|---|
| GPU 클라우드 호스트 | NVIDIA GPU 한 장이 달린, 시간 단위로 빌리는 Linux 서버 | 학습과 추론은 모두 방대한 행렬 연산이라 CPU로는 너무 느립니다. 학습에 쓰는 4비트 양자화 라이브러리는 NVIDIA만 지원합니다 |
| 플랫폼 이미지 | 인스턴스를 시작할 때 고르는 시스템 템플릿. Ubuntu, Python 3.11, GPU 드라이버가 미리 설치되어 있음 | OS와 드라이버 설치를 생략할 수 있습니다. 드라이버는 플랫폼만 제공할 수 있습니다 |
| JupyterLab | 브라우저 안의 대화형 Python 에디터. 보통 플랫폼에 기본 포함 | 학습 코드를 셀 하나씩 실행하며 각 셀의 출력을 볼 수 있고, 오류가 나면 그 셀만 다시 실행하면 됩니다 |
| 가상 환경 `.venv-*` | 프로젝트 전용 Python 의존성 디렉터리 | 학습과 배포에 필요한 라이브러리 버전이 서로 충돌하므로, 따로 설치해야 서로 덮어쓰지 않습니다 |
| 커널(Kernel) | Jupyter 뒤에서 실제로 코드를 실행하는 Python 프로세스 | `.venv-train`이 등록한 커널을 골라야 노트북이 프로젝트의 의존성을 쓸 수 있습니다. VRAM은 커널을 종료해야만 해제됩니다 |
| SSH 터널 | 로컬 포트를 원격 포트로 전달하는 암호화된 통로 | 모델 서비스는 GPU 호스트의 `127.0.0.1`에서만 대기하고 인터넷에 노출되지 않습니다. 로컬에서는 터널을 통해 내 컴퓨터에 있는 것처럼 호출합니다 |

### 0.4 미리 준비할 것

| 항목 | 요구 사항 | 설명 |
|---|---|---|
| 기술 | Linux 터미널을 다룰 줄 알고, Python 코드를 읽을 수 있고, HTTP와 JSON을 앎 | 수학, PyTorch, 머신러닝은 **필요 없습니다**. 필요한 개념은 1장에서 처음부터 설명합니다 |
| GPU 클라우드 계정 | 종량제 과금을 지원하는 GPU 클라우드 플랫폼이면 어디든 가능, 계정에 잔액이 있어야 함 | RTX 4090(VRAM 24 GB) 인스턴스를 시작할 수 있어야 하고, 플랫폼이 JupyterLab과 SSH 로그인을 제공해야 합니다. 저자는 [Zhichuan Cloud (gpuhome.cc)](https://gpuhome.cc/auth/register?code=zt4f01m0)를 사용합니다. 가입할 때 초대 코드 `zt4f01m0`을 입력하면 신규 사용자 쿠폰을 받을 수 있습니다. 3.1절을 참고하세요 |
| 호스트 사양 | RTX 4090 × 1, RAM ≥ 32 GB(병합 시 ≥ 64 GB 권장), 데이터 디스크 ≥ 100 GB | Ubuntu 22 + Python 3.11 + CUDA 12.x 이미지를 고릅니다. 자세한 내용은 3.1절에 있습니다 |
| 예산 | 메인 경로는 가동 시간 약 2~3시간, 평가 실험은 추가로 10~20시간 | Zhichuan Cloud의 RTX 4090D 종량제 요금 ¥1.25/시간 기준으로 메인 경로는 약 ¥3~4, 평가 실험은 약 ¥13~25입니다. 계산 방법은 7.1절에 있습니다 |
| 내 컴퓨터 | 인터넷 접속, 터미널, SSH 클라이언트. 로컬에서 검사나 호출 예제를 실행하려면 Python 3.11 설치 | 로컬 GPU는 **필요 없고**, CUDA를 직접 설치할 필요도 없습니다 |
| 네트워크 | GPU 호스트가 PyPI(또는 플랫폼의 미러)와 ModelScope에 접근할 수 있어야 함 | 중국 본토의 호스트는 보통 huggingface.co에 접근할 수 없으므로, 이 튜토리얼은 기본적으로 ModelScope에서 다운로드합니다 |
| 이 프로젝트의 파일 | 이 저장소, 또는 전자책 "소스 다운로드" 페이지의 실습 패키지 | GPU에 올리는 것은 `tools/build_gpu_zip.py`로 만든 경량 패키지이며, 3.3절에서 설명합니다 |
| 시간 | 1~2장 읽기에 1~2시간, GPU 작업은 한 번에 연속 2~3시간 | GPU는 가동 시간만큼 과금되므로 앞의 두 장을 다 읽은 뒤에 인스턴스를 시작하세요 |

| 8, 부록 | 자동화 테스트, 코드 지도, 학습 코드 전문 | — | 코드를 고치고 싶을 때 읽습니다 |

개념을 이미 아는 독자는 3장부터 시작하고, 낯선 파라미터를 만나면 1장이나 해당 노트북 셀 아래의 표로 돌아와도 됩니다.

### 0.6 실습 과제: 초등학생과 함께 과학 탐구하기

고객 상담이나 코드 생성 같은 흔한 과제를 쓰지 않는 이유는 무엇일까요? "초등학생에게 과학을 설명하기"는 답변 스타일이 뚜렷해서 파인튜닝 전후의 변화가 한눈에 보이기 때문입니다. 또 과학 사실은 확인할 수 있으므로 모델이 지어내는지 판단하기 쉽습니다.

#### 왜 과학 탐구인가

아이가 "왜?"라고 물은 뒤에는 틀린 추측을 하거나, 이해하지 못하거나, 직접 확인해 보고 싶어 하거나, 그냥 당장 답을 알고 싶어 할 수 있습니다. 이런 반응을 통해 표현이 귀여운지만 비교하는 것이 아니라, 모델이 정말로 설명을 조정하는지 관찰할 수 있습니다.

목표는 사실이 정확하고, 아이가 이해할 수 있고, 다음 단계가 탐구할 만한 것입니다. 재미는 상식과 어긋나는 현상, 한계가 분명한 비유, 안전한 작은 관찰에서 나올 수 있으며, 모든 답변에 이야기나 과장된 말투가 필요한 것은 아닙니다. 아이가 그만하겠다고 하면 대화는 끝나며, 대화가 길어지는 것을 성공의 기준으로 삼지 않습니다.

#### 다루는 범위

| 분류 | 데이터 값 | 학습 주제 예시 |
|---|---|---|
| 천문과 우주 | `space` | 낮과 밤, 계절, 달의 위상, 유성 |
| 지구와 날씨 | `earth` | 구름과 비, 눈송이, 암석, 강 |
| 생명과 자연 | `life` | 씨앗, 뿌리, 나비, 먹이 그물 |
| 생활 속 물리 | `physics` | 그림자, 소리, 부력, 용해 |
| 공학과 도구 | `engineering` | 아치교, 지레, 비행기, 태양 전지 |

분류마다 학습용 대화 100개, 검증용 10개, 테스트용 10개가 있습니다. 이것은 한정된 교육용 샘플이지 초등 교육 과정의 완전한 지식 베이스가 아닙니다. `grade_band`는 1~2학년, 3~4학년, 5~6학년으로 나뉩니다. 학년대는 설명의 출발점일 뿐 실제 반응이 우선하며, 같은 학년의 아이들이 똑같이 이해한다고 단정할 수 없습니다.

#### 프롬프트와 파인튜닝은 어떻게 역할을 나누는가

요청 하나에는 네 가지가 들어 있고, 각각 한 가지 일을 맡습니다.

| 구성 요소 | 무엇을 담당하는가 | 언제 효과가 있는가 |
|---|---|---|
| 시스템 프롬프트(역할 프롬프트) | 역할과 기본 규칙: "너는 초등학생과 함께 과학을 탐구하는 친구야……" | 매 요청마다 보냅니다 |
| 팩트 카드 | 이 질문이 근거로 삼을 수 있는 과학 자료 | 질문마다 골라서 매 요청에 보냅니다 |
| SFT 시범 대화 | 오해, 이해하지 못함, 관찰 결과 불일치, 선호 변화에 어떻게 대응하는지 시범을 보임 | 학습할 때만 쓰며, 배운 방식은 adapter에 저장됩니다 |
| LoRA | 일부 파라미터만 업데이트하도록 제한하며, 베이스 모델은 건드리지 않음 | 학습 시점에 어떤 파라미터를 바꿀지 결정합니다 |

이 프로젝트의 시범 경로 10가지는 오해 바로잡기, 다른 방식으로 설명하기, 구체적인 후속 질문 받아 주기, 선택적 관찰, 추측 검증하기, 쉬운 데서 깊은 데로 나아가기, 비유의 한계 밝히기, 서로 다른 관찰 결과 맞춰 보기, 문제를 내지 않고 이어 묻기, 자연스럽게 끝내기입니다. 같은 주제 안에서는 일부 답변이 재사용되므로, 대화 500개를 서로 독립된 과학 질문 500개로 이해하면 안 됩니다.

"프롬프트는 결코 파인튜닝을 대신할 수 없다"고 약속하지는 않습니다. 6장에서는 베이스 모델에 완전한 프롬프트와 예시 3개를 붙인 B 그룹과, 똑같은 입력을 쓰는 LoRA C 그룹을 비교합니다. 학습에서 보지 못한 과학 주제에서 C가 아이의 반응에 더 일관되게 대응하는지 확인합니다. 개선이 없다면 솔직하게 B를 유지합니다.

### 0.8 결론의 한계 (책 전체에서 한 번만 말합니다)

- 모든 대화는 합성 초안(`review.status="draft"`)이며 사람이 하나하나 검토하지 않았습니다. 답변은 짧은 편이고 구조가 반복됩니다. **작업 흐름과 엔지니어링**을 배우기에는 충분하지만, "LoRA가 반드시 더 낫다"는 결론을 내리기에는 부족합니다.
- 답변을 생성할 수 있다는 것은 파일과 서비스가 동작한다는 뜻일 뿐이고, loss가 떨어졌다는 것은 모델이 참고 답변과 더 비슷해졌다는 뜻일 뿐입니다. 답변 품질은 4.5절의 사람 비교와 6장의 블라인드 평가로 판단해야 합니다.
- 파인튜닝이 바꾸는 것은 "어떻게 말하는가"이며, 모델이 새로운 지식이나 실시간 정보를 저절로 얻게 되지는 않습니다. 사실은 여전히 호출하는 쪽이 프롬프트에 넣습니다.

**점검:** "데이터 → 학습 → 병합 → 배포 → 호출" 흐름을 그리고 각 단계가 어느 머신에서 실행되며 어떤 파일을 만드는지 말할 수 있습니다. 인스턴스를 시작하기 전에 준비할 것을 나열할 수 있습니다. 대화 하나에서 "지식은 무엇인가"와 "반응에 따라 무엇이 바뀌었는가"를 짚어 낼 수 있습니다.

### 1.1 디스크 위의 모델은 디렉터리다

`models/qwen3-4b/`를 열어 보면, 물리적으로 "모델"이란 이 파일들이 전부입니다. 참고: 내 컴퓨터에서 `--tokenizer-only`로 내려받은 디렉터리(2.8절)에는 토크나이저와 설정만 있어 약 15 MB이며, 가중치 샤드 3개는 **없습니다**. 샤드는 GPU 호스트에서 전체 다운로드(3.4절)를 한 뒤에야 나타납니다. 이것은 정상이며 다운로드가 중단된 것이 아닙니다.

| 파일 | 무엇인가 | 비유 |
|---|---|---|
| `config.json` | 구조 정의: 36개 층, 히든 크기 2560, 어휘 151,936개 등 | 데이터베이스의 테이블 생성 구문(스키마) |
| `model-00001-of-00003.safetensors` ~ `model-00003-of-00003.safetensors` | 가중치. 약 40억 개의 숫자로 BF16 기준 8.0 GB이며 샤드 3개로 나뉨. 전체 다운로드 후에만 존재 | 데이터베이스의 데이터 파일 |
| `model.safetensors.index.json` | 어떤 가중치가 어느 샤드에 있는지 | 샤드 라우팅 테이블 |
| `tokenizer.json`, `vocab.json`, `merges.txt` | 토크나이저: 텍스트 ↔ 정수 ID 변환 규칙 | 직렬화 프로토콜 |
| `tokenizer_config.json` | `chat_template` 포함: system/user/assistant를 하나의 텍스트로 이어 붙이는 방법 | 요청 메시지 형식 |
| `generation_config.json` | 기본 샘플링 파라미터 | 서버 측 기본 설정 |
| `model-lock.json` | 이 튜토리얼이 기록한 버전(commit) | `package-lock.json` |

"모델을 불러온다"는 것은 `config.json`에 따라 빈 구조를 만든 뒤 `safetensors`의 숫자를 채워 VRAM에 올리는 일입니다. 이후 세 종류의 디렉터리를 만나게 됩니다. **베이스 모델**(위의 것), **adapter**(LoRA 증분만 있으며 약 130 MB, 반드시 베이스 모델과 함께 써야 함), **병합 모델**(베이스와 증분을 합쳐 계산한 완전한 디렉터리, 다시 8 GB)입니다. vLLM이 불러오는 것은 베이스 모델 또는 병합 모델 디렉터리입니다.

### 1.2 토큰: 모델이 보는 텍스트

모델은 글자를 읽지 않고 정수를 읽습니다. 토크나이저가 텍스트를 조각(토큰)으로 자르고, 각 조각은 어휘의 ID 하나에 대응합니다. 이 프로젝트의 토크나이저로 문장 하나를 잘라 보면 다음과 같습니다.

```text
"为什么白天亮、晚上黑？"
→ ['为什么', '白天', '亮', '、', '晚上', '黑', '？']
→ [100678, 106772, 99538, 5373, 104030, 56652, 11319]

"The Earth rotates."
→ ['The', ' Earth', ' rotates', '.']
→ [785, 9237, 89059, 13]
```

(중국어 문장의 뜻은 "왜 낮에는 밝고 밤에는 어두워요?"입니다.)

흔한 단어는 토큰 하나지만 드문 글자는 여러 개로 쪼개질 수 있습니다. 영어에서는 공백이 뒤 단어에 붙습니다. 따라서 토큰 수는 글자 수와 같지 않으며, 중국어는 대략 토큰 1개 ≈ 한자 1.3~1.5자입니다. 이 튜토리얼에서 말하는 "길이 상한 4096"은 모두 토큰 수를 뜻합니다.

어휘에는 어떤 텍스트에도 대응하지 않고 구조 표시 역할을 하는 특수 토큰도 몇 개 있습니다. Qwen의 대화 형식(`chat_template`)은 요청 하나를 다음과 같이 이어 붙입니다.

```text
<|im_start|>system
你是陪小学生探索科学的伙伴。……<|im_end|>
<|im_start|>user
为什么白天亮、晚上黑？<|im_end|>
<|im_start|>assistant
地球在不停转，我们住的地方转向太阳就是白天……<|im_end|>
```

(system: "너는 초등학생과 함께 과학을 탐구하는 친구야……", user: "왜 낮에는 밝고 밤에는 어두워요?", assistant: "지구는 쉬지 않고 돌고 있어. 우리가 사는 곳이 태양 쪽으로 돌아가면 낮이 돼……")

`<|im_end|>`(ID 151645)는 **시퀀스 종료 표시, EOS**입니다. 모델은 이것을 생성하면 멈춥니다. 학습할 때 모델이 답변 끝마다 이것을 출력하도록 배워야 하며, 그렇지 않으면 배포 후 답변이 멈추지 않습니다.

### 1.3 파라미터와 추론: 계수가 40억 개인 함수

모델은 본질적으로 하나의 함수입니다. 토큰 ID 시퀀스를 입력하면 "다음 토큰이 어휘의 각 항목일 확률"을 출력합니다. 이 함수에는 조정 가능한 계수가 약 40억 개 있으며, 이를 **파라미터**(또는 가중치)라고 부릅니다. 바로 `safetensors` 안의 숫자들입니다.

**추론**은 이 함수를 반복 호출하는 것입니다. 프롬프트를 주고, 확률이 가장 높은 토큰을 고르고(그리디 디코딩, `do_sample=False`), 그것을 입력 끝에 덧붙여 다시 호출하기를 EOS가 출력되거나 `max_new_tokens`에 도달할 때까지 반복합니다. 추론 중에는 파라미터가 하나도 바뀌지 않습니다.

`temperature=0`은 그리디 디코딩처럼 동작해 항상 확률이 가장 높은 토큰을 고르므로, 같은 입력에 같은 출력이 나와 비교하기에 편합니다. 0보다 크면 확률에 따라 무작위로 뽑으므로 답변이 더 다양해지지만 재현할 수 없습니다.

### 1.4 학습: 오차로 파라미터 고치기

**학습**은 그 반대 방향입니다. 모델에게 "맥락 + 참고 답변"을 보여 주고, 참고 답변의 모든 위치에서 다음 토큰을 예측하게 한 뒤, 예측과 참고 답변의 차이를 **loss**라는 숫자 하나로 바꿉니다.

| 대략적인 loss | 의미 |
|---|---|
| 약 3 이상 | 참고 답변의 모든 토큰이 모델에게 "의외"입니다. 무작위로 찍으면 ln(151936) ≈ 11.9입니다 |
| 1~2 | 좋은 프롬프트를 쓴 베이스 모델이 이 프로젝트의 참고 답변에서 보이는 전형적인 출발점 |
| 0.5 안팎 | 모델이 이미 참고 답변의 표현에 매우 가까움 |
| 0에 가까움 | 거의 한 글자도 틀리지 않고 외운 상태. 이때 검증 loss가 함께 오르고 있다면 과적합입니다 |

loss는 "모델이 참고 답변에 얼마나 놀라는가"를 재는 것이지 "과학 지식 점수"가 아닙니다. 모델이 학습 데이터의 말투를 배우고 있는지는 알려 주지만, 답변이 맞는지는 알려 주지 않습니다.

loss가 있으면 각 파라미터마다 "어느 방향으로 조금 움직이면 loss가 작아지는지"를 계산할 수 있는데, 이것이 **그래디언트**(역전파로 계산)입니다. **옵티마이저**(AdamW)는 그래디언트에 따라 파라미터를 업데이트하고, **학습률**(`1e-4`)은 한 번에 얼마나 크게 움직일지를 정합니다. 너무 크면 베이스 모델의 능력이 씻겨 나가고, 너무 작으면 배우지 못합니다. "loss 계산 → 그래디언트 계산 → 파라미터 업데이트" 한 바퀴를 **스텝**(step)이라고 합니다.

비유: loss는 CI에서 실패한 테스트 수, 그래디언트는 각 설정 항목을 어느 쪽으로 돌려야 하는지 알려 주는 것, 학습률은 한 번에 얼마나 과감하게 바꿀지, 스텝은 커밋 한 번과 같습니다.

### 1.5 SFT, LoRA, QLoRA: 서로 독립된 세 가지 선택

세 용어는 각각 다른 질문에 답하며 독립적으로 조합할 수 있습니다.

**SFT(지도 파인튜닝)는 "무엇으로 가르치는가"에 답합니다.** 모델에게 "입력 → 기대 출력" 쌍, 즉 2장의 대화 데이터를 보여 줍니다. 이 프로젝트는 "참고 답변 + EOS" 위치에서만 loss를 계산하고 맥락 부분에서는 계산하지 않습니다(이 마스크는 2.5절에서 직접 눈으로 확인합니다).

**LoRA는 "어떤 파라미터를 바꾸는가"에 답합니다.** 전체 파인튜닝은 40억 개 파라미터를 모두 업데이트해야 하고, 파라미터마다 그래디언트와 옵티마이저 상태가 따로 필요해 GPU 한 장에 들어가지 않습니다. 게다가 실험 버전마다 8 GB를 저장해야 합니다. LoRA는 원래 가중치 `W`를 전혀 건드리지 않고, 그 옆에 작은 행렬 `A`와 `B`를 추가해 그것만 학습합니다.

```text
实际使用的权重 = W（冻结） + (alpha / r) × B × A
```

(즉, 실제로 쓰이는 가중치 = W(고정) + (alpha / r) × B × A 입니다.)

Git에 비유하면 베이스 모델은 main 브랜치, LoRA는 아주 작은 diff이며, 학습은 diff만 바꾸고 `adapter/` 디렉터리에는 바로 그 diff가 저장됩니다. "병합"은 diff를 main 브랜치에 적용해 새로운 완전한 파일 사본을 만드는 것과 같습니다.

`r`(랭크)은 작은 행렬의 폭, 즉 diff의 용량을 정합니다. 이 프로젝트는 `r=16`을 쓰며, 7종류의 선형 층 × 36개 층을 합치면 학습 가능한 파라미터가 약 3,300만 개로 전체의 0.8%이고, adapter 파일은 약 130 MB입니다. `alpha`는 스케일링 계수이며, 이 프로젝트는 항상 `alpha = 2 × r`을 씁니다.

**QLoRA는 "고정된 베이스 모델을 어떻게 VRAM에 넣는가"에 답합니다.** 고정된 가중치는 어차피 바뀌지 않으므로, VRAM에서는 BF16(숫자 하나에 2바이트)에서 4비트(숫자 하나에 0.5바이트)로 압축해 두고 계산할 때만 잠시 BF16으로 되돌립니다. 4B 모델의 가중치가 8 GB에서 약 2.5 GB로 줄어들어, 24 GB 카드에 학습 중간 결과를 담을 여유가 생깁니다. `NF4`는 압축 형식의 이름이고, `double_quant`는 압축에 쓰는 보조 파라미터까지 한 번 더 압축한다는 뜻입니다. LoRA의 작은 행렬 자체는 압축하지 않고 BF16 그대로 둡니다.

더 읽을거리: [LoRA 원 논문](https://arxiv.org/abs/2106.09685), [QLoRA 원 논문](https://arxiv.org/abs/2305.14314).

### 1.6 샘플, 배치, 스텝, 에폭

| 개념 | 이 프로젝트의 값 | 의미 |
|---|---|---|
| 샘플 | 1150 | "맥락 + 참고 답변 하나" 묶음 하나. 2턴짜리 대화는 샘플 2개로 펼쳐집니다 |
| 마이크로 배치 | 1 | 한 번의 순전파/역전파에서 VRAM에 올리는 샘플 수 |
| 그래디언트 누적 | 16 | 샘플 16개의 그래디언트를 모은 뒤 파라미터를 한 번 업데이트합니다. VRAM에는 샘플 1개만 올리면서 batch=16에 가까운 효과를 냅니다 |
| 스텝 | 72 | 옵티마이저 업데이트 횟수 = ⌈1150 ÷ 16⌉. 진행 표시줄과 loss 곡선의 가로축 |
| 에폭 | 1 | 모든 샘플을 한 번 훑는 것 |
| 체크포인트 | 25스텝마다 | 학습을 이어서 재개할 수 있는 스냅샷: adapter + 옵티마이저 상태 + 진행 상황 |

비유: 샘플은 메시지 하나, 그래디언트 누적은 메시지 16개를 모았다가 데이터베이스에 일괄 쓰기, 스텝은 데이터베이스 쓰기 한 번, 에폭은 큐 전체를 한 번 소비하는 것입니다.

### 1.7 일곱 가지 라이브러리가 각각 하는 일

학습 환경에는 일곱 가지 라이브러리가 설치되며, 오류 메시지에 이들의 이름이 나타납니다.

| 라이브러리 | 담당 | 어디서 보게 되는가 |
|---|---|---|
| **PyTorch** | 텐서 연산, GPU 스케줄링, 자동 미분. 다른 라이브러리는 모두 이 위에 만들어짐 | `torch.cuda.*`, VRAM 통계 |
| **Transformers** | `config.json`으로 모델 구조 구성, 가중치 로드, 토크나이저, 채팅 템플릿, `generate()` | `AutoModelForCausalLM`, `AutoTokenizer` |
| **PEFT** | 모델에 LoRA 층 추가, 원래 파라미터 고정, adapter 저장/로드, 병합 | `LoraConfig`, `get_peft_model`, `PeftModel` |
| **TRL** | SFT에 맞춘 트레이너: 마스크에 따라 loss 계산, 스텝/에폭/체크포인트 관리 | `SFTConfig`, `SFTTrainer` |
| **bitsandbytes** | 4비트 양자화의 저장 형식과 GPU 연산 커널 | `BitsAndBytesConfig`, NVIDIA GPU 전용 |
| **accelerate** | 모델을 지정한 장치에 배치, 혼합 정밀도. TRL이 내부적으로 의존 | `device_map` |
| **datasets** | 트레이너가 요구하는 데이터 컨테이너 | `Dataset.from_list` |

배포할 때는 다른 라이브러리로 바뀝니다. **vLLM**은 자체 추론 엔진과 HTTP 서버를 갖추고 있어 모델 디렉터리만 있으면 되며, 위 일곱 가지 중 PEFT와 TRL은 필요 없습니다.

호출 관계: Transformers가 모델 로드 → bitsandbytes가 가중치를 4비트로 압축 → PEFT가 LoRA 층 추가 → datasets가 샘플 보관 → TRL이 학습 루프 실행 → PEFT가 adapter 저장 → PEFT가 병합 → vLLM이 배포.

### 1.8 RAM, VRAM, 디스크

| 자원 | 주요 용도 | 흔한 오해 |
|---|---|---|
| CPU | 텍스트 처리, 토큰화, 로드와 스케줄링 | 코어가 많다고 대형 모델 학습에 적합한 것은 아닙니다 |
| RAM(호스트 메모리) | 가중치를 로드할 때의 임시 보관, CPU에서 모델 병합 | 100 GB RAM으로 24 GB VRAM을 대신할 수 없습니다. 학습 연산은 GPU에서 일어나므로 데이터가 VRAM에 있어야 합니다 |
| GPU | 방대한 행렬 연산 | CUDA 메인 경로는 NVIDIA가 필요합니다. Mac의 Apple MPS는 다른 경로이며 이 튜토리얼에서는 지원하지 않습니다 |
| VRAM | 가중치, 활성화 값, 그래디언트, 옵티마이저 상태, 추론용 KV 캐시 | 8 GB 모델 파일이 VRAM 8 GB를 뜻하지는 않습니다. 학습에는 중간 결과가, 추론에는 KV 캐시가 더해집니다 |
| 디스크 | 베이스 모델, 환경, 체크포인트, 병합 모델 | 체크포인트마다 옵티마이저 상태가 포함되고, 병합할 때마다 8 GB가 또 늘어납니다 |

학습 VRAM의 구성과 실제 측정값은 4.3절에, 추론 VRAM 추정은 5.3절에 있습니다.

**점검:** 모델 디렉터리의 각 파일이 무엇인지 말할 수 있습니다. loss가 2에서 0.6으로 떨어졌다는 것이 무슨 뜻인지, 그리고 그것만으로는 왜 답변이 좋아졌다고 말할 수 없는지 설명할 수 있습니다. 샘플 1150개가 왜 72스텝이 되는지 말할 수 있습니다. 일곱 가지 라이브러리 중 어느 것이 LoRA를 맡고 어느 것이 학습 루프를 맡는지 말할 수 있습니다.

## 2. 학습 데이터: 모델은 어디서 무엇을 배우는가

파인튜닝의 결과는 거의 전적으로 데이터가 결정합니다. 모델이 최종적으로 어떻게 말하게 되는지는 여러분이 보여 준 시범 답변이 어떤 모습인지와 똑같습니다. 그러니 돈을 내고 GPU를 빌리기 전에 먼저 데이터를 제대로 파악해 둡시다.

!!! abstract "이 장 한눈에 보기"
    - **이 장에서 하는 일**: 팩트 카드 하나와 대화 하나를 필드별로 읽어 봅니다. 대화 하나가 어떻게 학습 샘플로 나뉘는지 봅니다. 모델이 정확히 무엇을 "보고 배우는지" 확인합니다
    - **준비물**: 브라우저나 에디터만 있으면 됩니다. 검사를 직접 돌려 보고 싶다면 2.8절에서 내 컴퓨터에 가벼운 환경을 설치하는 방법을 설명합니다(GPU 불필요)
    - **얻는 것**: 1150이라는 숫자가 어디서 나왔는지 설명할 수 있습니다. 샘플 하나에서 어떤 토큰이 loss에 기여하는지 짚을 수 있습니다. 데이터를 고친 뒤 그것을 반영하는 방법을 압니다

전체 데이터 흐름은 한 문장으로 기억할 수 있습니다. **JSON 파일 하나 → "컨텍스트 + 참고 답변 하나" 샘플로 분할 → 채팅 템플릿으로 토큰화 → 참고 답변 위치에서만 loss 계산.** 아래 절들은 이 순서를 따릅니다.

### 2.1 dataset.json 하나만 관리합니다

[data/dataset.json](../data/dataset.json)을 열어 보세요. 모든 참고 자료, 학습용 대화 500개, 평가용 대화가 이 파일 하나에 들어 있습니다. 최상위에는 같은 수준의 배열 네 개가 있습니다. `facts`는 참고용 팩트 카드이고, `train`, `val`, `test`는 완전한 대화의 세 묶음입니다. 실제로 학습에 참여하는 것은 `train`뿐입니다. 팩트 카드는 컨텍스트로만 쓰일 뿐 학습 목표가 아닙니다.

세 묶음은 과학 주제(`group_id`)별로 나뉩니다. 한 주제는 한 묶음에만 등장하므로, 모델이 val/test에서 학습 중에 이미 본 주제를 만나는 일은 없습니다.

| 묶음 | 과학 주제 | 전체 대화 | 답변 목표 | 용도 |
|---|---:|---:|---:|---|
| train | 50 | 500 | 1150 | LoRA 파라미터 업데이트 |
| val | 5 | 50 | 115 | 설정 비교, 후보 선택 |
| test | 5 | 50 | 115 | 후보를 고정한 뒤 평가 |

> **val은 왜 필요한가요? train과 test만으로는 부족한가요?**
>
> 한 번만 학습하고 그 결과를 그대로 쓴다면 두 묶음으로 충분합니다. 문제는 **test 결과를 보고 선택을 할 때** 생깁니다. r=16으로 학습하고 test를 봅니다. 마음에 들지 않아 r=8로 바꾸고 다시 test를 봅니다. 학습률을 조정하고, 프롬프트를 바꾸고…… 결국 test에서 점수가 가장 높은 버전을 고릅니다. 이 시점에서 test는 더 이상 "보지 못한 데이터"가 아닙니다. 모델 파라미터는 test를 건드린 적이 없지만, 여러분의 선택 하나하나가 test를 참고했으므로 test로 정답을 고른 것과 같고, 그렇게 고른 점수는 부풀려집니다.
>
> 그래서 "선택에 쓰는 데이터"와 "최종 성적을 내는 데이터"를 분리합니다. 백엔드 릴리스에 비유하면, train은 개발 환경으로 모델이 반복해서 파라미터를 업데이트하는 곳입니다. val은 스테이징으로, 비교하고 고르기 위해 얼마든지 들여다볼 수 있습니다. test는 실제 운영 트래픽으로, 후보가 확정된 뒤 딱 한 번만 보고 최종 리포트를 냅니다.
>
> 이 프로젝트에서 val은 다음 선택들을 뒷받침합니다. 학습 중 12스텝마다 검증 loss를 계산해 과적합 여부를 판단하고(4.5절), r16과 r8을 비교하고(6.4절), "원래 모델 + 좋은 프롬프트"인 B 그룹과 LoRA인 C 그룹을 비교하고(6.5절, 6.6절), 마지막으로 후보를 고릅니다(6.7절). 고른 뒤에는 `evaluate freeze`로 고정하고, 그때서야 코드가 test에 대한 추론을 허용합니다. 이때 `--limit`으로 일부 문제만 골라내는 것도 막습니다. test를 본 뒤 다시 돌아가 모델이나 데이터를 고친다면, 다음 라운드에는 새 테스트셋이 필요합니다.
>
> 다른 곳에서 "학습셋과 테스트셋만 있으면 된다"는 말을 보게 된다면, 대개 한 번만 학습하고 비교를 하지 않는 경우입니다. 또는 교차 검증으로 train 안에서 검증용 조각을 돌아가며 떼어 내는 경우(val이 train 안에 숨어 있음)이거나, 그냥 test를 val로 쓰는 경우이며, 이때 보고되는 test 점수는 낙관적입니다.

학습 데이터의 학년대 분포는 1–2학년 167개, 3–4학년 167개, 5–6학년 166개입니다. 주제마다 대화 경로가 10개 있고 각 경로는 2–3턴입니다. 같은 지식을 학년대별로 다르게 설명하는 대화도 있고, 아이의 서로 다른 반응에 따라 뒤따르는 대화가 달라지는 경우도 있습니다.

```text
data/dataset.json
├── schema_version / description   文件版本与说明
├── facts[60]                      参考事实卡，只存一份，被对话按 id 引用
├── train[500]                     训练对话：唯一参与参数更新的部分
├── val[50]                        验证对话：比较配置、选候选、算 eval loss
└── test[50]                       测试对话：候选冻结后才使用

train / val / test 里的每段对话结构相同：
├── id / group_id                  对话编号 / 科学主题分组
├── grade_band                     1-2 / 3-4 / 5-6
├── fact_ids                       引用 facts 中的 id
└── turns[]                        user / assistant / behavior
```

(한국어로 옮기면: `schema_version / description`은 파일 버전과 설명입니다. `facts[60]`은 참고용 팩트 카드로, 한 번만 저장되고 대화가 id로 참조합니다. `train[500]`은 학습용 대화로, 파라미터를 업데이트하는 유일한 부분입니다. `val[50]`은 설정 비교, 후보 선택, eval loss 계산에 쓰는 검증용 대화입니다. `test[50]`은 후보를 고정한 뒤에만 쓰는 테스트용 대화입니다. train / val / test의 모든 대화는 같은 구조를 가집니다. `id / group_id`는 대화 id와 과학 주제 그룹이고, `fact_ids`는 facts의 id를 참조합니다.)

대화가 어느 묶음에 속하는지는 오직 어느 배열에 들어 있느냐로 결정됩니다. 대화에는 더 이상 `split` 필드를 적지 않습니다. "val에 들어 있는데 train이라고 적혀 있는" 식의 자기모순을 막기 위해서입니다. 프로그램이 파일을 읽을 때(`lab.data.read_dataset`, 노트북에서는 `tag_splits`) 메모리에서 각 대화에 `split`을 붙여 주며, 이후의 필터링과 묶음 간 검사는 모두 이것을 사용합니다. 원본 파일은 바뀌지 않습니다. 대화를 다른 묶음으로 옮기려면 대화 전체를 잘라 다른 배열에 붙여 넣고, 같은 `group_id`의 다른 대화들과 그 대화가 참조하는 팩트 카드도 함께 옮기세요.

JSON은 `//` 주석을 지원하지 않습니다. 필드 설명은 여기서 하고, 노트북에서는 실제로 쓰이는 위치를 D1–D7로 표시합니다. JSON 파일 전체를 프롬프트에 밀어 넣지 마세요. 평가용 대화를 트레이너에 넘기지도 마세요.

### 2.2 첫 번째 팩트 카드

```json
{
  "id": "day-night",
  "category": "space",
  "topic": "昼夜",
  "text": "自转使地球表面各处交替朝向和背向太阳，形成主要的昼夜变化。太阳没有按昼夜关闭发光。地球还绕太阳公转；假定取消自转但保留公转，光照位置仍会随公转缓慢变化。",
  "source_url": "https://spaceplace.nasa.gov/seasons/en/",
  "checked_at": "2026-09-29",
  "source_review": "reference_read_claim_review_pending",
  "scope": "昼夜的入门解释；模型和比喻不能替代真实测量。",
  "kind": "fact",
  "reuse": "科学事实摘要和教学对话为原创中文表达；来源仅供事实核对，不复制来源的教材段落、题目或图像，不把网页正文纳入训练。链接不表示来源机构认可本数据或授予网页内容的训练许可。"
}
```

(대략적인 뜻: 주제는 "낮과 밤"입니다. `text`: "자전 때문에 지구 표면의 각 지점이 번갈아 태양을 향했다가 등지게 되며, 이것이 주된 낮과 밤의 변화를 만든다. 태양은 밤이라고 빛을 끄지 않는다. 지구는 태양 주위를 공전하기도 한다. 만약 자전이 멈추고 공전만 계속된다면, 빛을 받는 위치는 공전에 따라 여전히 천천히 바뀐다." `scope`: "낮과 밤에 대한 입문 수준 설명. 모형과 비유는 실제 측정을 대신할 수 없다." `reuse`: 요약과 대화는 중국어로 새로 쓴 것이며, 출처는 사실 확인에만 쓰였고, 링크가 있다고 해서 출처 기관이 이 데이터를 보증하거나 학습 라이선스를 준다는 뜻은 아님.)

| 필드 | 의미와 용도 |
|---|---|
| `id` | 기본 키. 대화의 `fact_ids`가 참조합니다 |
| `category/topic` | 분류와 주제. 검색, 통계, 검토용입니다 |
| `text` | 답변의 근거가 될 수 있는 과학 자료. 컨텍스트에 들어갑니다 |
| `kind/scope` | 자료 유형과 적용 범위. 컨텍스트에 들어갑니다 |
| `source_url`, `checked_at`, `source_review`, `reuse` | 출처와 검토 기록. 사람만 보며 **모델에는 들어가지 않습니다** |

프롬프트에 들어가는 것은 `id`, `text`, `kind`, `scope` 네 필드뿐입니다. 나머지 필드는 검토자를 위한 것이므로 처음 읽을 때는 건너뛰어도 됩니다.

#### 팩트 카드가 왜 필요한가: 자주 나오는 질문 세 가지

파인튜닝은 "어떻게 말할지"를 가르칩니다(0.1절). 여기까지 읽은 입문자는 보통 질문 세 개를 연달아 떠올립니다.

**Q1: 초등 과학은 상식이고 베이스 모델은 이미 알고 있습니다. 팩트 카드가 왜 필요한가요?**

맞습니다. 이런 상식은 베이스 모델이 대부분 알고 있습니다. "지식이 어디서 오는가"만 따진다면 팩트 카드는 꼭 필요하지 않습니다. 그래도 팩트 카드를 쓰는 이유는 지식을 보충하기 위해서가 아닙니다.

1. **학습이 "어떻게 말할지"만 배우게 하기 위해서입니다.** loss는 참고 답변에서 계산되고, 참고 답변에는 말투와 사실 내용이 모두 들어 있습니다. 입력에 자료가 없으면 모델은 "태양 쪽으로 돈다", "빛을 등진 쪽" 같은 내용을 가중치에 억지로 외워 넣을 수밖에 없고, 학습은 "말투"와 "지식"을 뒤섞어 배우게 됩니다. 자료가 입력에 바로 있으면 자료를 따라 말하기만 해도 내용을 맞게 예측할 수 있으므로, LoRA의 한정된 용량은 주로 "짧은 문장, 오개념부터 바로잡기, 안전한 작은 관찰 하나 제안하기"에 쓰입니다. 원리는 Q3에서 설명합니다.
2. **베이스 모델의 지식은 확인할 수도 고칠 수도 없지만, 팩트 카드는 가능합니다.** 4B 모델이 어느 문제에서 틀릴지(예를 들어 계절을 태양과의 거리 탓으로 돌리는 것) 미리 알 수 없고, 틀렸을 때 가중치를 열어 고칠 수도 없습니다. 팩트 카드는 출처와 검토 상태가 붙은, 눈에 보이는 텍스트입니다. 잘못 적었다면 카드 한 장만 고치면 다음 요청부터 반영됩니다. 백엔드에 비유하면, 비즈니스 규칙을 컴파일된 바이너리 곳곳에 흩어 두지 않고 설정이나 데이터베이스에 두는 것과 같습니다.
3. **카드에는 베이스 모델이 스스로 지키지 않는 경계가 담겨 있습니다.** 예를 들어 `day-night`의 `text`에는 "만약 자전이 멈추고 공전만 계속된다면, 빛을 받는 위치는 공전에 따라 여전히 천천히 바뀐다"고 적혀 있고, 참고 대화 두 번째 턴의 후속 질문은 이것을 근거로 합니다. `scope`에는 "모형과 비유는 실제 측정을 대신할 수 없다"고 적혀 있습니다. `kind`는 fact, legend, current를 구분하므로 전설을 사실처럼 말해서는 안 됩니다.
4. **이것이 실제 제품의 모습이고, 평가의 근거이기도 합니다.** 실제 비즈니스에서 모델이 설명해야 하는 것은 모델이 전혀 모르는 내용인 경우가 많습니다. 제품 사양, 특정 학교의 교과서, 오늘의 데이터 같은 것들입니다. 흔한 방식은 호출하는 쪽이 자료를 찾아 프롬프트에 넣고 모델은 그것을 알기 쉽게 설명하는 것으로, 흔히 RAG(검색 증강 생성)라고 부릅니다. 이 프로젝트는 팩트 카드로 이 패턴을 처음부터 끝까지 연습합니다. 블라인드 평가에서도 평가자는 각 주장을 팩트 카드와 대조해 근거가 있는지 판단합니다(6.6절).

**Q2: 팩트 카드도 학습 샘플에 들어 있으니, 학습이 끝나면 모델이 이 지식을 기억하게 되나요?**

그렇게 이해하면 안 됩니다. 팩트 카드는 학습 샘플의 **입력**이지 **학습 목표**가 아닙니다. 2.5절의 408토큰짜리 샘플에서 팩트 카드는 mask=0인 386개 토큰 안에 있습니다. 모델은 카드를 볼 수 있지만, "카드를 기억하지 못했다"고 해서 감점되지는 않습니다. loss가 시험하는 것은 단 하나, 이 자료를 보면서 쓴 답변이 참고 답변과 얼마나 비슷한가입니다.

| | 학습 후 배웠는가 | 이유 |
|---|---|---|
| 자료를 읽는 법, 자료로 답변을 구성하는 법 | 배웠습니다 | loss가 배우도록 밀어붙이는 것이 바로 이것입니다 |
| 자료 자체의 내용과 경계 | 믿을 수 없습니다 | 학습 중 자료가 늘 눈앞에 있었으므로 외울 필요가 없었습니다 |

솔직히 짚어 둘 점이 하나 있습니다. 참고 답변 자체에 사실 내용이 들어 있고 이 부분은 mask=1 영역에 있으므로, 모델은 흔한 표현을 조금은 덤으로 익힙니다. 하지만 1 에폭만, 샘플마다 한 번씩만 보기 때문에 그 기억은 얕습니다. 카드의 전체 내용과 경계를 기억할 수 없고, 무엇을 기억했고 무엇을 잘못 기억했는지 여러분이 알 방법도 없습니다. 그래서 배포할 때는 **매번 팩트 카드를 넘겨야 하며**, 5.5절의 호출 예제가 먼저 `read_dataset`으로 facts를 읽어 오는 것도 이 때문입니다.

직접 확인해 보고 싶다면, 학습이 끝난 뒤 같은 질문을 두 번 해 보세요. 한 번은 팩트 카드를 넣고, 한 번은 `CURRENT REFERENCE FACTS` 부분을 빼고 물은 다음 답변의 정확성과 경계를 비교합니다. 차이가 클수록 모델이 외운 지식이 아니라 그 자리에서 주어진 자료에 의존한다는 뜻입니다.

**Q3: 지식을 외우게 하려는 게 아니라면 학습 때는 왜 넣나요? 배포할 때만 넘기면 안 되나요?**

안 됩니다. 학습의 목적은 모델이 팩트 카드를 **기억**하게 하는 것이 아니라 **활용**하는 법을 가르치는 것이고, 활용하는 법을 배우려면 학습 중에 카드를 봐야 합니다. 신입 사원 교육에 비유해 보겠습니다.

| | 방식 A: 문답만 | 방식 B: 문답 옆에 제품 매뉴얼 첨부(이 프로젝트) |
|---|---|---|
| 교육 자료 | 고객이 X를 물음 → 표준 응답 Y | 고객이 X를 물음 + 관련 매뉴얼 페이지 → 표준 응답 Y |
| 길러지는 습관 | 질문을 들으면 기억에서 답을 외워 말함 | 먼저 매뉴얼을 찾아본 뒤 표준 어조로 설명함 |
| 실무에서 매뉴얼을 건네받으면 | 매뉴얼 읽기를 연습한 적이 없어 아마 옛 답을 계속 외움 | 바로 연습해 온 절차 그대로 |
| 매뉴얼 항목 하나가 업데이트되면 | 계속 옛 답을 말함 | 새 매뉴얼대로 말함 |
| 교육에서 다룬 적 없는 질문을 받으면 | 어렴풋한 기억으로 둘러대다 지어내기 쉬움 | 매뉴얼대로 설명하고, 매뉴얼에 없는 것은 지어내지 않음 |

이 프로젝트의 같은 샘플로 바꿔 보면, 목표 답변은 완전히 같고 입력만 다릅니다.

```text
不带事实卡：
  输入：为什么白天亮、晚上黑？
  目标：地球在不停转，我们住的地方转向太阳就是白天……

带事实卡：
  输入：[事实卡：自转使地球表面交替朝向和背向太阳……] 为什么白天亮、晚上黑？
  目标：地球在不停转，我们住的地方转向太阳就是白天……
```

(한국어로 옮기면: "팩트 카드 없음 — 입력: 왜 낮에는 밝고 밤에는 어두워요? 목표: 지구는 쉬지 않고 돌고 있어요. 우리가 사는 곳이 태양 쪽으로 돌면 낮이에요……" 그리고 "팩트 카드 있음 — 입력: [팩트 카드: 자전 때문에 지구 표면이 번갈아 태양을 향했다가 등지게 된다……] 왜 낮에는 밝고 밤에는 어두워요? 목표: 위와 같음.")

카드가 없으면 입력에는 아무 근거도 없는데 목표는 확정된 과학적 결론이므로, 1150개 샘플이 반복해서 강화하는 것은 "질문을 들으면 아무 근거 없이 확정된 결론을 내놓는다"입니다. 카드가 있으면 목표의 내용을 모두 입력에서 찾을 수 있으므로, 강화되는 것은 "주어진 자료에서 내용을 가져와 아이가 알아들을 수 있는 말로 바꿔 쓴다"입니다.

학습 때는 카드를 빼고 배포할 때만 넣으면 네 가지 문제가 생깁니다.

1. **모델이 자료 읽기를 연습한 적이 없습니다.** 배포 시 `CURRENT REFERENCE FACTS` 블록이 크게 추가되는데, 모델에게는 낯선 입력이라 무시될 수 있고 모델은 예전처럼 기억에 의존해 답합니다.
2. **자료를 고쳐도 반영되지 않습니다.** 어떤 카드가 잘못된 것을 발견했거나 어떤 카드의 `scope`에 적용 경계를 하나 추가하고 싶어도, 방식 A의 모델은 그에 따라 바뀌지 않습니다. 학습 데이터를 고쳐 다시 학습하는 수밖에 없습니다.
3. **새 주제에서 지어내기 쉽습니다.** 방식 A는 "근거 없이 결론을 내놓는" 습관을 기르므로, 학습 데이터에 없는 주제에서도 자신만만하게 결론을 내립니다.
4. **입력 형식이 맞지 않습니다.** 학습 때는 프롬프트에 팩트 카드가 없는데 배포 때는 있습니다. 모델이 익힌 말하기 방식은 학습 때 본 입력의 모양에 의존합니다. 5.5절이 "프롬프트는 학습 때와 같아야 한다"고 강조하는 이유이기도 합니다.

코드로 말하면, 학습은 함수 `answer = f(question, facts, grade_band, history)`를 배우는 것입니다. 학습 때 `question`만 준다면 배우는 것은 `f(question)`입니다. 배포 때 한 번도 써 본 적 없는 파라미터 `facts`를 추가로 넘긴다고 해서 모델이 그것을 쓰기 시작하지는 않습니다.

팩트 카드 없이도 학습할 수 있고 답할 수도 있습니다. 그 대가가 위에서 말한 것들입니다. 잘못을 고칠 수 없고, 과신하기 쉽고, 베이스 모델이 모르는 분야로 옮겨 갈 때마다 처음부터 다시 해야 합니다. "사실"과 "말투"를 분리하는 것은 이 프로젝트의 설계상 트레이드오프일 뿐 유일한 방법은 아니며, 그 효과는 결국 6장의 비교로 검증해야 합니다.

#### 팩트 카드가 쓰이는 곳

**왜 따로 저장하는가.** 카드 60장은 대화 600개가 `fact_ids`로 참조합니다(대화 하나가 여러 카드를 참조할 수 있음). 데이터베이스의 외래 키와 비슷합니다. 사실 하나는 한 곳에서만 고치면 되고, 그 카드를 참조하는 모든 대화는 다음에 읽힐 때 새 내용을 씁니다.

**왜 묶음별로도 격리하는가.** 카드 한 장은 한 묶음(train/val/test 중 하나)의 대화에서만 참조할 수 있습니다. 그렇지 않으면 검증·테스트 문제의 근거 자료를 모델이 학습 중에 이미 본 셈이 되어 평가 결과가 낙관적으로 나옵니다.

| 단계 | 코드 위치 | 팩트 카드를 쓰는 방식 |
|---|---|---|
| 읽기와 검증(D1) | [data.py](../lab/data.py) `validate` | `id`가 고유함, 모든 필드가 있음, `source_url`이 https임, `kind`는 fact/legend/current 중 하나여야 함, 대화의 `fact_ids` 항목이 모두 존재해야 함, 같은 카드를 train/val/test가 공유할 수 없음 |
| 프롬프트 구성(D3) | [common.py](../lab/common.py) `build_messages` | `fact_ids`로 카드를 가져와 `id/text/kind/scope`만 남기고, system 프롬프트의 `CURRENT REFERENCE FACTS:` 뒤에 JSON으로 씁니다. 출처와 검토 필드는 모델에 들어가지 않습니다 |
| 노트북 학습·검증 샘플 | 노트북 2단계 `prepare-data` 셀 | train 샘플 1150개와 val 샘플 115개 모두 `build_messages`를 거쳐 각자의 팩트 카드를 가집니다 |
| 노트북 관찰 문제 | 노트북 4단계 `cases` 셀 | 관찰 문제 세 개가 각각 `fact_id`를 하나씩 지정하고, 같은 카드로 학습 전후의 답변을 비교합니다 |
| CLI 스냅숏 | [prepare.py](../lab/prepare.py) | 스냅숏의 `facts.jsonl`에 그대로 씁니다. few-shot 예시는 자신의 `fact_ids`를 기록합니다 |
| A/B/C 비교 추론 | [infer.py](../lab/infer.py) | 스냅숏에서 `facts.jsonl`을 읽고, 세 그룹 모두 현재 문제에 대해 같은 팩트 카드를 받습니다(6.4절) |
| 블라인드 평가 | [evaluate.py](../lab/evaluate.py) `blind` | 채점표에 `fact_ids`가 들어 있고, 평가자는 팩트 카드와 대조해 `fact_claims`/`supported`를 채웁니다(6.6절) |
| 배포 후 호출 | 5.5절의 호출 예제 | `read_dataset`으로 facts를 읽고, `messages_for(fact_id, ...)`로 학습 때와 같은 system 프롬프트를 만듭니다 |

#### 출처와 검토 필드

`source_url`은 사람이 출처를 다시 확인하러 가는 입구이며, 프로그램이 자동으로 온라인에 접속해 읽지는 않습니다. `checked_at`은 참고 입구를 읽었다는 뜻일 뿐입니다. `source_review`가 `reference_read_claim_review_pending`이면 개별 주장이 아직 검토 대기 중이라는 뜻입니다. `reuse`는 출처 표기와 독자적으로 다시 썼다는 설명이며, 출처 기관이 이 데이터를 보증한다는 뜻이 아닙니다. NASA, NOAA, USGS 등의 공식 과학 교양 자료와 OpenStax 교재가 참고 입구이고, 본문은 중국어로 새로 정리한 것이며, 비유, 아이의 반응, 관찰 설계는 합성된 시범입니다. URL이 있다고 해서 모든 문장이 출처의 뒷받침을 받는다는 뜻은 아닙니다.

### 2.3 첫 번째 완전한 대화

```json
{
  "id": "day-night-01",
  "group_id": "day-night",
  "category": "space",
  "topic": "昼夜",
  "grade_band": "1-2",
  "scenario": "repair_misconception",
  "fact_ids": [
    "day-night"
  ],
  "provenance": {
    "type": "synthetic",
    "author": "Codex",
    "date": "2026-09-29",
    "method": "按主题逐项撰写知识、误解、追问、比喻边界和安全观察，再组合为10种教学对话路径；不是儿童真实对话，部分主题内回答复用。"
  },
  "review": {
    "status": "draft",
    "reviewer": "",
    "reviewer_kind": "",
    "notes": "待逐段核查科学事实、来源支持、适读学段、观察可行性、近重复与上下文衔接；成人审阅不代表已验证儿童探索兴趣。"
  },
  "turns": [
    {
      "user": "为什么白天亮、晚上黑？",
      "assistant": "地球在不停转，我们住的地方转向太阳就是白天，转到背光的一面就是晚上。",
      "behavior": "explain_at_grade"
    },
    {
      "user": "太阳晚上关灯睡觉了吧？",
      "assistant": "太阳没有在晚上关灯。是我们所在的地面转到了背向太阳的一侧。还可以接着想：如果地球不转，就没有黑夜了吗？",
      "behavior": "repair_then_offer_specific_question"
    }
  ]
}
```

(두 턴을 한국어로 옮기면: 아이가 "왜 낮에는 밝고 밤에는 어두워요?"라고 묻고, 어시스턴트가 "지구는 쉬지 않고 돌고 있어요. 우리가 사는 곳이 태양 쪽으로 돌면 낮이고, 빛을 등진 쪽으로 돌아가면 밤이에요."라고 답합니다. 이어서 아이가 "태양이 밤에는 불 끄고 자는 거죠?"라고 묻고, 어시스턴트가 "태양은 밤에 불을 끄지 않아요. 우리가 서 있는 땅이 태양을 등진 쪽으로 돌아간 거예요. 이어서 생각해 볼까요? 만약 지구가 돌지 않으면 밤이 아예 없어질까요?"라고 답합니다. `provenance.method`는 대화를 주제별로 작성해 10가지 교육용 경로로 조합했으며, 실제 아이와의 대화가 아니고, 주제 안에서 일부 답변을 재사용한다고 설명합니다. `review.notes`는 아직 사람이 확인해야 할 항목을 나열합니다.)

아이는 먼저 낮과 밤에 대해 묻고, 이어서 "태양이 잠을 잔다"는 추측을 내놓습니다. 참고 답변은 먼저 현상을 설명하고, 이어서 구체적인 오개념을 바로잡고, 계속 생각해 볼 수 있는 선택적 질문을 하나 남깁니다. "你真棒"("참 잘했어요!") 같은 상투적인 말버릇만 배우게 해서는 안 됩니다.

| 필드 | 모델에 들어가는가, 어디에 쓰이는가 |
|---|---|
| `id` | `day-night-01:0` 같은 샘플 id를 만들어 추적에 씁니다 |
| `group_id` | 과학 주제 하나를 한 그룹으로 묶습니다. 모든 학년대, 경로, 바꿔 쓴 버전은 같은 split에 있어야 합니다 |
| (소속 배열) | 이 대화는 `train` 배열에 있습니다. 읽을 때 `split="train"`으로 표시되고 D2는 train만 걸러 냅니다. 프롬프트에는 쓰이지 않습니다 |
| `grade_band` | **D3가 system 프롬프트에 "小学学段"(초등 학년대)으로 씁니다.** 눈에 보이는 입력입니다 |
| `fact_ids` | D3가 이 파일에서 팩트 카드를 골라 id/text/kind/scope만 넘깁니다 |
| `turns[].user` | 아이의 현재 질문입니다. 이전 질문은 history로 들어갑니다 |
| `turns[].assistant` | 현재 답변이 학습 목표입니다. 이전 답변은 컨텍스트일 뿐입니다 |
| `turns[].behavior` | 이 턴이 어떤 행동을 시범으로 보이는지 사람이 보기 위한 것입니다. **모델에 넘기지 않습니다** |
| `category/topic/scenario` | 통계와 검토용 라벨입니다. "아이가 무엇을 틀렸는지"를 입력에 몰래 넣지 않습니다 |
| `provenance`, `review` | 합성 방법과 검토 상태로, 사람만 봅니다. 현재 모든 대화는 `draft`입니다 |

이 표에서 하나만 기억한다면 이것입니다. **모델이 보는 것은 system 프롬프트(역할 + 학년대 + 팩트 카드), history, 현재 user 턴뿐이고, 배우는 것은 현재 assistant 턴뿐입니다.** 2.5절에서 이 문장을 실제 토큰과 마스크로 보여 드립니다.

### 2.4 대화를 답변 단위로 펼치기

`day-night-01`은 두 턴이므로 샘플 두 개로 펼쳐집니다.

| 샘플 | 컨텍스트 | loss에 기여하는 목표 |
|---|---|---|
| `day-night-01:0` | 역할 + 학년대 + 낮과 밤 자료 + "왜 낮에는 밝고 밤에는 어두워요" | 첫 번째 참고 답변 + EOS |
| `day-night-01:1` | 같은 역할, 학년대, 자료 + 1턴 문답 + "태양이 잠을 잔다"는 추측 | 두 번째 참고 답변 + EOS |

첫 번째 샘플은 두 번째 턴을 볼 수 없습니다. 두 번째 샘플에서 history 속 이전 답변은 이번 턴의 loss에 기여하지 않습니다. train 대화 500개 중 350개가 두 턴, 150개가 세 턴이므로 **샘플 1150개**가 나옵니다. 1150은 토큰 수도 아니고 옵티마이저 스텝 수도 아닙니다.

**두 턴짜리 대화는 "두 번 학습한다"는 뜻인가요?** 같은 내용을 두 번 학습하는 것이 아니라, 이 대화가 독립된 샘플 두 개를 기여하고 각 샘플이 1 에폭에 한 번씩 학습된다는 뜻입니다. 샘플 1150개는 트레이너에 들어간 뒤 섞이고 16개마다 파라미터가 업데이트되므로, `day-night-01:0`과 `day-night-01:1`은 보통 서로 다른 스텝에 들어갑니다. 첫 번째 답변은 첫 번째 샘플에서만 loss에 포함되고, 두 번째 샘플에서는 history일 뿐입니다.

**턴이 더 많아도 같은 규칙입니다.** 한 세션의 전체 채팅 기록과 같습니다. k번째 샘플은 앞선 k−1턴의 문답을 모두 history로 취급하고 k번째 답변만 배웁니다. 이는 배포 시 호출 방식과 일치합니다. 서버는 상태를 저장하지 않고 클라이언트가 매번 전체 history를 보냅니다(5.5절). 알아 둘 차이점이 두 가지 있습니다.

- 학습 때 history에는 **참고 답변**이 들어 있고, 배포 때 history에는 **모델이 실제로 한 말**이 들어 있어 참고 답변과 다를 수 있습니다. 6.5절의 연속 대화 모드가 바로 이 차이를 점검합니다.
- 뒤쪽 샘플일수록 길어지고, history는 샘플마다 다시 계산됩니다. 이 프로젝트의 검증은 2–4턴 대화만 받아들이며, 4096토큰을 넘으면 몰래 잘라 내지 않고 즉시 오류를 냅니다.

### 2.5 마스크: 모델이 실제로 배우는 토큰은 무엇인가

이 프로젝트의 토크나이저로 `day-night-01:0`을 렌더링한 결과입니다(실제 출력이며, system 프롬프트 중간의 역할 규칙 몇 줄은 생략했습니다). 샘플 전체는 408토큰이고, 그중 마지막 22토큰만 loss에 기여합니다.

```text
mask │ 渲染后的文本
─────┼──────────────────────────────────────────────────────────
  0  │ <|im_start|>system
  0  │ 你是陪小学生探索科学的伙伴。用中文，先回应孩子真正的问题，再按需要解释。
  0  │ ……（角色规则共 10 行）
  0  │ 小学学段：1-2 年级。
  0  │ CURRENT REFERENCE FACTS:
  0  │ [{"id": "day-night", "text": "自转使地球表面……", "kind": "fact",
  0  │   "scope": "昼夜的入门解释；……"}]<|im_end|>
  0  │ <|im_start|>user
  0  │ 为什么白天亮、晚上黑？<|im_end|>
  0  │ <|im_start|>assistant
  1  │ 地球在不停转，我们住的地方转向太阳就是白天，转到背光的一面就是晚上。<|im_end|>
```

(헤더는 "mask │ 렌더링된 텍스트"라는 뜻입니다. system 프롬프트는 "너는 초등학생과 함께 과학을 탐구하는 친구다. 중국어를 쓰고, 먼저 아이의 진짜 질문에 답한 뒤 필요에 따라 설명하라."로 시작하고, 이어서 "(역할 규칙 총 10줄)"과 "초등 학년대: 1-2학년."이 나옵니다.)

mask가 0인 386개 토큰은 모델이 볼 수 있지만 여기서 loss를 계산하지 않습니다. mask가 1인 마지막 22개 토큰만 학습 목표입니다. 팩트 카드는 이 386개 토큰 안에 있습니다. 모델은 카드를 외우지 않지만 카드를 보면서 답하는 법을 배워야 하므로, 학습 때도 반드시 넣어야 합니다(2.2절 Q2, Q3).

마지막 줄을 토큰으로 나누면 `地球` `在` `不停` `转` `，` `我们` `住` `的地方` `转向` `太阳` `就是` `白天` `，` `转` `到` `背` `光` `的一面` `就是` `晚上` `。` `<|im_end|>`입니다. 학습 중 모델은 이 22개 위치에서 각각 "다음 토큰"을 한 번씩 예측하고, 얼마나 틀렸는지가 loss가 됩니다. 그 앞의 386개 위치는 컨텍스트만 제공합니다.

왜 system과 user 부분까지 모델이 배우게 하지 않을까요? 배포 후에는 그 내용을 항상 호출하는 쪽이 제공하므로, 모델은 "이런 입력을 보면 어떻게 답해야 하는가"만 배우면 되기 때문입니다. user 턴까지 loss에 넣으면 모델은 아이의 질문을 흉내 내는 데 힘을 쓰고, 다음 질문을 스스로 지어내는 법까지 배울 수 있습니다.

`rows`에는 `case_id/prompt/completion/input_ids/completion_mask`가 남아 있어 살펴보기 편합니다. 실제 학습에는 마지막 두 열만 씁니다. 노트북은 첫 번째 행의 전체 프롬프트, 목표, 실제 토큰 길이를 출력합니다. 예전 시나리오의 길이 숫자를 그대로 쓰지 마세요.

`completion_mask=0`은 컨텍스트, `=1`은 현재 답변과 EOS를 표시합니다. TRL은 컨텍스트와 패딩 위치의 labels를 `-100`으로 설정하므로 그 위치에서는 loss를 직접 계산하지 않지만, 모델은 답변을 예측할 때 여전히 컨텍스트를 볼 수 있습니다.

EOS는 <code>&lt;&#124;im_end&#124;&gt;</code>이며, 목표마다 정확히 한 번 나타나 모델이 멈추는 법을 배우게 합니다. PAD는 EOS와 다릅니다. 4096토큰을 넘으면 오류가 나므로 샘플을 다시 써야 하며, 답변이 몰래 잘리는 일은 없습니다.

### 2.6 정리: JSON 파일 하나에서 파라미터 업데이트까지 7단계

앞의 다섯 절은 "데이터의 모습 → 나누는 방법 → 모델이 보고 배우는 것" 순서로 데이터를 다뤘습니다. 이를 하나로 이으면 아래 7단계가 됩니다. 노트북의 코드 주석은 D1–D7로 각 단계가 어느 줄에서 일어나는지 표시합니다. 학습할 때 대조하며 보면 어느 줄이 이 장의 어느 부분을 하고 있는지 알 수 있습니다.

| 단계 | 하는 일 | 이 장의 해당 위치 |
|---|---|---|
| D1 읽기 | `dataset.json`을 읽고 각 대화에 소속 묶음을 표시하며, 팩트 카드 참조와 묶음 간 격리를 검사합니다 | 2.1절, 2.2절 |
| D2 분할 | train만 가져와 각 대화를 답변 단위로 샘플로 나눕니다. history에는 이전 턴만 들어갑니다 | 2.4절 |
| D3 입력 구성 | 역할 규칙 + 학년대 + 팩트 카드 + history + 현재 질문을 하나의 messages 리스트로 조립합니다 | 2.2절, 2.3절 |
| D4 목표 표시 | 채팅 템플릿을 적용하고 토큰화한 뒤, 현재 답변과 EOS를 mask=1로 표시합니다 | 2.5절 |
| D5 트레이너에 전달 | `input_ids`와 `completion_mask` 두 열만 TRL에 넘깁니다 | 2.5절 |
| D6 재확인 | 트레이너가 실제로 만든 labels를 확인합니다. 컨텍스트와 패딩 위치는 모두 -100(loss 없음)입니다 | 2.5절 |
| D7 기록 남기기 | 이번 실행의 데이터 사본과 지문(fingerprint)을 저장한 뒤에야 `trainer.train()`이 실제로 파라미터를 업데이트합니다 | 4장 |

### 2.7 데이터를 고치거나 내 데이터로 바꾸기

실습을 위해 데이터를 고칠 필요는 없습니다. 직접 고쳐 보고 싶을 때 이 절을 읽으세요.

**기존 데이터 수정.** 말투를 바꾸려면 `assistant`를 고칩니다. 새로운 반응 경로를 추가할 때는 앞뒤 턴도 함께 조정해서, 모델이 실제로 하지 않은 말을 아이가 인용하는 일이 없게 하세요. 팩트 카드를 고쳤다면 그 카드를 참조하는 모든 대화를 다시 확인합니다. 고친 뒤에는 먼저 구조 검사를 돌립니다.

```bash
python -m lab.data --input data/dataset.json --allow-draft
```

`{'train': 500, 'val': 50, 'test': 50}`이 출력되어야 합니다. 이 검사는 구조만 확인합니다. 모든 필드가 있는지, 팩트 참조가 존재하는지, 주제가 묶음을 넘나들지 않는지, 답변마다 물음표가 최대 하나인지를 봅니다. 과학 내용이 맞는지는 검사하지 않습니다.

**수정 사항 반영하기.** 이미 학습한 adapter는 JSON을 고쳤다고 해서 바뀌지 않습니다. 노트북에서 `RUN_DIR`을 새 디렉터리(예: `runs/science-002`)로 바꾸고 2단계부터 다시 실행하세요. 각 학습 실행 디렉터리에는 "이번 실행이 어떤 데이터를 썼는지"에 대한 기록으로 `dataset.json` 사본이 자동으로 남습니다. 평소 작업에서 이 사본은 편집하지 마세요.

**내 데이터로 바꾸기.** Alpaca(instruction/output), ShareGPT(conversations) 같은 흔한 오픈소스 SFT 데이터 형식은 본질적으로 이 프로젝트와 같습니다. "대화 메시지 리스트 + 그중 어느 것이 기대 출력인가"이며, JSON 배치만 다를 뿐입니다. 데이터를 바꿀 때는 주로 두 곳을 고칩니다. 데이터를 train/val/test 세 묶음의 대화로 정리하고, 필요에 따라 D3의 `build_messages`를 조정해 system 프롬프트에 무엇을 넣을지 정합니다.

### 2.8 선택: 내 컴퓨터에서 데이터 검사 돌려 보기

위 내용은 읽기만 해도 이해할 수 있습니다. GPU를 빌리기 전에 토큰화 결과를 직접 눈으로 보고 싶거나, 데이터를 고친 뒤 먼저 검사해 보고 싶다면, 내 컴퓨터(Mac 또는 Linux, Python 3.11)에 PyTorch 없는 가벼운 환경을 설치할 수 있습니다. 몇 분이면 끝나고 그래픽카드도 필요 없습니다.

### 3.2 먼저 nvidia-smi 읽기: 드라이버, CUDA, VRAM

GPU 호스트에 로그인한 뒤 가장 먼저 할 일은 `nvidia-smi`를 실행하는 것입니다. 출력은 대략 다음과 같습니다.

```text
+-----------------------------------------------------------------------------------------+
| NVIDIA-SMI 560.35.03              Driver Version: 560.35.03      CUDA Version: 12.6     |
|-----------------------------------------+------------------------+----------------------+
| GPU  Name                 Persistence-M | Bus-Id          Disp.A | Volatile Uncorr. ECC |
| Fan  Temp   Perf          Pwr:Usage/Cap |           Memory-Usage | GPU-Util  Compute M. |
|=========================================+========================+======================|
|   0  NVIDIA GeForce RTX 4090        Off | 00000000:01:00.0 Off   |                  Off |
| 30%   35C    P8             20W / 450W  |       0MiB / 24564MiB  |      0%      Default |
+-----------------------------------------+------------------------+----------------------+
| Processes:                                                                              |
|  GPU   GI   CI        PID   Type   Process name                              GPU Memory |
|=========================================================================================|
|  No running processes found                                                             |
+-----------------------------------------------------------------------------------------+
```

| 필드 | 의미 | 신경 써야 할 점 |
|---|---|---|
| `Driver Version` | 커널 드라이버 버전으로, 플랫폼 이미지가 정하며 일반 사용자는 바꿀 수 없습니다 | 아래 CUDA 상한을 결정합니다 |
| `CUDA Version` | **이 드라이버가 지원하는 최고 CUDA 버전**이며, 설치된 CUDA가 아닙니다 | PyTorch의 `cu126`은 이 값이 12.6 이상이어야 하고, vLLM 0.21의 `cu129`는 12.9 이상이어야 합니다 |
| `Memory-Usage` | 사용 중 / 전체 VRAM | 학습 전에는 0에 가까워야 합니다. 학습 중에는 얼마까지 오르는지 보십시오. vLLM을 시작하기 전에 학습 커널이 VRAM을 해제했는지 확인하십시오 |
| `GPU-Util` | GPU 연산 사용률 | 학습과 부하 테스트 중에는 꽤 높게 유지되어야 합니다. 오랫동안 0이라면 프로그램이 CPU에서 막혀 있거나 대기 중이라는 뜻입니다 |
| `Processes` | VRAM을 점유한 프로세스 | 깜빡하고 종료하지 않은 Jupyter 커널을 찾는 데 씁니다 |

**드라이버, CUDA, PyTorch의 관계:** 드라이버는 운영체제에 설치되며 GPU에 묶여 있습니다. CUDA는 NVIDIA의 연산 라이브러리이며, PyTorch wheel이 필요한 사본을 함께 담고 있습니다(`torch==2.8.0`의 `cu126` 접미사는 "CUDA 12.6 런타임 내장"이라는 뜻입니다). 그러므로 CUDA 툴킷을 직접 설치할 필요가 없습니다. 유일한 제약은 드라이버가 지원하는 버전이 wheel에 내장된 버전보다 낮으면 안 된다는 것입니다. 이미지 이름의 `CUDA12.6`은 사전 설치된 툴킷을 가리키며 드라이버 상한과는 별개입니다. `nvidia-smi`를 기준으로 판단하십시오.

비유하자면 드라이버는 OS 커널 버전, CUDA 런타임은 앱이 함께 번들하는 의존성, `nvidia-smi`는 `top`과 `free -h`를 합친 것과 같습니다.

VRAM과 호스트 RAM은 서로 독립된 두 메모리입니다. 모델 가중치, 학습 중간 결과, KV 캐시는 모두 VRAM에 있어야 하며, 호스트의 100 GB RAM은 데이터 중계와 CPU에서의 병합에만 쓰입니다. VRAM이 부족하면 `CUDA out of memory` 오류가 나며, 해결책은 사용량을 줄이는 것(양자화, 더 짧은 샘플, 더 낮은 동시성)이지 호스트 RAM을 늘리는 것이 아닙니다.

| 번들에 없는 것 | 이유 | 어디서 오는가 |
|---|---|---|
| 8 GB 가중치 샤드 `model-0000X-of-00003.safetensors` | 너무 커서 업로드가 느립니다. GPU 호스트는 중국 내 미러에서 더 빠르게 내려받습니다 | 3.4절에서 GPU에서 다운로드하고 `download-lock.json`으로 검증합니다 |
| PyTorch와 기타 의존성 자체 | GPU와 CUDA 버전에 묶여 있으므로 GPU 호스트에서 설치해야 합니다 | 아래 pip 명령이 `requirements-*.txt`에 따라 설치합니다 |
| 학습 결과 `runs/`, 스냅숏 `data/processed/` | GPU에서 생성되는 산출물입니다 | 4장의 학습과 4.6절의 스냅숏 생성 시 만들어집니다 |

토크나이저를 포함하는 것은 GPU 호스트가 가중치를 내려받기 전에 모델 버전을 확인할 수 있게 하기 위해서이며, 그러면 다운로드 시에는 가중치 샤드 3개만 채우면 됩니다. Notebook은 `data/dataset.json`을 직접 읽으므로 `lab.prepare`를 먼저 실행할 필요가 없습니다. 50 GB 데이터 디스크에는 학습 환경, 원본 가중치, 병합 가중치, 추론 환경이 동시에 들어가야 하므로, 전체 배포까지 하려면 100 GB로 확장할 것을 권합니다.

GPU 터미널에서 프로젝트 환경을 구축합니다.

```bash
python3.11 -m venv .venv-train
.venv-train/bin/python -m pip install --upgrade pip
.venv-train/bin/python -m pip install torch==2.8.0 --index-url https://download.pytorch.org/whl/cu126
.venv-train/bin/python -m pip install -r requirements-train.txt -r requirements-download.txt -r requirements-notebook.txt
.venv-train/bin/python -m pip check
.venv-train/bin/python -m ipykernel install --user --name lora-train --display-name "LoRA · Python 3.11"
```

학습에는 버전이 고정된 Torch/Transformers/TRL/PEFT를 사용합니다. ModelScope는 다운로드에만 쓰이고, ipykernel은 플랫폼의 Jupyter가 이 환경을 쓸 수 있게 해 줍니다. 튜토리얼의 이전 버전에 따라 이미 `.venv-train`을 만들었다면 재사용할 수 있습니다. 새로 추가된 의존성을 설치하고 커널을 등록하면 됩니다. 일반 Python 패키지 인덱스가 느리다면 플랫폼이 제공하는 PyPI 미러를 써도 됩니다. 모델 다운로드 소스와 pip 패키지 소스는 서로 별개입니다.

**`download.pytorch.org`에 접속할 수 없을 때(`Network is unreachable`이 나거나 재시도가 끝없이 반복될 때):** 세 번째 명령은 `--index-url`로 다운로드 주소를 임시로 PyTorch 공식 인덱스로 바꾸는데, 중국 내 호스트는 여기에 접속하지 못하는 경우가 많습니다. 일반 PyPI 미러(칭화, 알리바바 등)로만 바꿔서는 해결되지 않습니다. 이들 미러에는 PyPI의 기본 torch 2.8.0(CUDA 12.8 내장)만 있는데, 아래 자체 점검은 12.6을 요구하기 때문입니다. 대신 같은 `2.8.0+cu126` 패키지가 있는 Alibaba Cloud의 PyTorch 미러를 사용하십시오.

```bash
.venv-train/bin/python -m pip install 'torch==2.8.0+cu126' -f https://mirrors.aliyun.com/pytorch-wheels/cu126/
```

`-f`는 pip에게 torch 본체만 그 페이지에서 찾으라고 지시할 뿐이며, `nvidia-*`, `triton` 같은 torch의 의존성은 여전히 설정된 PyPI 소스에서 받습니다. 버전을 `2.8.0+cu126`으로 적으면 pip가 PyPI의 cu128 빌드를 설치하는 것을 막을 수 있습니다. 설치가 끝나면 위의 네 번째 명령(`requirements-*.txt`)부터 이어서 실행하십시오. 나머지 단계는 같습니다. PyPI 소스를 영구적으로 고정하려면 `.venv-train/bin/python -m pip config set global.index-url https://pypi.tuna.tsinghua.edu.cn/simple`을 실행하고, `pip config list`로 현재 설정을 확인하십시오.

```bash
.venv-train/bin/python - <<'CHECK'
import sys, torch, transformers, trl, peft, bitsandbytes
print("Python:", sys.executable)
```

### 3.4 중국 내 GPU 호스트에서 전체 가중치 다운로드

기본적으로 알리바바의 **ModelScope**를 사용하며, 저장소는 [Qwen/Qwen3-4B-Instruct-2507](https://www.modelscope.cn/models/Qwen/Qwen3-4B-Instruct-2507)입니다. ModelScope에는 자체 SDK가 있으며, `HF_ENDPOINT`를 ModelScope 홈페이지로 지정하는 방식이 아닙니다.

```bash
.venv-train/bin/python -m lab.download --source modelscope --output models/qwen3-4b
```

`--tokenizer-only`를 붙이지 마십시오. 이 명령은 업로드 번들의 `model-lock.json`과 이미 검증된 토크나이저를 유지한 채, 빠진 가중치 샤드 3개를 채웁니다. 네트워크가 끊기면 같은 명령을 다시 실행하십시오. `.cache`와 버전 잠금이 유지되므로 데이터를 다시 준비할 필요가 없습니다.

[download.py](../lab/download.py)는 [download-lock.json](../lab/download-lock.json)에 따라 원격 파일 크기와 SHA-256을 확인한 다음, 실제로 내려받은 내용을 확인합니다. ModelScope는 `master`에서 파일을 가져오지만, 여기서 고정한 Hugging Face 리비전과 **바이트 단위로 동일**해야 합니다. 저장소 내용이 바뀌었다면 중단하므로 버전이 섞이는 일이 없습니다. 목록에 있는 12개 파일의 메타데이터는 양쪽 소스에서 모두 확인했으며, 가중치 파일 3개의 합계는 약 8.0 GB(10진 기준)입니다.

다운로드한 뒤에는 오프라인 점검만 따로 실행할 수 있습니다.

```bash
.venv-train/bin/python -m lab.download --check-only --output models/qwen3-4b
```

**“校验通过：12 个文件；完整模型权重已就绪”**(“검증 통과: 파일 12개, 전체 모델 가중치 준비 완료”)가 출력되고 명령이 정상 종료된 경우에만 학습으로 넘어가십시오. 디렉터리에는 다음이 있어야 합니다.

```text
models/qwen3-4b/
├── model-lock.json
├── config.json
├── tokenizer.json
├── tokenizer_config.json
├── model.safetensors.index.json
├── model-00001-of-00003.safetensors
├── model-00002-of-00003.safetensors
```

다른 설정, 어휘, 라이선스 파일도 남겨 두십시오. `model-lock.json`과 가중치 인덱스만 보이거나, 로그에 `Returning existing local_dir`라고 나온다고 해서 가중치가 다운로드되었다는 뜻은 아닙니다. 현재 다운로더는 이런 불완전한 결과를 거부합니다.

#### 대안: 중국 내 Hugging Face 미러로 다운로드

ModelScope에 접속할 수 없다면 `hf-mirror.com`을 명시적으로 선택할 수 있습니다.

```bash
.venv-train/bin/python -m lab.download --source hf-mirror --output models/qwen3-4b
.venv-train/bin/python -m lab.download --check-only --output models/qwen3-4b
```

코드가 미러 주소를 Hugging Face SDK에 명시적으로 넘기므로, 설치된 패키지의 소스 코드를 고치거나 전역 환경 변수를 영구적으로 바꿀 필요가 없으며, 같은 버전 잠금과 파일 검증을 그대로 사용합니다. 이 미러는 독립된 서드파티 서비스로, Alibaba Cloud 공식 ModelScope가 아닙니다. 접속 가능 여부는 GPU 호스트의 네트워크에 달려 있습니다. [Hugging Face 다운로드 API](https://huggingface.co/docs/huggingface_hub/package_reference/file_download)를 기반으로 합니다.

개발 머신에서는 ModelScope의 설정/토크나이저 다운로드를 테스트해 검증을 통과했고, 큰 가중치 파일 3개도 몇 바이트만 받는 다운로드 테스트를 통과했습니다. **이 GPU 호스트에서는 아직 8 GB 전체 가중치를 다운로드하지 않았습니다.** 최종적으로는 호스트에서의 전체 검증 결과를 기준으로 삼습니다.

| 증상 | 대처 방법 |
|---|---|
| `huggingface.co` / `Network is unreachable` | `--source modelscope`를 명시하거나, 대안인 `--source hf-mirror`를 쓰십시오 |
| 가중치 샤드 누락 | 같은 디렉터리에서 `--tokenizer-only` 없이 전체 다운로드를 다시 실행하십시오 |
| 로컬 파일 해시 불일치 | 보고된 파일을 옆으로 옮겨 백업한 뒤, 버전 잠금은 유지한 채 다시 다운로드하십시오. 점검을 건너뛰지 마십시오 |
| 원격 파일이 고정 버전과 다름 | 그 소스 사용을 중단하고 다른 소스에서 고정된 내용을 받아 보십시오. 해시를 고쳐서 통과시키지 마십시오 |
| `No space left on device` | 프로젝트가 있는 파티션을 확인하고 확장하거나 데이터 디스크로 옮기십시오. 백업하지 않은 실험 결과는 지우지 마십시오 |

### 4.1 각 단계가 하는 일

| Notebook 단계 | 실행 내용 | 확인할 점 |

학습 전후의 질문 3개는 같은 역할 프롬프트, 사실, NF4 정밀도, 그리디 디코딩을 사용하므로 가중치 변화의 효과를 비교할 수 있습니다.

#### `trainer.train()` 내부에서 일어나는 일

7번 셀은 `trainer.train()` 한 줄뿐이지만, 1장의 모든 개념을 하나로 엮습니다. 한 스텝은 다음과 같이 진행됩니다.

```text
重复 16 次（梯度累积）：
    取 1 条样本的 input_ids（约 400 个 Token）
    前向：NF4 基座临时还原成 BF16 参与计算，LoRA 的 A、B 叠加在 7 类线性层上
          → 每个位置输出“下一个 Token”的概率
    loss：只在 completion_mask = 1 的位置（参考回答 + EOS）比较预测和答案
    反向：算梯度，但只算到 LoRA 的 A、B 上；基座参数冻结，没有梯度
          → 梯度累加起来，不立刻更新
AdamW 按累加的梯度更新 LoRA 参数一次（学习率按 warmup + cosine 变化）
step + 1；每 12 步在 115 条 val 样本上只做前向、算一次验证 loss；每 25 步存一次检查点
```

풀어 쓰면 이렇습니다. 16번 반복합니다(그래디언트 누적). 샘플 1개의 `input_ids`(약 400 토큰)를 가져옵니다. 순전파에서는 NF4 베이스를 임시로 BF16으로 역양자화해 계산에 쓰고, LoRA의 A와 B를 7종류의 선형 레이어 위에 더해서, 각 위치가 "다음 토큰"의 확률을 출력합니다. loss는 `completion_mask = 1`인 위치(참조 답변 + EOS)에서만 예측과 정답을 비교합니다. 역전파는 LoRA의 A와 B까지만 그래디언트를 계산하며(베이스 파라미터는 동결되어 그래디언트가 없습니다), 그래디언트는 곧바로 적용하지 않고 누적합니다. 그런 다음 AdamW가 누적된 그래디언트로 LoRA 파라미터를 한 번 업데이트합니다(학습률은 warmup + cosine을 따릅니다). 스텝 + 1. 12스텝마다 val 샘플 115개에 대해 순전파만 실행해 검증 loss를 계산하고, 25스텝마다 체크포인트를 저장합니다.

72스텝이 끝나면 샘플 1150개를 각각 정확히 한 번씩 본 것이 됩니다(1 에폭). 전체 과정에서 베이스 파라미터 40억 개 중 단 하나도 바뀌지 않고, 약 3300만 개의 LoRA 파라미터만 바뀝니다. 그래서 8번 셀은 "LoRA 텐서가 실제로 바뀌었는지"를 따로 확인합니다.

### 4.2 이렇게 설정한 이유

| 설정 | 현재 값 | 이유 |
|---|---|---|
| 베이스 모델 | Qwen3-4B-Instruct-2507, 고정 리비전 | 비교 기준을 고정합니다 |
| 학습 방식 | NF4 + BF16 연산 + LoRA | 24 GB GPU 한 장에서 소수의 파라미터만 업데이트합니다 |
| LoRA | rank 16, alpha 32, dropout 0.05 | 연습용으로 흔히 쓰는 출발점입니다 |
| 대상 레이어 | q/k/v/o 및 gate/up/down 프로젝션 | 어텐션과 피드포워드 프로젝션을 모두 포함합니다 |
| 마이크로 배치 / 누적 | 1 / 16 | VRAM에는 한 번에 샘플 1개만 올리고, 16개를 누적한 뒤 한 번 업데이트합니다 |
| 옵티마이저 / 학습률 | AdamW / 1e-4 | 짧은 warmup과 cosine 스케줄을 함께 씁니다 |
| 길이 / 이어 붙이기 | 4096 / packing 없음 | 타깃을 조용히 잘라 내지 않으며, 감독 범위를 확인하기 쉽게 유지합니다 |
| 학습량 | 1 에폭 ≈ 72스텝 | 모든 학습 샘플을 한 번씩 보며 학습 전후 차이가 드러납니다. 파이프라인만 테스트하려면 10으로 바꾸십시오 |
| 검증 | 12스텝마다 검증 loss 계산 | 학습에 쓰지 않은 주제로 과적합 여부를 관찰합니다 |

각 설정 파라미터의 의미, 그 값을 고른 이유, 바꾸면 어떻게 되는지는 Notebook의 해당 코드 셀 아래 표(3, 5, 6단계)에 있으므로 여기서는 반복하지 않습니다.

### 4.3 학습 중 GPU 관찰하기: VRAM은 어디에 쓰이는가

학습을 시작하기 전에 GPU 터미널을 하나 더 엽니다.

```bash
nvidia-smi --query-gpu=memory.used,memory.total,utilization.gpu --format=csv -l 2
```

2초마다 한 줄씩 출력됩니다. 숫자가 어떻게 변하는지 아래 추정치와 비교해 보십시오.

| 사용처 | 추정치 | 나타나는 시점 |
|---|---|---|
| CUDA 컨텍스트 | 약 0.5 GB | 커널이 처음 GPU를 사용할 때 |
| NF4 베이스 가중치 | 약 2.5~3 GB(4B × 0.5바이트, 단어 임베딩 등 일부 레이어는 BF16 유지) | 3단계에서 모델을 로드한 뒤 |
| LoRA 파라미터 + 그래디언트 + AdamW 상태 | 3300만 파라미터 × 약 16바이트 ≈ 0.5 GB | 5~7단계 |
| 활성화 값 | 샘플 길이에 따라 달라지며, 그래디언트 체크포인팅으로 비교적 작게 유지됩니다 | 학습 중, 각 샘플의 순전파/역전파 시 |

이 데이터셋에서 가장 긴 샘플은 약 550 토큰이므로, 최대 VRAM은 보통 24 GB보다 훨씬 낮습니다. 학습이 끝나면 `training-complete.json`에 PyTorch 기준 `peak_allocated_gib`와 `peak_reserved_gib`가 기록됩니다. `nvidia-smi`의 숫자는 CUDA 컨텍스트와 캐시 풀까지 포함하므로 조금 더 큽니다. 학습 중 GPU 사용률은 꽤 높게 유지되어야 하며, 오랫동안 낮게 머문다면 병목은 데이터 로딩이나 CPU에 있을 수 있습니다.

이번의 짧은 샘플들의 VRAM으로 4096 토큰 샘플의 비용을 추정하지 마십시오. OOM이 나면 먼저 다른 커널을 종료하고, 그다음 샘플 길이를 확인하십시오. 정말로 상한을 낮춰야 한다면 참조 답변을 잘라 내지 말고 지나치게 긴 샘플을 다시 작성하십시오.

프로젝트가 `/root/llm-lora-tutorial`에 있다면 기본 산출물은 아래 위치에 있습니다. 데이터 디스크에 있는 프로젝트라면 Notebook이 출력한 절대 경로를 기준으로 하십시오.

```text
├── trainer_state.json          # training log and global_step

├── dataset.json                # copy of the data actually read in this run; don't edit it day to day
```

### 4.5 loss 곡선을 읽고 답변 비교하기

`loss-curve.png` 읽는 법: 학습 loss가 전체적으로 내려가면 모델이 참조 답변에 맞춰지고 있다는 뜻이고, 검증 loss도 함께 내려가면 이런 답변 방식이 처음 보는 주제에도 통한다는 뜻입니다. 학습 loss는 계속 내려가는데 검증 loss가 오르기 시작하면 과적합입니다. 두 선 모두 움직이지 않는다면 학습률, 학습 가능한 파라미터, 마스크부터 확인하십시오.

아래 그림은 2026-10-11에 RTX 4090(24 GB)에서 이 장의 기본 설정으로 1 에폭 전체를 실행한 실제 곡선이며, 약 26분이 걸렸습니다.

![RTX 4090에서 1 에폭을 실행한 실제 loss 곡선: 학습 loss는 약 6에서 2.5 안팎까지 빠르게 떨어진 뒤 천천히 내려가고, 검증 loss는 2.51에서 1.96까지 내려간 뒤 평탄해집니다](../images/loss-curve-rtx4090-2026-10-11.png)

| 스텝 | 12 | 24 | 36 | 48 | 60 | 72 |
|---|---:|---:|---:|---:|---:|---:|
| 검증 loss | 2.51 | 2.19 | 2.03 | 1.98 | 1.96 | 1.96 |

이 곡선을 구간별로 읽어 보겠습니다.

- **처음 10스텝: 학습 loss가 약 6에서 2.5 안팎으로 급락합니다.** 베이스 모델이 익숙한 말투는 이 짧고 구어체인 참조 답변과 매우 다르기 때문에, 처음에는 크게 "놀랍니다". LoRA는 형식과 어조부터 배웁니다. 처음 몇 스텝 동안은 학습률이 아직 warmup 중이므로 1~3스텝에서는 거의 내려가지 않습니다.
- **10~48스텝: 두 선이 함께 천천히 내려갑니다.** "어떻게 말할지"를 실제로 배우는 단계입니다. 검증 loss도 내려가고 있으므로, 배운 것이 처음 보는 주제 5개에도 통한다는 뜻입니다.
- **48스텝 이후: 검증 loss가 1.96에서 평탄해집니다.** 1 에폭으로 배울 수 있는 만큼은 거의 다 배웠습니다. 더 오래 학습해도 검증 세트에서는 아마 더 나아지지 않을 것입니다.
- **파란 선의 들쭉날쭉함은 무시하십시오.** 각 점은 한 스텝의 샘플 16개 평균일 뿐이므로, 쉬운 배치나 어려운 배치를 만나면 튑니다. 전체 추세를 보십시오.
- **파란 선이 주황 선보다 약간 낮게 끝나는 것(약 1.5 대 1.96)은 정상입니다.** 검증 세트는 처음 보는 주제이고 답변에는 주제 고유의 내용이 많이 들어 있어서, 말투만 배워서는 그 부분을 낮출 수 없습니다.

**비정상적인 곡선과 비교해 보십시오:** 커널을 재시작하지 않고 학습 셀을 다시 실행하면, 이미 학습된 모델을 이어서 학습하게 되어 에폭을 몇 번 더 돌린 것과 같아집니다. 그러면 학습 loss는 0.5 안팎까지 눌려 내려가는 반면 검증 loss는 2.0에서 2.3까지 다시 올라갑니다. 학습 세트는 점점 좋아지고 검증 세트는 점점 나빠지는 것, 이것이 학습 데이터를 외워 버리는 과적합입니다. 다시 학습하기 전에는 반드시 먼저 **Kernel → Restart Kernel**을 하고, 1번 셀부터 다시 실행하십시오.

9단계는 베이스 모델을 다시 만들고 디스크에서 adapter를 로드하며, 10단계는 학습 전후의 답변을 출력합니다. 1 에폭 뒤에는 보통 답변이 짧아지고 구조가 학습 데이터와 더 비슷해집니다. `answer-review.json`을 열고 질문마다 판단하십시오. 사실이 정확한지, “一句话”(“한 문장으로”)와 “不追问”(“되묻지 않기”) 같은 요구를 지키는지, 중국어가 해당 학년대에 맞는지, 탐구 제안이 구체적이고 안전한지 확인한 다음, 어느 답변이 더 나은지와 그 이유를 적으십시오.

관찰용 질문 3개는 학습 주제에서 나온 것이므로 "어떤 스타일을 배웠는지"만 보여 줍니다. "좋은 프롬프트를 붙인 베이스 모델보다 LoRA가 나은가"에 답하려면 6장의 검증 세트 블라인드 평가를 사용하십시오.

### 4.6 재실행, 소규모 샘플 과적합, 체크포인트 재개

처음부터 다시 학습하려면 커널을 재시작하고, `RUN_DIR`를 `runs/science-002` 같은 새 디렉터리로 바꾼 뒤 셀을 하나씩 다시 실행하십시오. 이전 디렉터리는 그대로 둡니다. 저장 셀은 로그를 확인하는 데 쓸 수 있지만, 학습이 끝난 뒤 `trainer.train()`을 함부로 다시 실행하지 마십시오.

아래 두 연습은 Notebook에 없으며, 명령줄 스크립트를 사용합니다.

**먼저 알아 둘 점: 명령줄 스크립트는 "스냅숏"을 읽습니다.** Notebook은 `dataset.json`을 직접 읽지만, 명령줄 스크립트(이 절, 5.2절, 6장)는 `lab.prepare`가 생성한 읽기 전용 스냅숏을 읽습니다. 데이터베이스에 비유하면 `dataset.json`은 편집 가능한 원본 테이블이고, 스냅숏은 체크섬이 붙은 읽기 전용 내보내기로, 모든 실험 결과를 이것까지 추적할 수 있습니다. 스냅숏에는 데이터, 토크나이저, 프롬프트 코드의 지문이 기록되어 있어서, 그중 하나라도 바뀌면 이후 명령은 몰래 섞어 쓰지 않고 이전 스냅숏 사용을 거부합니다. 스냅숏 디렉터리에는 train/val/test 대화, `facts.jsonl`, `fewshots.json`, `manifest.json`, 토큰화된 샘플이 들어 있으며, 모두 자동 생성되므로 손으로 고치지 마십시오. 출력 디렉터리가 비어 있지 않으면 거부되니, 다른 버전 이름을 고르면 됩니다.

연습 내용은 이렇습니다. **소규모 샘플 과적합**은 샘플 20개로 100스텝을 학습해 학습 파이프라인이 참조 답변을 "외울" 수 있는지 확인하며, "loss가 내려가지 않는다"는 문제를 디버깅할 때 첫 번째로 하는 일입니다. **체크포인트 재개**는 학습이 중단된 뒤 체크포인트(옵티마이저 상태와 진행 상황 포함)에서 이어서 같은 학습 계획을 마치는 방법을 보여 줍니다. GPU 터미널에서 실행하되, 먼저 스냅숏을 생성하고 출력은 각각 별도 디렉터리에 두십시오. CLI의 `--resume`을 Notebook 디렉터리에 바로 쓰지 마십시오. 두 진입점은 설정을 기록하는 방식이 다릅니다.

```bash
# Only needed the first time you use the CLI; skip if it already exists and the data hasn't changed.
.venv-train/bin/python -m lab.prepare --input data/dataset.json --allow-draft --output data/processed/science-v3

# Checks whether a small batch of samples can learn the reference answers; it can't be used to judge generalization.
.venv-train/bin/python -m lab.train --data data/processed/science-v3 \
  --output runs/overfit-20 --allow-draft --limit 20 --max-steps 100

# The same plan: 10 steps in total, stop at step 5 first, then resume the remaining 5.
.venv-train/bin/python -m lab.train --data data/processed/science-v3 \
  --output runs/resume-demo --allow-draft --max-steps 10 --stop-after 5
.venv-train/bin/python -m lab.train --data data/processed/science-v3 \
  --output runs/resume-demo --allow-draft --max-steps 10 --resume runs/resume-demo/checkpoint-5
```

이러한 추가 실험은 필요할 때 실행하십시오. 처음 진행할 때는 학습, 다시 로드, 답변 평가, 배포부터 마치십시오.
## 5. 배포와 API 호출: 모델 내보내기, vLLM 서빙, 부하 테스트

학습으로 얻는 것은 디스크 위의 파일일 뿐입니다. 이 장에서는 그 파일을 어떤 백엔드 코드에서든 호출할 수 있는 HTTP 서비스로 바꾸고, 동시 요청을 얼마나 감당할 수 있는지 측정합니다.

!!! abstract "이 장 한눈에 보기"
    - **이 장에서 하는 일**: 어댑터와 완전한 모델을 구분합니다. vLLM이 VRAM을 어떻게 쓰는지 이해합니다. 병합 모델을 배포합니다. 내 컴퓨터에서 SSH 터널을 통해 호출합니다(단일 턴, 멀티 턴, 스트리밍). "베이스 모델 + 어댑터 마운트" 방식으로 바꿔 배포하고 비교합니다. 부하 테스트를 합니다
    - **준비물**: 4장에서 만든 `runs/science-001/merged-model/`과 `adapter/`, 이미 **Shut down**한 노트북 커널(VRAM 해제용), GPU 호스트에 SSH로 접속할 수 있는 로컬 컴퓨터
    - **결과물**: 실행 중인 OpenAI 호환 서비스, 로컬에서 호출해 받은 답변, 동시성 1/4/16의 지연 시간과 처리량을 채운 표
    - **예상 소요 시간**: vLLM 설치 약 10분, 배포·호출·부하 테스트 약 30~60분

API 요청 하나가 내 컴퓨터를 떠나 답변을 받아 오기까지 다음 단계를 거칩니다.

```text
本地 Python 发出请求
  → 本地 127.0.0.1:18000
  → SSH 隧道
  → GPU 主机 127.0.0.1:8000 上的 vLLM
      ① 用模型目录里的 chat_template 把 messages 拼成一段文本（和训练时相同）
      ② 分词成 Token，进入调度队列，和其他请求拼成同一批
      ③ 模型逐个生成 Token，KV Cache 保存已处理部分，直到 EOS 或 max_tokens
      ④ Token 解码回文字，一次返回 JSON，或按 stream=True 分段推送
  → 原路返回：回答文本 + finish_reason
```

(우리말로 옮기면: 로컬 Python이 요청을 보냄 → 로컬 127.0.0.1:18000 → SSH 터널 → GPU 호스트의 127.0.0.1:8000에 있는 vLLM. vLLM은 ① 모델 디렉터리의 chat_template으로 messages를 하나의 텍스트로 이어 붙이고(학습 때와 같음), ② 토큰화해서 스케줄링 큐에 넣고 다른 요청과 같은 배치로 묶고, ③ 토큰을 하나씩 생성하며 이미 처리한 부분은 KV Cache에 보관하다가 EOS나 max_tokens에 도달하면 멈추고, ④ 토큰을 다시 텍스트로 디코딩해 JSON으로 한 번에 돌려주거나 stream=True이면 조각조각 푸시합니다 → 같은 경로로 되돌아옴: 답변 텍스트 + finish_reason.)

①단계가 호출할 때 학습과 같은 프롬프트 구조를 써야 하는 이유입니다. vLLM은 똑같은 채팅 템플릿을 사용하므로, messages가 같기만 하면 모델은 학습 때와 같은 토큰을 보게 됩니다.

### 5.1 어댑터와 완전한 모델 구분하기

기본 튜토리얼 결과물인 `runs/science-001/adapter/`는 증분(델타)이며, 같은 버전의 `models/qwen3-4b/`가 있어야 동작합니다. 노트북 9~10단계에서는 학습 객체를 해제한 뒤 디스크에서 베이스 모델과 어댑터를 다시 불러와 답변 세 개를 생성합니다. `inference-check.json`과 `answer-review.json`을 확인하세요. 불러오기에 성공했더라도 출력 품질은 여전히 사람이 판단해야 합니다.

11단계에서는 CPU에 새로 **양자화하지 않은 BF16 베이스 모델**을 불러와 LoRA를 병합하고 `runs/science-001/merged-model/`에 저장한 다음, 이 디렉터리를 다시 불러와 답변 하나를 생성합니다. vLLM 배포에는 설정, 토크나이저, 가중치 샤드, 인덱스가 모두 들어 있는 완전한 디렉터리를 사용합니다. 배포하기 전에 4.5절의 답변 비교를 이미 보았는지, 이 모델이 대략 어떻게 답하는지 알고 있는지 확인하세요.

다른 실험의 어댑터를 내보내야 할 때는 터미널에서 [merge.py](../lab/merge.py)를 실행합니다.

```bash
.venv-train/bin/python -m lab.merge --model models/qwen3-4b \
  --adapter runs/science-001/adapter --output runs/science-001/merged-model
```

**노트북에서 이미 병합했다면 이 명령은 건너뛰세요.** 병합 디렉터리는 비어 있어야 하며, 독립된 어댑터와 베이스 모델 버전 잠금은 그대로 유지됩니다.

### 5.2 선택: 병합 전후를 같은 정밀도로 검사하기

이 절에서는 4.6절에서 소개한 명령줄 스냅숏을 사용합니다. 아직 준비하지 않았다면 먼저 4.6절의 매개변수로 `lab.prepare --input runs/science-001/dataset.json`을 실행해 `data/processed/science-v3`를 만드세요. 그래야 이번 학습에 쓴 데이터 사본을 사용하게 됩니다. 디렉터리가 이미 있다면 내용이 일치하는지 확인하고, 원본 데이터를 바꿨다면 다른 출력 디렉터리를 사용하세요.

병합 전 NF4 답변과 병합 후 BF16 답변은 다를 수 있습니다. 병합 과정에서 이상이 생겼는지 확인하려면, 프롬프트와 디코딩 설정을 똑같이 유지한 채 새로 불러온 BF16 베이스 모델 + 어댑터를 BF16 완전한 모델과 비교합니다.

```bash
.venv-train/bin/python -m lab.infer --model models/qwen3-4b --data data/processed/science-v3 \
  --variant C --adapter runs/science-001/adapter --precision bf16 \
  --split train --limit 3 --output runs/science-001/bf16-adapter.jsonl
.venv-train/bin/python -m lab.infer --model runs/science-001/merged-model --data data/processed/science-v3 \
  --variant C --merged --precision bf16 \
  --split train --limit 3 --output runs/science-001/bf16-merged.jsonl
```

이것은 저장/병합에 대한 기본적인 정상 동작 확인일 뿐입니다. 정식 후보라면 검토를 마친 검증 세트와 후보 경로로 바꾸세요. 사실 관계, 지시 준수, 비정상적인 반복이나 잘림이 있는지 살펴보고 차이를 기록하되, 학습 세트에서 답변이 비슷하다는 것을 품질 향상으로 여기지 마세요. 서빙 프레임워크도 수치 차이를 만들 수 있으므로, 서비스를 공개하기 전에 같은 고정 사례로 다시 확인하세요.

### 5.3 vLLM이 GPU에서 하는 일

vLLM은 **VRAM에 상주하는 애플리케이션 서버**라고 생각하면 됩니다. 시작할 때 모델 가중치를 GPU에 올리고, OpenAI와 같은 형식의 HTTP 엔드포인트(`/v1/chat/completions`, `/v1/models`)를 제공합니다. 그래서 OpenAI API를 호출하는 백엔드 코드라면 `base_url`만 바꿔서 여러분의 모델을 호출할 수 있습니다.

노트북의 `model.generate()`보다 훨씬 빠른 이유는 주로 두 가지입니다.

| 메커니즘 | 비유 | 효과 |
|---|---|---|
| 연속 배칭(continuous batching) | 공유 스레드 풀처럼, 요청이 도착하는 대로 같은 처리 배치에 합류 | 여러 요청을 동시에 생성해 GPU가 놀지 않습니다. 요청 하나가 끝나면 즉시 다음 요청이 들어옵니다 |
| PagedAttention으로 KV Cache 관리 | 요청마다 최대 공간을 미리 잡아 두지 않고, 운영체제처럼 페이지 단위로 메모리를 할당 | 요청이 실제로 쓰는 토큰만큼만 VRAM을 차지하므로 동시에 더 많은 요청을 담을 수 있습니다 |

**KV Cache**는 생성 중에 이미 처리한 각 토큰에 대해 저장해 두는 어텐션 중간 결과입니다. 덕분에 새 글자를 하나 생성할 때마다 앞의 텍스트를 전부 다시 계산하지 않아도 됩니다. "컨텍스트 길이 × 동시에 처리하는 요청 수"에 비례해 커지며, 추론 시 VRAM에서 가중치 다음으로 큰 비중을 차지합니다.

#### 먼저 VRAM을 직접 계산한 다음 로그와 비교하기

Qwen3-4B의 구조 매개변수는 `models/qwen3-4b/config.json`에 있습니다. 36개 층, 8개 KV 헤드, 헤드당 128차원입니다. BF16은 숫자 하나에 2바이트를 쓰므로 다음과 같습니다.

```text
每个 Token 的 KV Cache = 2（K 和 V）× 36 层 × 8 头 × 128 维 × 2 字节
                       = 147,456 字节 ≈ 144 KiB
一条 4096 Token 的满长请求 ≈ 4096 × 144 KiB ≈ 576 MiB
```

(즉, 토큰당 KV Cache = 2(K와 V) × 36층 × 8헤드 × 128차원 × 2바이트 = 147,456바이트 ≈ 144 KiB이고, 4096토큰짜리 최대 길이 요청 하나 ≈ 4096 × 144 KiB ≈ 576 MiB입니다.)

| VRAM 예산(`--gpu-memory-utilization 0.85`) | 추정치 |
|---|---|
| vLLM이 쓸 수 있는 총량: 24 GB × 0.85 | ≈ 20.4 GiB |
| BF16 가중치: 약 40억 개 매개변수 × 2바이트 | ≈ 7.5 GiB |
| 활성화, CUDA Graph 등 런타임 오버헤드 | ≈ 1~2 GiB |
| 나머지는 모두 KV Cache로 | ≈ 11 GiB ≈ 7만~8만 토큰 ≈ 최대 길이 요청 18~20개 |

시작 로그의 `GPU KV cache size: ... tokens`와 `Maximum concurrency for 4096 tokens per request: ...x` 줄이 vLLM이 실제로 계산한 결과입니다. 이 값을 적어 두고 위 표와 비교해 보세요. 차이가 크다면 대개 다른 프로세스(예: 깜빡하고 종료하지 않은 학습 커널)가 VRAM을 차지하고 있는 것입니다.

여기 나온 `--gpu-memory-utilization`, `--max-model-len`, `--max-num-seqs` 같은 시작 매개변수는 5.4절의 실행 명령 아래에서 하나씩 설명합니다.

### 5.4 병합한 완전한 모델 배포하기

다음 명령은 Python 셀이 아니라 **GPU 호스트의 터미널**에서 실행합니다. 먼저 Jupyter 메뉴의 **Shutdown Kernel**로 학습에 쓰던 VRAM을 해제한 다음 프로젝트 디렉터리로 이동하세요. 별도의 `.venv-serve`를 두면 vLLM이 학습 의존성을 덮어쓰지 않습니다.

```bash
cd /root/llm-lora-tutorial  # if the project is on a data disk, use the actual path instead
nvidia-smi
python3.11 -m venv .venv-serve
.venv-serve/bin/python -m pip install --upgrade pip
.venv-serve/bin/python -m pip install 'vllm==0.21.0' --extra-index-url https://download.pytorch.org/whl/cu129
.venv-serve/bin/python -m pip check
```

이 vLLM 버전은 기본적으로 CUDA 12.9로 빌드되어 있습니다. `nvidia-smi` 오른쪽 위에 표시되는 CUDA Version은 드라이버가 지원하는 최고 버전이며, 12.9보다 낮다면 먼저 플랫폼에서 드라이버를 업그레이드하거나 다른 이미지로 바꾸세요. 이미지 이름에 들어 있는 CUDA 12.6은 드라이버의 상한이 아닙니다. 출처: [vLLM 0.21 GPU 설치](https://docs.vllm.ai/en/v0.21.0/getting_started/installation/gpu/).

**`download.pytorch.org`에 접속할 수 없을 때:** vLLM 0.21은 `torch==2.11.0`, `torchaudio==2.11.0`, `torchvision==0.26.0`에 의존하며, 위 명령은 이들의 CUDA 12.9 빌드를 PyTorch 공식 인덱스에서 받아 옵니다. 중국 본토의 호스트에서 접속할 수 없다면 Alibaba Cloud PyTorch 미러에서 같은 패키지를 받으세요.

```bash
.venv-serve/bin/python -m pip install 'vllm==0.21.0' -f https://mirrors.aliyun.com/pytorch-wheels/cu129/
.venv-serve/bin/python -m pip check
```

설치한 뒤 `.venv-serve/bin/python -c "import torch; print(torch.__version__, torch.version.cuda)"`로 확인합니다. `2.11.0+cu129 12.9`가 출력되어야 합니다.

```bash
HF_HUB_OFFLINE=1 .venv-serve/bin/vllm serve "$PWD/runs/science-001/merged-model" \
  --served-model-name science-explorer-lora \
  --host 127.0.0.1 --port 8000 \
  --dtype bfloat16 --max-model-len 4096 \
  --gpu-memory-utilization 0.85 --max-num-seqs 4 \
  --generation-config vllm
```

#### 이 실행 명령을 한 부분씩 읽어 보기

웹 서비스를 띄워 본 적이 있다면 이 명령이 낯설지 않을 것입니다. uvicorn으로 Python 웹 앱을 실행하는 것과 같은 종류의 일입니다.

```text
uvicorn app:app       --host 127.0.0.1 --port 8000 --workers 4
vllm serve <模型目录>  --host 127.0.0.1 --port 8000 --max-num-seqs 4 ……
```

(`<模型目录>`은 `<모델 디렉터리>`라는 뜻입니다.)

차이는 vLLM이 "배포"하는 대상이 비즈니스 코드가 아니라 모델 디렉터리라는 점뿐입니다. 그래서 모델과 VRAM에 관한 매개변수가 몇 개 더 붙습니다. 먼저 명령에 나오는 세 가지 셸 표현을 알아 둡시다.

| 표기 | 의미 |
|---|---|
| 줄 맨 앞의 `HF_HUB_OFFLINE=1` | 이 명령 하나에만 적용되는 환경 변수입니다. `export`한 뒤 명령을 실행하는 것과 같지만, 터미널에서 이후에 실행하는 명령에는 영향을 주지 않습니다 |
| `$PWD` | 현재 디렉터리의 절대 경로입니다. 그래서 실행하기 전에 반드시 프로젝트 디렉터리로 `cd`해야 합니다 |
| 줄 끝의 `\` | 줄 이어 쓰기입니다. 다음 줄도 같은 명령이라고 셸에 알려 줍니다. `\` 뒤에 공백이 있으면 안 됩니다 |

아래에서는 "누가 실행하는가 → 무엇을 불러오는가 → 외부에 어떤 이름으로 보이는가 → 어디서 수신하는가 → 정밀도와 길이 → VRAM과 동시성 → 기본 생성 매개변수" 순서로 매개변수를 하나씩 설명합니다.

| 매개변수 | 이 튜토리얼의 값 | 의미 | 이 값을 쓰는 이유 / 바꾸면 어떻게 되는가 |
|---|---|---|---|
| `HF_HUB_OFFLINE=1` | — | 로컬 파일만 읽고 Hugging Face 웹사이트에 접속하지 않습니다 | 모델은 이미 로컬에 있습니다. 중국 본토의 호스트는 huggingface.co에 접속하다 멈추는 일이 잦아, 이 설정이 없으면 시작 단계에서 멈출 수 있습니다 |
| `.venv-serve/bin/vllm serve` | — | 추론 전용 환경의 vLLM으로 HTTP 서비스를 시작합니다 | `.venv-train`이 아니라 `.venv-serve`를 씁니다. 두 환경은 torch 버전이 달라서 섞어 쓰면 서로를 덮어씁니다 |
| 첫 번째 인자: 모델 디렉터리 | `runs/.../merged-model` | 불러올 모델입니다. `from_pretrained`와 마찬가지로 **디렉터리**를 넘기며, vLLM이 그 안의 `config.json`, 토크나이저, 가중치 샤드를 알아서 읽습니다 | `models/qwen3-4b`로 바꾸면 원본 모델을 배포합니다. 5.6절에서는 원본 모델을 불러온 뒤 어댑터를 마운트하는 다른 방식을 보여 줍니다 |
| `--served-model-name` | `science-explorer-lora` | 외부에 공개하는 모델 이름입니다. 클라이언트 요청의 `"model"` 필드에 이 이름을 넣어야 하며, `/v1/models`에도 이 이름이 나옵니다 | 단순한 별칭일 뿐 어떤 가중치를 불러오는지와는 관계없습니다. 서비스의 공개 도메인 이름이 서버의 디렉터리 이름과 무관한 것과 같습니다. 요청에 이름을 잘못 넣으면 404가 반환됩니다 |
| `--host` | `127.0.0.1` | 수신할 네트워크 인터페이스 주소입니다. `127.0.0.1`은 이 머신에서 오는 연결만 받는다는 뜻입니다 | 공용 인터넷에 노출되지 않으며, 외부에서는 5.5절의 SSH 터널로만 접근합니다. `0.0.0.0`으로 바꾸면 모든 인터페이스에 열리므로 반드시 인증을 추가해야 합니다(5.8절) |
| `--port` | `8000` | 수신할 포트입니다 | 포트가 이미 사용 중이면 8001 같은 다른 포트를 고르고, 뒤에 나오는 `curl` 명령과 SSH 터널도 함께 바꾸세요 |
| `--dtype` | `bfloat16` | 가중치와 계산에 쓰는 수치 정밀도입니다 | 4장에서 병합할 때 저장한 정밀도와 같습니다. 서빙할 때는 양자화하지 않으므로 가중치가 VRAM을 학습 때의 2.5 GiB가 아니라 약 7.5 GiB 차지합니다 |
| `--max-model-len` | `4096` | 요청 하나의 최대 토큰 수로, **입력과 출력을 합친 값**입니다 | 학습 때의 상한과 같습니다. 이보다 긴 요청은 곧바로 HTTP 400을 받습니다. 늘리면 더 긴 대화를 받을 수 있지만, 최대 길이 요청 하나가 차지하는 KV Cache가 커져서 동시에 담을 수 있는 요청 수가 줄어듭니다 |
| `--gpu-memory-utilization` | `0.85` | vLLM이 시작할 때 가중치와 KV Cache용으로 카드 전체 VRAM 중 얼마만큼을 **한 번에 예약**할지 정하는 비율입니다 | 그래서 시작 직후 요청이 하나도 없는데도 `nvidia-smi`에 약 85%가 사용 중으로 나옵니다. 이것은 사전 할당이지 누수가 아닙니다. 값을 올리면 KV Cache를 더 담을 수 있고, 남겨 둔 15%는 CUDA 컨텍스트와 다른 프로세스용입니다. VRAM이 부족해 시작에 실패하면 먼저 이 값을 낮추세요 |
| `--max-num-seqs` | `4` | 어느 순간이든 함께 생성 중일 수 있는 최대 요청 수입니다 | 웹 서비스의 워커 수나 커넥션 풀 크기와 비슷합니다. 넘치는 요청은 대기열에서 기다립니다. 값을 올리면 전체 처리량은 늘지만 요청 하나하나는 느려집니다. 5.7절의 부하 테스트에서 4와 16을 실제로 비교합니다 |
| `--generation-config` | `vllm` | 요청에 지정하지 않은 생성 매개변수(`temperature` 등)에 모델 디렉터리의 `generation_config.json` 값 대신 vLLM 자체 기본값을 씁니다 | 그 파일에는 Qwen의 기본 랜덤 샘플링 설정(`temperature 0.7` 등)이 들어 있습니다. 이 튜토리얼은 모든 요청에 `temperature=0`을 명시적으로 넘기며, 이 매개변수는 모델 디렉터리의 기본값이 몰래 영향을 주지 못하게 보장합니다 |

**VRAM 관련 매개변수 세 개가 함께 동작하는 방식:** `--gpu-memory-utilization`은 vLLM이 쓸 수 있는 VRAM 총량을 정합니다(24 GB × 0.85 ≈ 20 GiB). 여기서 가중치와 런타임 오버헤드를 빼고 남은 약 11 GiB는 모두 KV Cache가 됩니다. `--max-model-len`은 요청 하나가 차지할 수 있는 KV Cache의 최대치(4096토큰 ≈ 576 MiB)를, `--max-num-seqs`는 동시에 실행할 수 있는 최대 요청 수를 정합니다. 시작 로그의 `Maximum concurrency`는 "전체 KV Cache에 최대 길이 요청을 몇 개 담을 수 있는가"이며, 전체 추정 과정은 5.3절에 있습니다.

**이 명령에서 생략되어 기본값을 쓰는 것:** GPU는 1장만 사용합니다(`--tensor-parallel-size 1`). API 키는 검사하지 않습니다(`--api-key`, 5.8절). 엔드포인트는 OpenAI 호환 `/v1/chat/completions` 등입니다. 전체 매개변수는 `.venv-serve/bin/vllm serve --help`로 볼 수 있습니다.

경로의 `science-001`은 방금 학습한 실험 이름으로 바꾸세요. `science-explorer-lora`는 API 요청에 쓰는 모델 이름이고, 실제로 불러오는 가중치는 `merged-model/`에서 옵니다. 시작 로그에서 `GPU KV cache size`와 `Maximum concurrency` 두 줄을 찾으세요. 튜토리얼 5.3절에서 이 값으로 VRAM 추정치를 확인합니다. `Application startup complete`가 나타나면 GPU 호스트의 다른 터미널에서 확인합니다.

```bash
curl --fail http://127.0.0.1:8000/health
curl --fail http://127.0.0.1:8000/v1/models
nvidia-smi --query-gpu=memory.used,memory.total,utilization.gpu --format=csv
```

성공하면 `/health`는 본문 없이 200을 반환하고, `/v1/models`는 다음과 비슷한 결과를 반환합니다.

```json

```

요청이 없어도 VRAM은 이미 약 85%가 사용 중입니다. vLLM은 시작할 때 `--gpu-memory-utilization`에 따라 가중치와 KV Cache를 한 번에 예약하기 때문입니다. 이것은 사전 할당이지 누수가 아닙니다. 서비스 프로세스는 계속 실행해 두세요.

`HF_HUB_OFFLINE=1`은 vLLM이 로컬 디렉터리만 읽고 오프라인으로 동작하게 하므로, 중국 본토의 호스트에서 huggingface.co에 접속하려다 멈추는 일이 없습니다. 시작에 실패하면 다음 순서로 확인하세요. 학습 커널을 종료했는지(`nvidia-smi`에 다른 Python 프로세스가 있는지), 드라이버의 CUDA 버전, 모델 디렉터리가 완전한지(`config.json`, 토크나이저, 모든 `*.safetensors`가 있는지). VRAM이 부족하면 먼저 `--max-model-len`이나 `--gpu-memory-utilization`을 낮추세요. 모델 경로를 원본 모델로 되돌려서 서비스를 "고치지" 마세요.

### 5.5 로컬 컴퓨터에서 호출하기: 단일 턴 질문 세 개와 멀티 턴 질문 하나

먼저 **로컬 컴퓨터의 터미널**에서 SSH 터널을 엽니다. 자리 표시자(`<平台SSH端口>` = 플랫폼의 SSH 포트, `<平台SSH地址>` = 플랫폼의 SSH 주소)를 클라우드 플랫폼이 알려 준 실제 값으로 바꾸고, 이 터미널은 열어 두세요. 이 단계는 서비스를 호출하기 위한 것이지 파일 업로드용이 아닙니다.

```bash
ssh -p <平台SSH端口> -N -L 18000:127.0.0.1:8000 root@<平台SSH地址>
```

터널은 로컬 `127.0.0.1:18000`을 GPU 호스트의 `127.0.0.1:8000`으로 전달합니다. 서비스는 GPU 호스트의 루프백 주소에서만 수신하고 공용 인터넷에 노출되지 않습니다. 이것이 가장 간단한 형태의 접근 제어입니다. 로컬의 다른 터미널에서 `curl --fail http://127.0.0.1:18000/v1/models`를 실행해 보세요. 플랫폼이 웹 Jupyter만 제공하고 SSH 포워딩을 지원하지 않는다면, 먼저 플랫폼에서 포워딩을 활성화하거나 인증이 붙은 포트 프록시를 사용하세요. Jupyter 파일 브라우저의 URL은 모델 API 주소가 아닙니다.

#### 먼저 curl로 직접 호출하기

다음 명령은 모두 **로컬 컴퓨터의 다른 터미널**에서 실행하고, 터널 터미널은 열어 둡니다. 로컬에는 `curl`만 있으면 됩니다. macOS와 Linux에는 기본으로 들어 있고, Windows에서는 Git Bash나 WSL을 사용하세요. PowerShell은 따옴표 규칙이 달라서 그대로 붙여 넣으면 실패합니다.

##### 1. 서비스에 접근할 수 있는지 확인하기

```bash
curl --fail http://127.0.0.1:18000/health
curl --fail http://127.0.0.1:18000/v1/models
```

성공하면 `/health`는 아무것도 출력하지 않고 오류도 내지 않습니다. `/v1/models`가 반환하는 JSON에는 실행 명령의 `--served-model-name` 값인 `"id": "science-explorer-lora"`가 들어 있어야 합니다. 연결되지 않으면 먼저 터널 터미널이 아직 열려 있는지 확인하세요.

##### 2. 가장 간단한 대화

```bash
curl http://127.0.0.1:18000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model": "science-explorer-lora", "messages": [{"role": "user", "content": "为什么白天亮、晚上黑？"}], "temperature": 0, "max_tokens": 256}'
```

(질문 “为什么白天亮、晚上黑？”는 “왜 낮에는 밝고 밤에는 어두워요?”라는 뜻입니다.)

이것이 OpenAI 호환 엔드포인트의 최소 요청입니다. `POST /v1/chat/completions`에 모델 이름, 메시지 목록, 생성 매개변수를 요청 본문으로 보냅니다. `temperature: 0`은 매번 확률이 가장 높은 토큰을 고른다는 뜻이므로 같은 요청에는 같은 답변이 나옵니다. `max_tokens`는 이번 호출에서 생성할 수 있는 최대 토큰 수입니다. 반환되는 JSON은 대략 다음과 같습니다.

```json
{"id": "chatcmpl-...", "object": "chat.completion", "model": "science-explorer-lora",
 "choices": [{"index": 0, "message": {"role": "assistant", "content": "……"}, "finish_reason": "stop"}],
 "usage": {"prompt_tokens": 15, "completion_tokens": ..., "total_tokens": ...}}
```

답변은 `choices[0].message.content`에 있습니다. `finish_reason`이 `stop`이면 모델이 스스로 종료 표시를 출력한 것이고, `length`이면 `max_tokens`에 도달해 잘린 것입니다. `usage`는 입력과 출력의 토큰 수로, 토큰 단위 과금이나 속도 제한을 할 때 참고하는 값입니다.

참고: 이 요청에는 user 메시지 하나만 있고 **학습 때의 역할 프롬프트, 학년대, 팩트 카드가 들어 있지 않으므로** 답변 스타일이 학습 데이터와 다를 수 있습니다. API 형식을 익히는 용도로만 쓰세요.

##### 5. 스트리밍 출력

```bash
curl -N http://127.0.0.1:18000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model": "science-explorer-lora", "messages": [{"role": "user", "content": "为什么白天亮、晚上黑？"}], "temperature": 0, "max_tokens": 256, "stream": true}'
```

`"stream": true`를 붙이면 서비스는 작은 조각이 생성될 때마다 바로 푸시합니다. `curl -N`은 curl이 받은 내용을 버퍼링하지 않고 즉시 출력하게 합니다. 출력은 Server-Sent Events 형식이며, 각 줄은 `data:`로 시작하고 마지막 줄은 `data: [DONE]`입니다.

```text
data: {"id":"chatcmpl-...","object":"chat.completion.chunk",...,"choices":[{"index":0,"delta":{"content":"地球"},...}]}
data: {"id":"chatcmpl-...","object":"chat.completion.chunk",...,"choices":[{"index":0,"delta":{"content":"在"},...}]}
...
data: [DONE]
```

각 줄의 `delta.content`가 새로 생성된 작은 조각입니다. 프런트엔드에서 이를 순서대로 이어 붙이면 "생성하면서 바로 보여 주는" 효과를 낼 수 있습니다.

#### Python으로 일괄 호출하기

다음 Python 예제는 **로컬 컴퓨터의 프로젝트 루트**에서 실행합니다. Python 표준 라이브러리와 이 저장소의 코드만 있으면 됩니다. 학습 때의 `build_messages`를 재사용하므로, 서비스에 보내는 system 프롬프트, 학년대, 팩트 카드 형식이 학습 샘플과 정확히 같습니다. 로컬 GPU도 OpenAI 계정도 필요 없습니다.

```python
import json
from urllib.request import Request, urlopen

from lab.common import build_messages
from lab.data import read_dataset

url = "http://127.0.0.1:18000/v1/chat/completions"
MODEL = "science-explorer-lora"
_, facts = read_dataset("data/dataset.json")


def ask(messages):
    body = {"model": MODEL, "messages": messages, "temperature": 0, "max_tokens": 256}
    request = Request(url, data=json.dumps(body).encode(),
                      headers={"Content-Type": "application/json"})
    with urlopen(request, timeout=120) as response:
        choice = json.load(response)["choices"][0]
    print("finish_reason:", choice["finish_reason"])
    return choice["message"]["content"]


def messages_for(fact_id, grade, user, history=()):
    # Same as training: role prompt + grade band + fact cards + history + current question.
    case = {"fact_ids": [fact_id], "grade_band": grade, "history": list(history), "user": user}
    return build_messages(facts, case)


questions = [
    ("day-night", "1-2", "晚上是太阳关灯了吗？先用一句话回答，不要反问。"),
    ("buoyancy", "3-4", "为什么小铁块沉，大铁船却浮着？我猜是大东西更容易浮。"),
    ("moon-phase", "5-6", "月亮变弯是被地球影子挡住了吗？我想安全地观察一下。"),
]
for fact_id, grade, question in questions:
    print("问题:", question)
    print("回答:", ask(messages_for(fact_id, grade, question)), "\n")

# Multi-turn: the service does not remember the previous turn, so you must pass the actually generated answer back as history.
first_question = "轮船那么重，为什么不会沉？"
first = ask(messages_for("buoyancy", "3-4", first_question))
history = [{"role": "user", "content": first_question},
           {"role": "assistant", "content": first}]
print("多轮回答:", ask(messages_for("buoyancy", "3-4", "我还是不懂排开水，换个简单说法，先别考我。", history)))
```

(스크립트가 출력하는 레이블 问题 / 回答 / 多轮回答은 "질문" / "답변" / "멀티 턴 답변"이라는 뜻입니다. 질문은 “为什么小铁块沉，大铁船却浮着？我猜是大东西更容易浮。”(“작은 쇳조각은 가라앉는데 커다란 쇠배는 왜 떠 있어요? 큰 물건이 더 잘 뜨는 것 같아요.”), “月亮变弯是被地球影子挡住了吗？我想安全地观察一下。”(“달이 휘어 보이는 건 지구 그림자에 가려서예요? 안전하게 관찰해 보고 싶어요.”), “轮船那么重，为什么不会沉？”(“배는 그렇게 무거운데 왜 안 가라앉아요?”), 그리고 이어지는 질문 “我还是不懂排开水，换个简单说法，先别考我。”(“물을 밀어낸다는 게 아직도 이해가 안 돼요. 더 쉽게 말해 주고, 아직 문제는 내지 마세요.”)입니다.)

질문마다 먼저 `finish_reason: stop`을 출력한 다음 답변을 출력합니다. 예를 들면 다음과 같습니다.

```text
问题: 晚上是太阳关灯了吗？先用一句话回答，不要反问。
finish_reason: stop
回答: 太阳没有关灯。是我们住的地面转到了背向太阳的一侧。
```

(답변의 뜻: “해는 불을 끄지 않았어요. 우리가 사는 땅이 해를 등지는 쪽으로 돌아간 거예요.”)

`stop`은 모델이 스스로 EOS를 출력해 정상적으로 끝났다는 뜻이고, `length`는 출력이 `max_tokens`에 도달해 잘렸다는 뜻이므로 완전한 답변으로 볼 수 없습니다. 첫 요청은 1~2초 더 느리고(vLLM 워밍업), 그 뒤로는 질문 하나가 보통 1초 안에 돌아옵니다.

다음 순서로 확인하세요. 틀린 추측을 바로잡는가, 아이가 이해할 수 있는 설명으로 바꿔 말할 수 있는가, 제안하는 관찰이 안전하고 구체적인가, "문제 내지 말라"는 요청을 존중하는가.

프롬프트는 학습 때와 같아야 합니다. 모델은 "역할 프롬프트 + 학년대 + 팩트 카드" 형태의 입력에서 답하는 방식을 배웠으므로, 많이 다른 프롬프트로 바꾸면 결과가 눈에 띄게 나빠질 수 있습니다. 팩트 카드를 넘겨주는 것은 호출하는 쪽의 책임입니다. 파인튜닝은 모델에 새로운 지식이나 실시간 정보를 주지 않습니다.

#### OpenAI SDK와 스트리밍 출력 사용하기

백엔드 프로젝트에서는 공식 OpenAI SDK를 직접 쓰는 경우가 더 많습니다. 로컬에서 `python3 -m pip install openai`로 설치하고 `base_url`만 터널 주소로 지정하면 됩니다. vLLM은 기본적으로 키를 검사하지 않으므로 `api_key`에는 비어 있지 않은 아무 문자열이나 넣으면 됩니다.

```python
from openai import OpenAI

from lab.common import build_messages
from lab.data import read_dataset

client = OpenAI(base_url="http://127.0.0.1:18000/v1", api_key="EMPTY")
_, facts = read_dataset("data/dataset.json")
messages = build_messages(facts, {"fact_ids": ["seasons"], "grade_band": "3-4", "history": [],
                                  "user": "为什么夏天热、冬天冷？"})

# stream=True: the service pushes each small piece as it is generated, so the frontend can display while generating.
stream = client.chat.completions.create(model="science-explorer-lora", messages=messages,
                                        temperature=0, max_tokens=256, stream=True)
for chunk in stream:
    if chunk.choices and chunk.choices[0].delta.content:
        print(chunk.choices[0].delta.content, end="", flush=True)
print()
```

(질문 “为什么夏天热、冬天冷？”은 “왜 여름은 덥고 겨울은 추워요?”라는 뜻입니다.)

스트리밍 출력은 Server-Sent Events를 사용합니다. 하나의 HTTP 응답 안에서 여러 JSON 조각을 연달아 푸시하는 방식입니다. 사용자가 체감하는 대기 시간은 답변 전체가 끝나는 데 걸리는 시간보다 주로 "첫 토큰이 나오기까지 얼마나 걸리는가"(TTFT)입니다. 5.7절에서 이 지표를 측정합니다.

### 5.6 병합하지 않고: 어댑터를 직접 마운트해 같은 서비스에서 베이스 모델과 비교하기

병합만이 배포 방법은 아닙니다. vLLM은 **원본 베이스 모델**을 불러온 다음 LoRA 어댑터를 추가 "모델 이름"으로 마운트할 수 있습니다. 같은 서비스 안에서 `qwen3-4b-base`로 보낸 요청은 베이스 모델로, `science-lora`로 보낸 요청은 베이스 모델 + LoRA로 처리됩니다. 먼저 `Ctrl+C`를 눌러 5.4절의 서비스를 멈춘 다음(포트와 VRAM을 두 서비스에 동시에 줄 수 없습니다) 다음 명령으로 시작합니다.

```bash
HF_HUB_OFFLINE=1 .venv-serve/bin/vllm serve "$PWD/models/qwen3-4b" \
  --served-model-name qwen3-4b-base \
  --enable-lora --lora-modules science-lora="$PWD/runs/science-001/adapter" \
  --max-lora-rank 16 \
  --host 127.0.0.1 --port 8000 \
  --dtype bfloat16 --max-model-len 4096 \
  --gpu-memory-utilization 0.85 --max-num-seqs 4 \
  --generation-config vllm
```

이제 `/v1/models`에 이름 두 개가 나옵니다. 5.5절 예제의 `MODEL`을 `qwen3-4b-base`, 그다음 `science-lora`로 바꿔 각각 한 번씩 실행하면, 같은 프롬프트에서 "파인튜닝 전과 후"를 비교할 수 있습니다. `--max-lora-rank`는 학습에 쓴 rank(이 튜토리얼에서는 16)보다 작으면 안 됩니다.

| | 병합 배포(5.4) | 어댑터 마운트(5.6) |
|---|---|---|
| 디스크 | 버전마다 약 8 GB의 완전한 모델 | 베이스 모델 하나 + 버전마다 약 130 MB의 어댑터 |
| 추론 속도 | 베이스 모델과 같음 | 층마다 작은 행렬 계산이 한 번 더 들어가서 보통 조금 느림 |
| 여러 파인튜닝 버전 | 버전마다 서비스 하나와 VRAM 한 벌 | 서비스 하나가 여러 어댑터를 동시에 마운트하고 베이스 모델의 VRAM을 공유 |
| 모델 업데이트 | 다시 병합하고 재시작 | 어댑터 디렉터리를 바꾸고 서비스를 재시작 |
| 적합한 경우 | 버전이 하나뿐이고 지연 시간을 최소화하고 싶을 때 | A/B 비교, 멀티 테넌트, 여러 버전의 점진적 배포 |

### 5.7 부하 테스트: 동시성, 지연 시간, 처리량

서비스를 공개하기 전에 "4090 한 장으로 요청을 얼마나 처리할 수 있는가"를 알아야 합니다. vLLM에는 부하 테스트 도구가 들어 있습니다. GPU 호스트의 **다른 터미널**에서 실행하세요(서비스는 계속 실행해 두고, 이 예에서는 5.4절의 병합 모델 서비스를 사용합니다).

```bash
.venv-serve/bin/vllm bench serve --backend openai-chat \
  --base-url http://127.0.0.1:8000 --endpoint /v1/chat/completions \
  --model science-explorer-lora --tokenizer "$PWD/runs/science-001/merged-model" \
  --dataset-name random --random-input-len 512 --random-output-len 128 \
  --num-prompts 64 --max-concurrency 1
```

`random` 데이터셋은 지정한 길이의 무작위 입력을 생성합니다. 성능 측정 전용이며 답변 내용은 보지 않습니다. 매개변수 이름은 여러분 머신의 `vllm bench serve --help`를 기준으로 하세요. `--max-concurrency`를 1, 4, 16으로 차례로 바꿔 한 번씩 실행하고 표를 채우세요.

| 클라이언트 동시성 | Request throughput (req/s) | Output token throughput (tok/s) | Mean TTFT (ms) | Mean TPOT (ms) |
|---:|---:|---:|---:|---:|
| 1 | | | | |
| 4 | | | | |
| 16 | | | | |

| 지표 | 의미 | 비유 |
|---|---|---|
| TTFT(Time To First Token) | 요청을 보낸 시점부터 첫 토큰을 받을 때까지 | 첫 바이트까지의 시간 |
| TPOT(Time Per Output Token) | 그 뒤 토큰 사이의 평균 간격 | 스트리밍 응답의 푸시 간격 |
| Output token throughput | 초당 생성하는 전체 토큰 수 | 토큰 단위의 QPS |

다음과 같은 결과를 보게 될 것입니다. 동시성을 1에서 4로 올리면 전체 처리량은 뚜렷하게 늘고 요청당 TPOT는 조금만 느려집니다. 이것이 연속 배칭의 효과입니다. 동시성 16에서는 서버 쪽 `--max-num-seqs 4`가 동시에 생성하는 요청 수를 제한하므로 넘치는 요청이 대기열에 쌓이고 TTFT가 눈에 띄게 길어집니다. 서비스를 멈추고 `--max-num-seqs`를 16으로 바꿔 다시 시작한 뒤 동시성 16을 다시 실행해 처리량과 TTFT를 비교해 보세요. 이것이 "처리량"과 "요청당 지연 시간" 사이의 트레이드오프입니다.

### 5.8 서비스 공개 전에 아직 부족한 것

이 튜토리얼의 서비스는 `127.0.0.1`에서만 수신하고 SSH 터널로 접근하므로 연습용으로는 충분합니다. 다른 사람이 쓰게 하려면 최소한 다음이 필요합니다.

| 영역 | 해야 할 일 |
|---|---|
| 인증 | 시작할 때 `--api-key <密钥>`(`<密钥>` = 여러분의 키)를 추가하고, 클라이언트가 `Authorization: Bearer <密钥>`에 담아 보내게 합니다. 또는 이미 인증이 있는 게이트웨이 뒤에 둡니다. 인증 없이 `0.0.0.0`에서 수신하는 일은 절대 없어야 합니다 |
| 모니터링 | vLLM은 같은 포트에서 Prometheus 형식의 `/metrics`(`curl http://127.0.0.1:8000/metrics`)를 제공하며, 대기 중인 요청 수, KV Cache 사용률, 토큰 처리량 등을 담고 있어 기존 모니터링에 연결할 수 있습니다 |
| 프로세스 관리 | systemd, Docker 또는 플랫폼의 서비스 기능으로 호스팅해 크래시 시 자동으로 재시작되게 합니다. 모델을 불러오는 데 수십 초가 걸리며, 헬스 체크에는 `/health`를 사용합니다 |
| 클라이언트 | 타임아웃을 설정합니다. 연결 실패와 5xx에 대해서만 제한된 횟수로 재시도합니다. HTTP 400은 대개 입력이 `--max-model-len`을 넘었다는 뜻이므로 재시도해도 소용없습니다 |
| 비용 | 서비스가 놀고 있어도 VRAM은 계속 점유되므로, 종량제 인스턴스는 쓰지 않을 때 중지하세요 |
## 6. 평가: 파인튜닝은 정말 프롬프트보다 나은가

이 장은 아주 실용적인 엔지니어링 질문에 답합니다. GPU 시간을 들여 파인튜닝하는 것이 좋은 프롬프트를 작성하는 것보다 얼마나 나을까요? 이 **탐색적 비교**는 초안 데이터로 바로 실행해 실험 방법을 연습할 수 있습니다. 다만 결론을 다른 사람에게 보고하기 전에는 먼저 데이터 검토를 마쳐야 합니다.

!!! abstract "이 장 한눈에 보기"
    - **하는 일**: 세 그룹의 모델(기본 모델 + 간단한 프롬프트, 기본 모델 + 좋은 프롬프트와 예시, LoRA)이 같은 검증 문제에 답하게 합니다. 두 가지 rank를 비교하고, 블라인드 평가로 점수를 매기며, 후보를 정한 뒤에야 테스트셋을 사용합니다
    - **준비물**: 3장의 `.venv-train`과 기본 모델, 몇 시간 동안 연속으로 쓸 수 있는 GPU, 평가자 최소 1명(가능하면 모델을 학습시킨 사람이 아닌 사람)
    - **얻는 것**: 원본 출력, 점수, 불확실성 구간을 담아 "파인튜닝할 가치가 있는가?"에 답할 수 있는 실험 기록
    - **언제 하나**: 4~5장의 메인 경로가 처음부터 끝까지 동작한 뒤입니다. 이 장은 GPU 시간이 대략 10~20시간(여러 번의 추론과 두 번의 학습 포함) 걸리며, 사람이 점수를 매기는 시간은 별도입니다

왜 loss만 보면 안 될까요? loss는 "참조 답변과 얼마나 비슷한가"만 측정합니다. 참조 답변 자체가 장황하거나 실수와 누락을 포함할 수 있고, 좋은 프롬프트를 받은 기본 모델이 이미 충분히 잘 말할 수도 있습니다. 파인튜닝이 가치를 더하는지 판단하려면 **학습에 한 번도 쓰지 않은 주제**를 가져와 "좋은 프롬프트"와 "좋은 프롬프트 + LoRA"가 **완전히 같은 입력**에 답하게 하고, 어느 쪽인지 모르는 상태에서 사람이 점수를 매겨야 합니다. 백엔드에서 A/B 실험을 하는 것과 같습니다. 변수를 통제하고, 블라인드로 테스트하고, 신뢰 구간을 봅니다.

이 장은 두 부분으로 나뉩니다. 6.1~6.4절은 데이터를 준비하고 세 그룹의 답변을 생성하며, 6.5~6.8절은 점수를 매기고, 고정하고, 결론을 내립니다. 모든 명령은 GPU 호스트의 프로젝트 루트에서 실행합니다.

### 6.1 현재 데이터 규모와 검토 요건

이미 500/50/50개의 에피소드가 있으므로 예전 버전 규모로 다시 늘릴 필요는 없습니다. 카테고리마다 100/10/10개의 에피소드가 있고, 팩트 카드는 모두 60장입니다. "formal"은 이 교육용 실험에서 정한 고정 할당량이며, LoRA의 일반적인 최소 요건이 아닙니다.

같은 주제의 모든 변형은 하나의 group_id를 공유하며, 팩트 참조도 분할(split)을 넘나들 수 없습니다. 검증셋과 테스트셋은 각각 독립된 주제가 5개뿐이므로, 에피소드가 50개씩 있더라도 서로 무관한 50개의 지식 테스트로 취급할 수 없습니다.

**무엇을 검토라고 하는가.** 정식 검토는 모든 에피소드를 확인합니다. 출처가 사실을 뒷받침하는가, 지나친 의인화는 없는가, 아이가 이해할 수 있는가, 각 비유의 한계가 분명한가, 관찰 활동이 안전하고 실행 가능한가, 질문받기 싫어하거나 그만두고 싶어 하는 아이를 존중하는가. 검토는 `dataset.json`에서 직접 하고, 이력은 버전 관리로 남깁니다. 실제로 검토한 항목만 `review.status`를 `approved`로 바꾸고 실제 `reviewer`, `reviewer_kind`, `notes`를 채웁니다. 상태를 일괄 변경해 검토한 것처럼 꾸미지 마십시오. 프로그램은 구조는 검사할 수 있지만 유사 중복, 틀에 박힌 문구, 과학적 오류는 검사할 수 없습니다. 10가지 경로 유형은 의도적으로 교육 행동을 반복하고, 같은 주제는 일부 답변을 재사용하며, 50개의 학습 주제가 500개의 독립된 주제와 같은 것은 아닙니다. val/test는 학습 주제와 분리되어 있지만 빛, 힘, 생물 같은 기본 개념은 여전히 공유합니다.

`--allow-draft`를 쓰면 초안 데이터만으로도 이 장 6.1~6.6절의 검증셋 비교를 끝낼 수 있으며, 출력 매니페스트에는 `draft: true`가 기록됩니다. 후보 고정과 테스트셋(6.7절)에는 여전히 검토된 데이터가 필요합니다. 초안 결과를 정식 결론으로 오인하지 않기 위해서입니다.

### 6.2 데이터를 계속 개선하는 방법

먼저 주제마다 10개 경로를 모두 읽고, 아이의 각 피드백이 그에 맞는 변화로 이어지는지 확인합니다. 저학년 대상인데 설명 없는 전문 용어가 여전히 나온다면 다시 씁니다. 같은 비유가 구체적인 설명을 반복해서 대신해서는 안 되며, 한 번의 관찰로 그와 무관한 모든 결론을 증명할 수는 없습니다.

검증셋으로 실패 유형을 찾은 다음 그에 맞는 학습 시연 데이터를 추가합니다. 테스트 답변을 보고 데이터를 고치는 일은 피하십시오. 새 주제는 먼저 그룹으로 묶은 다음 분할에 배정합니다. 현재의 10가지 경로 유형은 구조화된 합성 데이터이지 아이와의 실제 상호작용이 아닙니다. 여건이 된다면 보호자의 사전 동의를 받아 익명 피드백을 수집하고, "대화 턴 수 늘리기"를 유일한 목표로 삼기보다 이해도와 자발적 탐구를 따로 평가하십시오.

### 6.3 검증과 준비

GPU 호스트의 프로젝트 루트에서 터미널을 열고, 먼저 3장에서 설치한 학습 환경을 활성화합니다. 다음 명령에는 PyTorch와 TRL이 필요합니다.

```bash
source .venv-train/bin/activate

python -m lab.data \
  --input data/dataset.json --allow-draft --formal

python -m lab.prepare \
  --input data/dataset.json \
  --tokenizer models/qwen3-4b --allow-draft --formal --output data/processed/experiment-v1

python -m lab.audit --data data/processed/experiment-v1 \
  --output runs/formal-token-audit.json
```

`--formal`은 500/50/50개 에피소드, 60장의 팩트 카드, 카테고리별 100/10/10 할당량을 검사합니다. `--allow-draft`는 검토되지 않은 항목을 허용합니다. 두 가지는 서로 독립된 검사입니다. 실제 검토를 마친 뒤 `--allow-draft`를 빼면 정식 데이터 버전이 됩니다(다른 출력 디렉터리, 예를 들어 `experiment-v2`를 사용하십시오).

자동 검사 항목: 할당량, 검토 상태, 출처 ID, 전체 대화 그룹의 중복, 동일한 사용자 대화, 제어 문자, 비어 있지 않은 타깃, 질문 횟수. 유사 중복, 의미상의 오류, 근거 없는 주장 등은 여전히 검토가 필요합니다. 프로그램은 URL만 보고 사실 여부를 판단할 수 없습니다.

### 6.4 세 가지 베이스라인과 두 가지 rank

| 그룹 | 가중치 | 프롬프트와 예시 |
|---|---|---|
| A | 기본 모델 | 기본 프롬프트, 예시 없음 |
| B | 기본 모델 | 전체 역할 프롬프트 + 학습셋에서 고른 few-shot 예시 3개 |
| C | 기본 모델 + 이 LoRA | B와 완전히 같은 프롬프트와 few-shot 예시 3개 |

B와 C의 few-shot 예시 3개는 `lab.prepare`가 고릅니다. train의 앞, 중간, 끝 부근에서 에피소드를 하나씩(가능하면 세 학년대를 모두 포함하도록) 골라 첫 번째 질문-답변 턴만 가져와 스냅숏의 `fewshots.json`에 씁니다. few-shot 예시는 추론 시에만 쓰고, SFT 학습 샘플에는 예시를 넣지 않습니다. 샘플 자신의 답변이 입력에 미리 붙어 버리는 일을 막기 위해서입니다.

세 그룹 모두 현재 질문에 대해 같은 팩트 카드, NF4 정밀도, greedy 디코딩을 사용합니다. 기본적으로 `val`을 읽으며, 참조 답변은 이후 검토에만 사용합니다. 고정 이력 모드는 이전 턴들의 참조 답변을 컨텍스트로 사용합니다. 이 절의 B/C 설정과 노트북의 few-shot 없는 관찰 질문 3개는 서로 다른 프로토콜이므로 점수를 섞지 마십시오.

먼저 검증셋에서 A와 B를 실행합니다.

```bash
python -m lab.infer --data data/processed/experiment-v1 --variant A \
  --output runs/val-A.jsonl
python -m lab.infer --data data/processed/experiment-v1 --variant B \
  --output runs/val-B.jsonl
```

r=16으로 1 epoch 학습합니다.

```bash
python -m lab.train --data data/processed/experiment-v1 \
  --output runs/formal-r16 --allow-draft --epochs 1 --rank 16
python -m lab.infer --data data/processed/experiment-v1 --variant C \
  --adapter runs/formal-r16/adapter --output runs/val-C-r16.jsonl
```

rank와 그에 대응하는 alpha만 바꾸고, 다시 기본 모델에서 시작합니다.

```bash
python -m lab.train --data data/processed/experiment-v1 \
  --output runs/formal-r8 --allow-draft --epochs 1 --rank 8
python -m lab.infer --data data/processed/experiment-v1 --variant C \
  --adapter runs/formal-r8/adapter --output runs/val-C-r8.jsonl
```

코드는 항상 alpha=2×rank로 설정하므로 두 실행 모두 스케일링 계수는 2입니다. r16 어댑터에서 r8을 이어서 학습한 뒤 이를 독립적인 비교라고 부르지 마십시오.

학습 샘플 1150개, 유효 배치 ≈16이면 1 epoch는 약 72번의 옵티마이저 업데이트로, 노트북 기본값과 같은 학습량입니다. B 그룹은 이미 좋은 프롬프트와 few-shot 예시를 갖추고 있으므로 C 그룹이 뚜렷한 우위를 보이지 않는 것도 지극히 정상이며, 그 자체로 가치 있는 결론입니다. 이 작업에는 프롬프트만으로 충분하다는 뜻이기 때문입니다.

**완료 기준:** 두 실행이 완전히 같은 데이터, 프롬프트, 생성 파라미터, 기본 모델을 사용하고, 검증 결과, 학습 시간, VRAM, 어댑터 크기를 비교할 수 있어야 합니다. 학습 loss만 보고 "더 나은 탐구 동반자"를 고르지 마십시오.

새 터미널을 열면 먼저 `source .venv-train/bin/activate`를 실행하고, 6.3~6.4절의 데이터 스냅숏과 후보 모델이 생성되어 있는지 확인하십시오.

### 6.5 고정 이력 먼저, 그다음 연속 대화

고정 이력(기본값, `--mode fixed`)은 데이터에 있는 참조 이력을 사용합니다. B/C의 각 입력 해시가 동일해야 하므로 특정 턴의 표현 차이를 정확히 짚어 내기에 좋습니다.

연속 대화는 모델 자신의 답변을 이후 이력으로 사용합니다.

```bash
python -m lab.infer --data data/processed/experiment-v1 --variant B \
  --mode rollout --output runs/val-B-rollout.jsonl
python -m lab.infer --data data/processed/experiment-v1 --variant C \
  --adapter runs/formal-r16/adapter --mode rollout --output runs/val-C-rollout.jsonl
```

두 그룹은 같은 사용자 스크립트를 사용하지만 각 모델이 이후 이력을 스스로 생성하므로, 뒤쪽 프롬프트의 해시는 달라질 수 있습니다. 미리 정해 둔 후속 질문 중 일부가 생성된 답변과 맞지 않을 수 있으니, 그런 경우는 채점할 때 기록하십시오. 실제 사람이 답변을 보고 후속 질문을 하는 것은 또 다른 종류의 평가입니다.

### 6.6 사람의 블라인드 평가

전체 프로그램: [evaluate.py](../lab/evaluate.py).

```bash
python -m lab.evaluate blind --base runs/val-B.jsonl \
  --tuned runs/val-C-r16.jsonl --output runs/blind-val-r16
```

이 명령은 `ratings.jsonl`, `key.json`, 그리고 프로토콜을 생성합니다. 채점할 때는 평가 파일과 팩트 카드만 보고 key는 보지 않습니다. 어느 쪽이 LoRA인지는 채점이 끝난 뒤에 공개합니다. 학습에 관여하지 않은 사람에게 채점을 부탁하면 후보에 대한 작성자의 편향을 줄일 수 있습니다.

각 항목에 대해 `winner`에는 X/Y/tie를, `reason`에는 구체적인 이유를 적습니다. `fact_claims_X/Y`와 `supported_X/Y`는 각각 따로 채웁니다. 검증할 수 있는 사실이 없으면 0을 적고, 이를 "100% 정확"으로 취급하지 마십시오. issues 필드에는 사실 오류, 학년대를 넘는 중국어나 전문 용어 남발, 지나친 질문, 선호 무시, 잘못된 출처 귀속, 아이의 관찰을 본 척하기 같은 문제를 기록합니다.

| 항목 | 0점 | 1점 | 2점 |
|---|---|---|---|
| 사실성 | 핵심 주장이 근거 없음/틀림 | 일부가 불분명하거나 범위가 지나치게 넓음 | 검증 가능한 모든 주장이 뒷받침되고, 모르는 것은 분명히 밝힘 |
| 학년대 적합성 | 아이의 수준을 넘고 전문 용어를 남발 | 이해는 되지만 피드백에 따라 설명을 조정하지 않음 | 구체적이고 간결하며, 이해하지 못하면 다시 설명함 |
| 탐구 가치 | 상투적 표현, 지어낸 내용, 억지 질문 | 흥미로운 지점은 있지만 다음 단계가 모호함 | 구체적이고 안전하며 선택 가능한 관찰이나 후속 질문 |
| 상호작용 | 명시적인 선택을 무시 | 대체로 반응하지만 반복적 | 선택을 존중하고 진행 속도가 적절함 |
| 근거 인식 | 추측이나 비유를 사실처럼 다룸 | 단서는 달지만 충분하지 않음 | 관찰, 설명, 비유를 구분하고 정보가 부족함을 인정함 |

이 기준표는 승자를 정하는 데 도움을 주며, 항목별 점수는 reason에 적어도 됩니다. 키워드 기반 자동 채점이 아닙니다. 심각한 사실 오류가 있는 답변은 더 "재미있더라도" 재미만으로 이겨서는 안 됩니다.

```bash
python -m lab.evaluate score --ratings runs/blind-val-r16/ratings.jsonl \
  --key runs/blind-val-r16/key.json --output runs/val-r16-score.json
```

승리는 1, 무승부는 0.5, 패배는 0으로 계산합니다. 스크립트는 group_id 과학 주제 단위로 부트스트랩하여, 같은 주제의 10개 경로와 여러 턴을 독립 샘플로 취급하지 않도록 합니다. 턴, 대화, 주제의 수를 보고하며, 주제가 2개 미만이면 구간을 출력하지 않습니다. 검증셋과 테스트셋의 주제는 각각 5개로 여전히 아주 적어서, 구간이 폭넓은 결론을 뒷받침할 수는 없습니다. 소표본 구간은 탐색적 결과일 뿐이며 평가자 편향을 없애 주지도 못합니다.

사실 근거율 = 출처로 뒷받침되는 주장 수 / 검증 가능한 주장 수이며, 스크립트는 이 주장들을 자동으로 검증하지 않습니다. 사실 검토 필드가 모두 채워지지 않았으면 `factual_review_complete=false`로 표시하므로, 일부만의 비율을 완전한 품질 결론으로 취급해서는 안 됩니다.

### 6.7 테스트셋은 고정한 뒤에만 사용하기

이 절에는 검토를 마친 정식 데이터가 필요합니다(6.3절의 prepare를 `--allow-draft` 없이 다시 실행). `freeze`와 테스트셋 추론은 초안 데이터를 거부합니다. 모델은 검증셋을 근거로 고릅니다. 아래는 r16을 예로 들며, r8이 더 적합하다면 이후의 어댑터 인자를 전부 그 후보로 바꾸십시오. 어떤 것을 고를지는 이 학습 실험의 결과이며, 튜토리얼이 미리 정해 두는 것이 아닙니다.

```bash
python -m lab.evaluate freeze --data data/processed/experiment-v1 \
  --adapter runs/formal-r16/adapter --output runs/frozen-candidate.json

python -m lab.infer --data data/processed/experiment-v1 --split test --variant B \
  --freeze runs/frozen-candidate.json --output runs/test-B.jsonl
python -m lab.infer --data data/processed/experiment-v1 --split test --variant C \
  --adapter runs/formal-r16/adapter --freeze runs/frozen-candidate.json \
  --output runs/test-C.jsonl

python -m lab.evaluate blind --base runs/test-B.jsonl \
  --tuned runs/test-C.jsonl --output runs/blind-test
```

테스트셋에서의 연속 대화도 같은 방식으로, `--mode rollout`과 새 출력 파일로 실행합니다. 테스트에서 `--limit`로 쉬운 문제만 골라내는 것은 금지입니다. freeze 파일에는 데이터 해시, 기본 모델, 어댑터 가중치와 설정을 합친 지문, 추론 코드, 디코딩 파라미터가 기록됩니다.

테스트 파일은 여전히 로컬에 있으므로, 실험자는 모델을 고정할 때까지 테스트 문제를 보지 않고 미뤄 두어야 합니다. 그것을 보고 학습 답변을 쓰는 일을 막기 위해서입니다. 테스트 결과를 보고 나서 계속 튜닝한다면 다음 라운드에는 새롭고 독립적인 테스트셋이 필요합니다.

### 6.8 결론을 내리는 방법

다음 순서로 한 페이지짜리 실험 기록을 작성합니다. 학습 설정과 비용 → 사실성과 블라인드 평가의 B/C 비교 → 대표적인 성공과 실패 사례 → 불확실성 → 다음 단계.

다음 단계는 검증 결과를 보고 정합니다. 차이가 불확실하면 독립적인 평가를 추가하고, 특정 행동이 잘못되면 그에 맞는 학습 예시를 추가하며, LoRA의 개선 폭이 부족하면 프롬프트 베이스라인을 유지합니다. 결론에는 사실 오류와 스타일 선호를 모두 고려해야 합니다.

성인의 선호나 모델의 자체 평가로는 아이들이 더 기꺼이 탐구하게 되었다는 것을 직접 증명할 수 없습니다. 진짜 목표를 확인하려면 참여 거부를 존중하면서, 아이가 핵심 이유를 이해하는지, 관련된 새로운 질문을 스스로 하는지, 안전한 관찰을 기꺼이 선택하는지도 관찰해야 합니다.

**완료 기준:** 전체 점수, 원본 출력, 실패 분류를 저장해 다른 사람이 각 비교에 어떤 입력이 쓰였는지 다시 확인할 수 있게 합니다.

### 7.1 먼저 속도를 측정하고 비용을 추정하기

먼저 제공업체의 시간당 가격, 스토리지 요금, 인스턴스 중지 후의 과금 규칙을 확인한 다음 이번 실험의 예산을 정합니다. 아래 계산은 시간당 US$0.74라는 가정 가격을 사용합니다. 실제 가격은 인스턴스를 만들 때 제시되는 금액을 따릅니다.

```text
GPU 费用 = 小时单价 × 开机计费时长
总成本 = GPU 费用 + 存储 + 其他服务 + 数据制作/审核投入
训练时间估算 ≈ 预热后每个 optimizer step 耗时 × 预计更新步数
```

(풀어 쓰면: GPU 비용 = 시간당 가격 × 과금되는 실행 시간, 총비용 = GPU 비용 + 스토리지 + 기타 서비스 + 데이터 작성/검토 노력, 예상 학습 시간 ≈ 워밍업 이후 옵티마이저 스텝당 시간 × 예상 업데이트 스텝 수.)

메인 경로(환경 구성, 다운로드, 1 epoch 학습, 병합, 배포, 부하 테스트)는 머신 시간으로 2~3시간 정도로 예상되며, 6장의 비교 실험과 검토까지 더하면 10~20시간이 걸릴 수 있습니다. 예시 가격으로는 각각 약 US$1.5~2.2와 US$7.4~14.8입니다. 실제로는 설정, 전송, 유휴, 스토리지 비용도 고려해야 합니다.

노트북의 `training-complete.json`(CLI에서는 `metrics-step-N.json`)에는 학습 시간과 최대 allocated/reserved VRAM이 기록됩니다. PyTorch의 통계는 다른 프로세스나 드라이버 오버헤드 전체를 포함하지 않으므로 `nvidia-smi`와 청구서로 교차 확인하십시오. 측정된 시간으로 예산을 갱신합니다.

### 7.2 문제 해결 표

| 증상 | 먼저 확인할 것 | 하지 말아야 할 것 |
|---|---|---|
| CUDA를 사용할 수 없음 | 호스트, 드라이버, Torch wheel, 현재 가상 환경 | Mac에 CUDA를 몇 번이고 재설치하기 |

| 토크나이저는 되는데 모델이 실패함 | 토크나이저만 내려받았는지, 가중치가 온전한지 | 무조건 VRAM 부족이라고 단정하기 |
| 길이 제한 초과 | 팩트, 이력, 타깃의 토큰 길이 | 참조 답변을 몰래 잘라 내기 |
| loss는 낮은데 결과가 나쁨 | 타깃 누출, 유사 중복, 실제로 로드된 어댑터 | epoch만 늘리기 |
| loss가 줄지 않음 | 마스크, 학습 가능한 파라미터, 학습률, 데이터 | 곧바로 GPU 바꾸기 |
| thinking/역할 마커를 출력함 | 모델 변형, 템플릿, 학습 타깃, 정지 토큰 | 백엔드에서 특수 텍스트를 무작정 제거하기 |
| 반복함/멈추지 않음 | EOS 감독, 중복 데이터, 과적합, 출력 한도 | 반복 문장만 걸러 내기 |
| OOM | 다른 프로세스, 길이, 배치, KV 캐시, 양자화 | RAM을 VRAM과 같은 것으로 여기기 |
| 재개가 거부됨 | 데이터/코드/환경/모델이 바뀌었는지 | 매니페스트 검사 우회하기 |
| 이야기를 더 지어냄 | 허구를 사실처럼 썼는지, 정직한 응답 샘플이 빠졌는지 | 재미 점수로 사실 오류 덮기 |
| 병합 후 품질 저하 | 리비전, 양자화되지 않은 기본 모델, 템플릿, 정밀도 | NF4/BF16 차이를 전부 LoRA 탓으로 돌리기 |
| API 타임아웃 | 서비스 상태, 모델 로딩, 컨텍스트, 동시성, 로그 | 끝없이 재시도하기 |
| API가 400을 반환함 | 입력 + `max_tokens`가 `--max-model-len`을 넘는지, `model` 이름이 `/v1/models`와 일치하는지 | 같은 요청을 계속 재시도하기 |
| 부하 테스트 중 지연 급증 | 동시성이 `--max-num-seqs`를 넘는지, KV 캐시가 가득 찼는지(`/metrics`와 로그 확인) | 대기열은 보지 않고 평균만 보기 |
| vLLM이 시작되지 않음 | 추론 환경, 드라이버, 모델 디렉터리, 다른 프로세스가 GPU를 쓰고 있는지 | 학습 환경의 의존성 덮어쓰기 |

### 7.3 최종 학습 체크리스트

- 이 프로젝트가 왜 SFT+QLoRA를 쓰는지 설명할 수 있다.
- 샘플 하나의 전체 컨텍스트와 실제 감독 타깃을 보여 줄 수 있다.
- 1 epoch 학습을 마치고, loss 곡선을 읽을 수 있으며, 완료 기록을 확인하고 어댑터를 저장한 뒤 다시 로드했다.
- 학습 중 VRAM의 구성 요소를 말할 수 있고 `nvidia-smi` 수치와 대조할 수 있다.
- 4.6절의 소표본 과적합 연습과 체크포인트 재개 연습을 마쳤다.
- 1 epoch 학습과 rank 비교 1회를 마치고, 검토 가능한 체크리스트를 저장했다.
- 학습 중 성능, 검증 결과, 고정 후 테스트 결과를 구분할 수 있다.
- 개선, 퇴보, 또는 "불확실"을 보고하고 근거의 한계를 설명할 수 있다.
- 병합하고, 내보내고, vLLM을 시작하고, 멀티턴 호출과 스트리밍 호출을 할 수 있다.
- KV 캐시 용량을 추정해 vLLM 시작 로그와 비교할 수 있고, `--gpu-memory-utilization`, `--max-model-len`, `--max-num-seqs`를 설명할 수 있다.
- 어댑터를 마운트해 같은 서비스에서 기본 모델과 LoRA를 비교하고, 병합 배포와 비교한 장단점을 설명할 수 있다.
- 여러 동시성 수준에서 부하 테스트를 실행해 TTFT, TPOT, 처리량 표를 채웠고, 처리량과 지연 시간의 트레이드오프를 설명할 수 있다.

프롬프트 베이스라인 대비 LoRA의 개선 또는 퇴보를 기록하고, 다른 사람이 다시 확인할 수 있도록 데이터와 출력을 함께 첨부하십시오.

```python
"""The TRL path is shared by the CUDA lesson and the tiny CPU regression test."""
from trl import SFTConfig, SFTTrainer
from transformers import TrainerCallback


class StopAfter(TrainerCallback):
    """Deliberately interrupt a planned run without changing its LR schedule."""
    def __init__(self, step):
        self.step = step

    def on_step_end(self, args, state, control, **kwargs):
        if self.step and state.global_step >= self.step:
            control.should_save = True
            control.should_training_stop = True
        return control


def make_trainer(model, tokenizer, train, val, output, *, cpu=False, epochs=1,
                 max_steps=-1, accum=16, lr=1e-4, max_length=4096, seed=42, stop_after=0):
    args = SFTConfig(
        output_dir=output, num_train_epochs=epochs, max_steps=max_steps,
        per_device_train_batch_size=1, per_device_eval_batch_size=1,
        gradient_accumulation_steps=accum, learning_rate=lr,
        warmup_ratio=0.05, lr_scheduler_type="cosine", optim="adamw_torch",
        max_grad_norm=1.0, bf16=not cpu, fp16=False, use_cpu=cpu,
        gradient_checkpointing=not cpu,
        gradient_checkpointing_kwargs={"use_reentrant": False},
        max_length=max_length, packing=False, completion_only_loss=True,
        assistant_only_loss=False, eos_token=tokenizer.eos_token,
        eval_strategy="epoch" if val is not None else "no",
        save_strategy="steps", save_steps=5, save_total_limit=2,
        logging_steps=1, report_to="none", prediction_loss_only=True,
        seed=seed, data_seed=seed, dataloader_num_workers=0,
        dataloader_pin_memory=not cpu, push_to_hub=False)
    return SFTTrainer(model=model, args=args, processing_class=tokenizer,
                      train_dataset=train, eval_dataset=val,
                      callbacks=[StopAfter(stop_after)])


def check_supervision(trainer, rows, eos_id, count=10):
    # D6：上下文和 padding 的 labels 应为 -100，当前参考回答及 EOS 才参与损失。
    for i, row in enumerate(rows[:count]):
        item = trainer.train_dataset[i]
        batch = trainer.data_collator([item])
        actual = batch["labels"][0].tolist()
        expected = [token if mask else -100 for token, mask in
                    zip(row["input_ids"], row["completion_mask"])]
        if actual != expected or -100 not in actual or not any(x != -100 for x in actual):
            raise ValueError(f"supervision mismatch at row {i}")
        supervised = [x for x in actual if x != -100]
        if supervised[-1] != eos_id or supervised.count(eos_id) != 1:
            raise ValueError("supervision must include one final EOS")
```

### lab/train.py

```python
"""Single NVIDIA GPU QLoRA lesson. Run `python -m lab.train --help` first."""
import argparse
import importlib.metadata
import json
import math
import os
import shutil
import subprocess
import time
from pathlib import Path

from lab.common import sha, tokenizer_signature, verify_bundle, write_json
from lab.data import read_sft


def main():
    p = argparse.ArgumentParser()
    p.add_argument("--model", default="models/qwen3-4b")
    p.add_argument("--data", required=True)
    p.add_argument("--output", required=True)
    p.add_argument("--epochs", type=float, default=1)
    p.add_argument("--max-steps", type=int, default=-1)
    p.add_argument("--limit", type=int, default=0)
    p.add_argument("--rank", type=int, default=16)
    p.add_argument("--lr", type=float, default=1e-4)
    p.add_argument("--accum", type=int, default=16)
    p.add_argument("--max-length", type=int, default=4096)
    p.add_argument("--seed", type=int, default=42)
    p.add_argument("--allow-draft", action="store_true")
    p.add_argument("--resume")
    p.add_argument("--stop-after", type=int, default=0)
    a = p.parse_args()
    if min(a.rank, a.accum, a.max_length) <= 0 or a.lr <= 0 or a.epochs <= 0:
        raise ValueError("positive training settings required")
    if a.max_steps == 0 or a.max_steps < -1 or a.limit < 0 or a.stop_after < 0:
        raise ValueError("invalid step/limit settings")
    import torch
    from datasets import Dataset
    from transformers import AutoModelForCausalLM, AutoTokenizer, BitsAndBytesConfig, set_seed
    from peft import LoraConfig, get_peft_model, prepare_model_for_kbit_training
    from lab.training import make_trainer, check_supervision
    if not torch.cuda.is_available() or not torch.cuda.is_bf16_supported():
        raise RuntimeError("main lesson requires a BF16-capable NVIDIA CUDA GPU")
    if int(os.environ.get("WORLD_SIZE", "1")) != 1:
        raise ValueError("this lesson uses one process and one GPU")
    folder, out = Path(a.data), Path(a.output)
    bundle = verify_bundle(folder)
    if bundle["draft"] and not a.allow_draft:
        raise ValueError("draft data requires --allow-draft; results are exploratory, not formal claims")
    if not bundle["formal"] and a.max_steps <= 0:
        raise ValueError("epoch experiments require the formal 600-episode science bundle")
    if out.exists() and any(out.iterdir()) and not a.resume:
        raise ValueError("output nonempty: choose new directory or resume")
    lock = json.loads((Path(a.model)/"model-lock.json").read_text())
    tok = AutoTokenizer.from_pretrained(a.model, local_files_only=True, trust_remote_code=False)
    if tokenizer_signature(tok) != bundle["tokenizer_sha256"]:
        raise ValueError("tokenizer differs from prepared data")
    tok.padding_side = "right"
    # CLI 读取 lab.prepare 从 dataset.json 生成的快照；Notebook 直接在内存中生成同样的 rows。
    rows = read_sft(folder, "train", bundle)
    if a.limit:
        rows = rows[:a.limit]
    val_rows = read_sft(folder, "val", bundle)
    if not rows:
        raise ValueError("training set is empty")
    for row in [*rows, *val_rows]:
        if len(row["input_ids"]) > a.max_length:
            raise ValueError("sample length exceeds training limit; rewrite and prepare again")
    packages = {name: importlib.metadata.version(name) for name in
                ("torch", "transformers", "trl", "peft", "bitsandbytes", "accelerate", "datasets")}
    config = {k: v for k,v in vars(a).items() if k not in {"resume", "stop_after", "output", "model", "data"}}
    contract = {"config": config, "base_lock": lock, "data_manifest_sha256": sha(folder/"manifest.json"),
                "code": {f: sha(Path(__file__).with_name(f)) for f in ("train.py", "training.py", "common.py")},
                "packages": packages}
    resume_step = 0
    if a.resume:
        previous = json.loads((out/"manifest.json").read_text())
        if previous["contract"] != contract:
            raise ValueError("resume configuration/data/code/environment differs")
        checkpoint = Path(a.resume).resolve()
        if checkpoint.parent != out.resolve():
            raise ValueError("resume checkpoint must belong to this output directory")
        for f in ("trainer_state.json", "optimizer.pt", "scheduler.pt"):
            if not (checkpoint/f).is_file():
                raise ValueError(f"not a resumable training checkpoint: missing {f}")
        resume_step = json.loads((checkpoint/"trainer_state.json").read_text())["global_step"]
    set_seed(a.seed)
    model = AutoModelForCausalLM.from_pretrained(
        a.model, local_files_only=True, trust_remote_code=False, torch_dtype=torch.bfloat16,
        device_map={"": 0}, attn_implementation="sdpa",
        quantization_config=BitsAndBytesConfig(load_in_4bit=True, bnb_4bit_quant_type="nf4",
            bnb_4bit_use_double_quant=True, bnb_4bit_compute_dtype=torch.bfloat16))
    model.config.use_cache = False
    model = prepare_model_for_kbit_training(model, use_gradient_checkpointing=True,
                                            gradient_checkpointing_kwargs={"use_reentrant": False})
    model = get_peft_model(model, LoraConfig(
        task_type="CAUSAL_LM", r=a.rank, lora_alpha=2*a.rank, lora_dropout=0.05,
        bias="none", target_modules=["q_proj", "k_proj", "v_proj", "o_proj",
                                     "gate_proj", "up_proj", "down_proj"]))
    model.print_trainable_parameters()
    trainable = {n: p for n,p in model.named_parameters() if p.requires_grad}
    if not trainable or any("lora_" not in n for n in trainable):
        raise ValueError("unexpected trainable parameters")
    initial = {n: p.detach().cpu().clone() for n,p in trainable.items()}
    def dataset(items):
        # D5：只将 Token 与监督掩码交给训练器，case_id/prompt 等保留用于人工核对。
        return Dataset.from_list([{k: row[k] for k in ("input_ids", "completion_mask")} for row in items])
    trainer = make_trainer(model, tok, dataset(rows), dataset(val_rows) if val_rows else None, str(out),
        epochs=a.epochs, max_steps=a.max_steps, accum=a.accum, lr=a.lr,
        max_length=a.max_length, seed=a.seed, stop_after=a.stop_after)
    check_supervision(trainer, rows, tok.eos_token_id)
    out.mkdir(parents=True, exist_ok=True)
    manifest = {"contract": contract, "draft": bundle["draft"], "gpu": torch.cuda.get_device_name(0),
                "cuda": torch.version.cuda, "supervised_rows": len(rows),
                "trainable_parameters": sum(p.numel() for p in trainable.values())}
    write_json(out/"manifest.json", manifest)
    (out/"dependencies.txt").write_text("\n".join(sorted(
        f"{d.metadata['Name']}=={d.version}" for d in importlib.metadata.distributions())) + "\n")
    driver = subprocess.run(["nvidia-smi"], capture_output=True, text=True, check=False)
    (out/"nvidia-smi.txt").write_text(driver.stdout + driver.stderr)
    torch.cuda.reset_peak_memory_stats()
    started = time.monotonic()
    result = trainer.train(resume_from_checkpoint=a.resume)
    if trainer.state.global_step <= resume_step:
        raise RuntimeError("no new optimizer step; inspect resume/max-steps")
    if not math.isfinite(result.training_loss) or any(not torch.isfinite(p).all() for p in trainable.values()):
        raise RuntimeError("non-finite loss or adapter parameters; inspect data and precision")
    changed = [n for n,p in trainable.items() if not torch.equal(initial[n], p.detach().cpu())]
    if not changed:
        raise RuntimeError("no LoRA parameter changed")
    trainer.save_model(str(out/"adapter"))
    tok.save_pretrained(out/"adapter")
    shutil.copyfile(out/"manifest.json", out/"adapter"/"manifest.json")
    trainer.save_state()
    metrics = dict(result.metrics, elapsed_seconds=time.monotonic()-started,
                   peak_allocated_gib=torch.cuda.max_memory_allocated()/2**30,
                   peak_reserved_gib=torch.cuda.max_memory_reserved()/2**30,
                   changed_lora_tensors=len(changed), resumed_from_step=resume_step,
                   final_step=trainer.state.global_step)
    if val_rows:
        metrics.update(trainer.evaluate())
    write_json(out/f"metrics-step-{trainer.state.global_step}.json", metrics)
    print(json.dumps(metrics, indent=2))


if __name__ == "__main__":
    main()
```
