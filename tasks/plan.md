# LoRA 微调实操：陪小学生探索十万个为什么

本教程面向**不做算法、想从零学习 LoRA 微调**的开发者，后端、前端、客户端、数据开发都适用，不需要机器学习背景。你会在一台租来的 RTX 4090 上亲手完成：下载开源模型 → 用 QLoRA 微调 → 保存和重载 → 合并导出 → 用 vLLM 部署成 OpenAI 兼容 API → 从自己电脑调用和压测。练习任务是用中文给小学生解答科学问题，让训练前后的变化容易看出来。

只读书用 `./book_review.sh`。命令均在项目根目录执行。

## 0. 开始之前：我们要做什么、需要准备什么

本章不碰任何命令。读完你应该能回答四个问题：我们到底要做出什么东西；整个过程分几步、每一步在哪台机器上做；需要提前准备什么；各个部件之间怎样配合。

### 0.1 一句话说清楚：把通用模型“岗前培训”成专用服务

我们从网上下载一个开源的通用大模型 **Qwen3-4B**（约 40 亿参数，阿里通义千问团队发布）。它什么都能聊，但说话方式不受我们控制：可能回答太长、用词超出小学生水平、喜欢反问。

接着用 600 段“孩子提问 → 理想回答”的示范对话**微调**它，让它学会一种固定的说话方式：先回答、短句、遇到错误猜想先纠正、给一个安全的小观察。最后把训练好的模型部署成一个 HTTP 服务，任何会调 OpenAI API 的后端代码改一下地址就能用。

用招聘做类比：

| 现实中的招聘 | 本教程里对应的东西 |
|---|---|
| 招来一个知识面很广的新员工 | 下载开源基座模型 Qwen3-4B |
| 给他看一叠“标准回复示范”做岗前培训 | 用示范对话做 SFT 微调 |
| 培训只记在一本小笔记里，不改变他原来的知识 | LoRA：原模型不动，只训练约 130 MB 的增量 |
| 培训后让他上岗接电话 | 用 vLLM 把模型部署成 API |
| 抽查他接电话的质量、看他一天能接多少通 | 调用测试、盲评、压测 |

**最重要的一条边界：** 微调教的是“怎么说”，不是“知道什么”。具体的科学事实由调用方每次放进提示词（本项目叫“事实卡”），模型负责用合适的方式讲出来。基座明明已经懂常识，为什么还要事实卡、训练时为什么也要放，第 2.2 节专门回答。

### 0.3 两台机器、三个窗口：它们怎样配合

整个过程只涉及两台机器。GPU 主机按小时租用，用完就停；你自己的电脑负责阅读、打包和调用。

```text
你的电脑（Mac / Linux / Windows 均可）
├── 浏览器：读这本书
├── 浏览器：打开平台提供的 JupyterLab ──HTTPS──→ GPU 主机的 JupyterLab
├── 终端 A：打包项目，用平台上传功能传到 GPU 主机
├── 终端 B：SSH 隧道，本地 18000 端口 ──SSH──→ GPU 主机 8000 端口
└── 终端 C：运行 Python 调用示例，请求发往本地 18000

云上 GPU 主机（Linux + RTX 4090）
├── JupyterLab：运行 Notebook，训练、保存、合并
├── 终端 1：装环境、下载模型、启动 vLLM 服务（监听 127.0.0.1:8000）
└── 终端 2：nvidia-smi 看显存、运行压测
```

| 部件 | 是什么 | 为什么需要它 |
|---|---|---|
| GPU 云主机 | 按小时租用的 Linux 服务器，带一张 NVIDIA 显卡 | 训练和推理都是海量矩阵运算，CPU 太慢；训练用的 4 bit 量化库只支持 NVIDIA |
| 平台镜像 | 开机时选的系统模板，预装了 Ubuntu、Python 3.11、显卡驱动 | 省去装系统和驱动；驱动只能由平台提供 |
| JupyterLab | 浏览器里的交互式 Python 编辑器，平台一般自带 | 训练代码一格一格执行，每格都能看到输出，出错时只重跑那一格 |
| 虚拟环境 `.venv-*` | 项目私有的 Python 依赖目录 | 训练和部署需要的库版本互相冲突，分开装才不会互相覆盖 |
| 内核（kernel） | Jupyter 背后真正执行代码的 Python 进程 | 必须选 `.venv-train` 注册的内核，Notebook 才能用到项目的依赖；关闭内核才会释放显存 |
| SSH 隧道 | 把本地端口转发到远端端口的加密通道 | 模型服务只监听 GPU 主机的 `127.0.0.1`，不暴露公网；本地通过隧道像访问本机一样调用它 |

### 0.6 练习任务：陪小学生探索科学

为什么不用客服、写代码之类的常见任务？因为“给小学生讲科学”这种回答风格鲜明，微调前后的变化一眼就能看出来；而且科学事实可以核对，方便判断模型有没有乱编。

#### 为什么选择科学探索

孩子问“为什么”，后续可能是猜错了、没听懂、想亲手验证，或者只想马上知道答案。这些反馈能让我们观察模型是否真的调整解释，而不只比较措辞是否可爱。

目标是：事实正确、孩子听得懂、下一步值得探索。趣味可以来自一个反常识现象、一个有边界的比喻或一个安全的小观察，不必每条都讲故事或用夸张语气。孩子说结束就结束，不以延长对话时长作为成功标准。

#### 覆盖范围

| 类别 | 数据值 | 训练主题例子 |
|---|---|---|
| 天文与太空 | `space` | 昼夜、四季、月相、流星 |
| 地球与天气 | `earth` | 云雨、雪花、岩石、河流 |
| 生命与自然 | `life` | 种子、根、蝴蝶、食物网 |
| 身边的物理 | `physics` | 影子、声音、浮力、溶解 |
| 工程与工具 | `engineering` | 拱桥、杠杆、飞机、太阳能电池 |

每类 100 段训练，另有 10 段验证和 10 段测试。这是有限教学样本，不是完整小学课程知识库。`grade_band` 分为 1–2、3–4、5–6 年级；学段是解释起点，实际反馈优先，不能断言同年级的孩子理解能力一致。

#### 提示词与微调怎样分工

一次请求里有四样东西，各管一件事：

| 部件 | 管什么 | 什么时候生效 |
|---|---|---|
| System Prompt（角色提示词） | 角色和基本规则：“你是陪小学生探索科学的伙伴……” | 每次请求都发 |
| 事实卡 | 这道题可以依据的科学资料 | 每次请求按题目选出来发 |
| SFT 示范对话 | 示范如何处理误解、没听懂、观察不一致和偏好变化 | 只在训练时用，学到的方式存进 adapter |
| LoRA | 限定只更新一小部分参数，原模型不动 | 训练时决定改哪些参数 |

本项目的 10 类示范路径是：纠正误解、换一种解释、接住具体追问、可选观察、检验猜想、由简入深、说明比喻边界、核对观察差异、不出题追问、自然结束。同一主题内部分答案复用，不能把 500 段理解成 500 个独立科学问题。

不承诺“提示词永远替代不了微调”。第 6 章会比较原模型加完整提示词及三个示例的 B 组，与使用完全相同输入的 LoRA C 组。在未训练的科学主题上，观察 C 是否更稳定地回应孩子反馈。如果没有改善，就如实保留 B。

### 0.8 结论的边界（全书只说一次）

- 所有对话都是合成草稿（`review.status="draft"`），没有经过人工逐条审核，回答偏短、结构重复。用它学**流程和工程**完全够用；用它得出“LoRA 一定更好”的结论不够。
- 能生成回答，只说明文件和服务可用；loss 下降，只说明模型更像参考回答。回答质量要看第 4.5 节的人工对比和第 6 章的盲评。
- 微调改变的是“怎么说”，不会让模型自动获得新知识或实时信息；事实仍由调用方放进提示词。

**验收：** 能画出“数据 → 训练 → 合并 → 部署 → 调用”的流程，说出每一步在哪台机器上做、产出什么文件；能列出开机前要准备好的东西；能指出一段对话中“知识是什么”以及“根据反馈改变了什么”。

### 1.1 模型在磁盘上是一个目录

打开 `models/qwen3-4b/`，一个"模型"物理上就是这些文件。注意：在自己电脑上用 `--tokenizer-only` 下载的目录（第 2.8 节）只有分词器和配置，约 15 MB，**没有**三个权重分片；分片要到 GPU 主机上完整下载（第 3.4 节）后才会出现，这是正常的，不是下载中断。

| 文件 | 是什么 | 类比 |
|---|---|---|
| `config.json` | 结构定义：36 层、隐藏维度 2560、词表 151,936 等 | 数据库的建表语句（schema） |
| `model-00001-of-00003.safetensors` 到 `model-00003-of-00003.safetensors` | 权重，约 40 亿个数字，BF16 共 8.0 GB，分 3 个分片；仅完整下载后才有 | 数据库的数据文件 |
| `model.safetensors.index.json` | 哪个权重在哪个分片 | 分片路由表 |
| `tokenizer.json`、`vocab.json`、`merges.txt` | 分词器：文字 ↔ 整数编号的规则 | 序列化协议 |
| `tokenizer_config.json` | 含 `chat_template`：system/user/assistant 怎样拼成一段文本 | 请求报文格式 |
| `generation_config.json` | 默认采样参数 | 服务端默认配置 |
| `model-lock.json` | 本教程记录的版本号（commit） | `package-lock.json` |

"加载模型"就是按 `config.json` 建好空结构，再把 `safetensors` 里的数字填进去，放到显存。后面会碰到三种目录：**基座**（上面这个）、**adapter**（只有 LoRA 增量，约 130 MB，必须搭配基座）、**合并模型**（基座 + 增量算好后的完整目录，又是 8 GB）。vLLM 加载的是基座或合并模型目录。

### 1.2 Token：模型眼里的文字

模型不读汉字，读整数。分词器把文本切成片段（Token），每个片段对应词表里的一个编号。用本项目的分词器切一句话：

```text
"为什么白天亮、晚上黑？"
→ ['为什么', '白天', '亮', '、', '晚上', '黑', '？']
→ [100678, 106772, 99538, 5373, 104030, 56652, 11319]

"The Earth rotates."
→ ['The', ' Earth', ' rotates', '.']
→ [785, 9237, 89059, 13]
```

常见词是一个 Token，生僻字可能拆成几个；英文的空格附在下一个词上。所以 Token 数不等于字数，中文大约 1 个 Token ≈ 1.3～1.5 个汉字。本教程所有"长度上限 4096"都指 Token 数。

词表里还有几个特殊 Token，不对应任何文字，而是结构标记。Qwen 的对话格式（`chat_template`）把一次请求拼成这样：

```text
<|im_start|>system
你是陪小学生探索科学的伙伴。……<|im_end|>
<|im_start|>user
为什么白天亮、晚上黑？<|im_end|>
<|im_start|>assistant
地球在不停转，我们住的地方转向太阳就是白天……<|im_end|>
```

`<|im_end|>`（编号 151645）是**结束标记 EOS**：模型生成到它就停。训练时必须让模型学会在回答末尾输出它，否则部署后回答停不下来。

### 1.3 参数与推理：一个有 40 亿个系数的函数

模型本质上是一个函数：输入一串 Token 编号，输出"下一个 Token 是词表中每一个的概率"。这个函数里有约 40 亿个可调系数，叫**参数**（或权重），就是 `safetensors` 里的数字。

**推理**就是反复调用这个函数：给它 prompt，取概率最高的 Token（贪心解码，`do_sample=False`），接到输入末尾，再调用一次，直到输出 EOS 或达到 `max_new_tokens`。参数在推理时一个都不改。

`temperature=0` 和贪心解码一样，每次都选概率最高的，所以同样输入会得到同样输出，便于对比；大于 0 时按概率随机抽，回答更多样但不可复现。

### 1.4 训练：用误差修正参数

**训练**是反过来：给模型看"上下文 + 参考回答"，让它在参考回答的每个位置预测下一个 Token，再把预测和参考的差距转成一个数，叫 **loss**。

| loss 大致范围 | 含义 |
|---|---|
| 约 3 以上 | 模型对参考回答的每个 Token 都很"意外"；随机猜的水平是 ln(151936) ≈ 11.9 |
| 1～2 | 原模型加好提示词，面对本项目参考回答的典型起点 |
| 0.5 左右 | 模型已经很接近参考回答的措辞 |
| 接近 0 | 几乎逐字背下来了；在验证集上若同时上升，就是过拟合 |

loss 是"对参考回答有多意外"，不是"科学知识得分"。它只能告诉你模型是否在学会训练数据的说法，不能告诉你回答是否正确。

有了 loss，就能算出每个参数"往哪个方向调一点能让 loss 变小"，这就是**梯度**（反向传播算出来的）。**优化器**（AdamW）按梯度更新参数，**学习率**（`1e-4`）决定每次改多大步：太大会把原模型的能力冲掉，太小学不动。一次"算 loss → 算梯度 → 更新参数"叫一个 **step**。

类比：loss 像 CI 的失败用例数，梯度像告诉你每个配置项该往哪边调，学习率像每次只敢改多少，step 像一次提交。

### 1.5 SFT、LoRA、QLoRA：三个独立的选择

三个词分别回答三个问题，可以独立组合：

**SFT（监督微调）回答"用什么教"。** 给模型看成对的"输入 → 期望输出"，也就是第 2 章的对话数据。本项目只对"参考回答 + EOS"的位置算 loss，上下文部分不算（第 2.5 节会亲眼看到这个掩码）。

**LoRA 回答"改哪些参数"。** 全量微调要更新 40 亿个参数，每个参数还要配梯度和优化器状态，单卡放不下，而且每个实验版本都要保存 8 GB。LoRA 的做法是：原权重 `W` 一个都不动，在旁边加两个小矩阵 `A`、`B`，只训练它们：

```text
实际使用的权重 = W（冻结） + (alpha / r) × B × A
```

类比 Git：基座是主分支，LoRA 是一个很小的 diff，训练只改 diff，`adapter/` 目录保存的就是这个 diff。"合并"等于把 diff 应用到主分支生成一份新的完整文件。

`r`（秩）决定小矩阵的宽度，也就是 diff 的容量。本项目 `r=16`，7 类线性层 × 36 层加起来约 3300 万个可训练参数，占总参数的 0.8%，adapter 文件约 130 MB。`alpha` 是缩放系数，本项目固定 `alpha = 2 × r`。

**QLoRA 回答"冻结的基座怎么放进显存"。** 冻结的权重反正不改，就把它们从 BF16（每个数 2 字节）压缩成 4 bit（每个数 0.5 字节）存在显存里，计算时临时还原成 BF16。4B 模型的权重从 8 GB 降到约 2.5 GB，24 GB 的卡才有余量放训练中间结果。`NF4` 是压缩格式的名字，`double_quant` 是把压缩用的辅助参数也压缩一下。LoRA 的小矩阵本身仍是 BF16，不压缩。

深入阅读：[LoRA 原论文](https://arxiv.org/abs/2106.09685)、[QLoRA 原论文](https://arxiv.org/abs/2305.14314)。

### 1.6 样本、Batch、Step、Epoch

| 概念 | 本项目的值 | 含义 |
|---|---|---|
| 样本 | 1150 条 | 一条"上下文 + 一个参考回答"；一段 2 轮对话展开成 2 条 |
| Micro-batch | 1 | 一次前向/反向放进显存的样本数 |
| 梯度累积 | 16 | 攒 16 条样本的梯度再更新一次参数；效果接近 batch=16，显存只占 1 条 |
| Step | 72 | 优化器更新次数 = ⌈1150 ÷ 16⌉；进度条和 loss 曲线的横轴 |
| Epoch | 1 | 所有样本过一遍 |
| Checkpoint | 每 25 步 | 可恢复训练的快照：adapter + 优化器状态 + 进度 |

类比：样本是一条消息，梯度累积是攒够 16 条再批量写库，step 是一次写库，epoch 是把队列消费一遍。

### 1.7 七个库各管什么

训练环境里会装七个库，报错信息里会出现它们的名字：

| 库 | 负责 | 你会在哪里看到它 |
|---|---|---|
| **PyTorch** | 张量计算、GPU 调度、自动求梯度；其他库都建在它上面 | `torch.cuda.*`、显存统计 |
| **Transformers** | 按 `config.json` 搭建模型结构、加载权重、分词器、聊天模板、`generate()` | `AutoModelForCausalLM`、`AutoTokenizer` |
| **PEFT** | 给模型加 LoRA 层、冻结原参数、保存/加载 adapter、合并 | `LoraConfig`、`get_peft_model`、`PeftModel` |
| **TRL** | 为 SFT 定制的训练器：按掩码算 loss、管理 step/epoch/检查点 | `SFTConfig`、`SFTTrainer` |
| **bitsandbytes** | 4 bit 量化的存储格式和 GPU 计算核 | `BitsAndBytesConfig`，只能在 NVIDIA GPU 上用 |
| **accelerate** | 把模型放到指定设备、混合精度；TRL 内部依赖它 | `device_map` |
| **datasets** | 训练器要求的数据容器 | `Dataset.from_list` |

部署时换另一个库：**vLLM** 自带推理引擎和 HTTP 服务，只需要模型目录，不需要上面七个库里的 PEFT 和 TRL。

调用关系：Transformers 加载模型 → bitsandbytes 把权重压成 4 bit → PEFT 加上 LoRA 层 → datasets 装好样本 → TRL 跑训练循环 → PEFT 保存 adapter → PEFT 合并 → vLLM 部署。

### 1.8 内存、显存与磁盘

| 资源 | 主要用途 | 容易误解的地方 |
|---|---|---|
| CPU | 文本处理、分词、加载与调度 | 核心数多不等于适合大模型训练 |
| RAM（主机内存） | 加载权重时的中转、CPU 上合并模型 | 100 GB RAM 不能替代 24 GB 显存：训练计算在 GPU 上，数据必须在显存里 |
| GPU | 大量矩阵运算 | CUDA 主线依赖 NVIDIA；Mac 的 MPS 是另一条路线，本教程不支持 |
| 显存（VRAM） | 权重、激活、梯度、优化器状态、推理 KV Cache | 模型文件 8 GB 不等于显存占 8 GB：训练要加中间结果，推理要加 KV Cache |
| 磁盘 | 基座、环境、检查点、合并模型 | 每个检查点含优化器状态；每次合并又是 8 GB |

训练显存的组成和实际读数见第 4.3 节；推理显存的估算见第 5.3 节。

**验收：** 能说出一个模型目录里每个文件是什么；能解释 loss 从 2 降到 0.6 意味着什么、为什么不能据此说回答更好；能说出 1150 条样本为什么是 72 步；能说出七个库中哪个负责 LoRA、哪个负责训练循环。

## 2. 训练数据：模型从哪里学、学什么

微调的效果几乎完全由数据决定：模型最后会说成什么样，就是你给它看的示范长什么样。所以在花钱开 GPU 之前，先把数据看明白。

!!! abstract "本章速览"
    - **本章做什么**：逐字段读一张事实卡和一段对话；看一段对话怎样拆成训练样本；看清模型到底“看到什么、学什么”
    - **需要准备**：只需要浏览器或编辑器；想亲手跑检查时，第 2.8 节说明怎样在自己电脑装一个轻量环境（不需要 GPU）
    - **做完得到**：能说出 1150 这个数字怎么来；能指出一条样本里哪些 Token 参与 loss；知道改数据后怎样让它生效

整个数据流可以先用一句话记住：**一份 JSON → 拆成“上下文 + 一个参考回答”的样本 → 用聊天模板变成 Token → 只在参考回答的位置算 loss。** 下面按这个顺序展开。

### 2.1 只维护一份 dataset.json

打开 [data/dataset.json](../data/dataset.json)。所有资料、500 段训练对话和评估对话都在这个文件里。顶层有四个平级数组：`facts` 是参考事实卡，`train`、`val`、`test` 是三组完整对话。真正参与训练的只有 `train`；事实卡只作为上下文，不是学习目标。

三份按科学主题（`group_id`）切开，同一个主题只会出现在一份里，避免模型在 val/test 上遇到训练时见过的同一话题。

| 集合 | 科学主题 | 完整对话 | 回答目标 | 用途 |
|---|---:|---:|---:|---|
| train | 50 | 500 | 1150 | 更新 LoRA 参数 |
| val | 5 | 50 | 115 | 比较配置、选择候选 |
| test | 5 | 50 | 115 | 候选冻结后评估 |

> **为什么还要一份 val，只有 train 和 test 不行吗？**
>
> 只训练一次、直接拿结果时，两份就够了。问题出在**根据测试结果做选择**：用 r=16 训练，看 test；不满意换 r=8，再看 test；再调学习率、改提示词……最后挑出 test 上分数最高的版本。这时 test 已经不算“没见过的数据”：模型参数没碰过它，但你的每一次选择都参考了它，等于用它挑过答案，挑出来的分数会偏高。
>
> 所以把“用来做选择”和“用来出最终成绩”分开。类比后端发布：train 是开发环境，模型反复用它更新参数；val 是预发环境，你可以反复看它来比较、挑选；test 是上线后的真实流量，候选定下来后只看一次，出最终报告。
>
> 本项目里 val 支撑了这些选择：训练中每 12 步算一次验证 loss，判断是否过拟合（第 4.5 节）；比较 r16 和 r8（第 6.4 节）；比较“原模型 + 好提示词”的 B 组和 LoRA 的 C 组（第 6.5、6.6 节）；最终选定候选（第 6.7 节）。选定后用 `evaluate freeze` 冻结，代码才允许在 test 上推理，而且不能用 `--limit` 只挑部分题。看过 test 又回去改模型或数据，下一轮就要换一份新的测试集。
>
> 别处常见“只要训练集和测试集”，通常是只训练一次、不做比较；或者用交叉验证在 train 内部轮流切出验证部分（val 藏在 train 里）；或者直接把 test 当 val 用，这样得到的 test 分数偏乐观。

训练学段分布：1–2 年级 167 段，3–4 年级 167 段，5–6 年级 166 段。每个主题 10 条交流路径，每段 2～3 轮；既有同一知识在不同学段的解释，也有不同反馈导致的后续变化。

```text
data/dataset.json
├── schema_version / description   文件版本与说明
├── facts[60]                      参考事实卡，只存一份，被对话按 id 引用
├── train[500]                     训练对话：唯一参与参数更新的部分
├── val[50]                        验证对话：比较配置、选候选、算 eval loss
└── test[50]                       测试对话：候选冻结后才使用

train / val / test 里的每段对话结构相同：
├── id / group_id                  对话编号 / 科学主题分组
├── grade_band                     1-2 / 3-4 / 5-6
├── fact_ids                       引用 facts 中的 id
└── turns[]                        user / assistant / behavior
```

对话属于哪个集合，只由它放在哪个数组决定，对话里不再写 `split` 字段，避免“放在 val 里却写着 train”这种自相矛盾。程序读入时（`lab.data.read_dataset`，Notebook 里是 `tag_splits`）会在内存里给每段对话补上 `split`，后面的筛选和跨集合检查都用它；源文件保持不变。要把一段对话挪到别的集合，就把整段剪切到另一个数组里，同一 `group_id` 的其他对话和它引用的事实卡要一起挪。

JSON 不支持 `//` 注释。这里解释字段，Notebook 用 D1～D7 标记实际使用位置。不要把整份 JSON 塞进提示词，也不要把评估对话一起传给训练器。

#### 为什么需要事实卡：三个常见疑问

微调教的是“怎么说”（第 0.1 节），初学者读到这里通常会接连冒出三个问题。

**问 1：小学科学是常识，基座模型早就知道，为什么还要事实卡？**

确实，这些常识基座模型大多知道。只论“知识从哪来”，事实卡不是必需的。仍然要它，原因不在补知识：

1. **让训练只学“怎么说”。** loss 算在参考回答上，而参考回答里既有说法，也有事实内容。输入里没有资料时，模型只能靠权重把“转向太阳”“背光的一面”这些内容硬记下来，训练会把“说法”和“知识”混在一起学；资料就在输入里时，内容照着资料说就能预测对，LoRA 有限的容量主要花在“短句、先纠正误解、给一个安全的小观察”上。原理见问 3。
2. **基座的知识检查不了、也改不了，事实卡可以。** 你说不准一个 4B 模型会在哪道题上出错（比如把季节归因于离太阳远近），错了也没法打开权重去改。事实卡是一段看得见的文字，有来源、有审核状态，写错了改一张卡，下一次请求就生效。类比后端：业务规则放在配置或数据库里，而不是散落在编译好的二进制里。
3. **卡上有基座不会主动遵守的边界。** 例如 `day-night` 的 `text` 写明“假定取消自转但保留公转，光照位置仍会随公转缓慢变化”，参考对话第二轮的追问就以它为依据；`scope` 写明“模型和比喻不能替代真实测量”；`kind` 区分 fact、legend、current，传说不能当事实讲。
4. **这就是真实产品的形态，也是评估的依据。** 业务里模型要讲的往往是它根本不知道的东西：产品规格、本校课本、当天的数据。常见做法是调用方查到资料放进提示词，模型负责讲清楚，也就是常说的 RAG（检索增强生成）。本项目用事实卡完整练一遍这个模式。盲评时，评分人也要对照事实卡判断每条断言有没有依据（第 6.6 节）。

**问 2：事实卡也在训练样本里，那训练完模型就记住这些知识了吗？**

不能这样理解。事实卡是训练样本的**输入**，不是**学习目标**。第 2.5 节那条 408 Token 的样本里，事实卡在 mask=0 的 386 个 Token 中：模型看得到它，但不会因为“没记住它”而被扣分。loss 只考一件事：看着这些资料，回答写得像不像参考回答。

| | 训练后学到了吗 | 原因 |
|---|---|---|
| 怎样读资料、怎样用资料组织回答 | 学到了 | 这是 loss 推着它学的东西 |
| 资料本身的内容和边界 | 不可靠 | 训练时资料一直摆在眼前，不需要记 |

需要说实话的一点：参考回答本身含有事实内容，这部分在 mask=1 的区域，模型会顺带记住一点常见说法。但只训 1 个 Epoch、每条只看一遍，记得很浅，也记不住卡上的完整内容和边界；你更没法知道它记住了哪些、记错了哪些。所以部署时**每次都要传事实卡**，第 5.5 节的调用示例先 `read_dataset` 读出 facts，就是这个原因。

想亲眼验证：训练完后用同一个问题问两次，一次带事实卡，一次去掉 `CURRENT REFERENCE FACTS` 那段，比较回答的准确性和边界。差别越明显，说明模型依赖的是当场给的资料，而不是背下来的知识。

**问 3：既然不靠它背知识，训练时为什么还要放？部署时再传不行吗？**

不行。训练不是要模型**记住**事实卡，而是要它学会**使用**事实卡；要学会使用，训练时就必须看见。用新员工培训打个比方：

| | 练法 A：只给问答 | 练法 B：问答旁边附产品手册（本项目） |
|---|---|---|
| 培训材料 | 客户问 X → 标准回复 Y | 客户问 X + 手册相关页 → 标准回复 Y |
| 练出来的习惯 | 听到问题，凭记忆背答案 | 先翻手册，再用标准口吻讲出来 |
| 上岗时递给他手册 | 没练过看手册，多半还背老答案 | 正是练过的流程 |
| 手册更新了一条 | 还按旧答案说 | 照新手册说 |
| 遇到没培训过的问题 | 凭印象硬答，容易编 | 照手册讲，手册没写的不乱说 |

换成本项目的同一条样本，目标回答完全相同，只是输入不同：

```text
不带事实卡：
  输入：为什么白天亮、晚上黑？
  目标：地球在不停转，我们住的地方转向太阳就是白天……

带事实卡：
  输入：[事实卡：自转使地球表面交替朝向和背向太阳……] 为什么白天亮、晚上黑？
  目标：地球在不停转，我们住的地方转向太阳就是白天……
```

不带卡时，输入里没有任何依据，目标却是确定的科学结论，1150 条样本反复强化的是“听到问题，凭空给出确定结论”；带卡时，目标里的内容都能在输入里找到，反复强化的是“从给的资料里取内容，改写成孩子听得懂的话”。

如果训练时不放、只在部署时放，会出现四个问题：

1. **模型没练过看资料。** 部署时多出一大段 `CURRENT REFERENCE FACTS`，对它是陌生输入，可能被忽略，照样凭记忆回答。
2. **改资料不生效。** 发现某张卡写错，或想在某张卡的 `scope` 里补一条适用边界，练法 A 的模型不会跟着变，只能改训练数据重新训练。
3. **新主题更容易编。** 练法 A 养成的是“凭空给结论”的习惯，遇到训练里没有的主题也照样自信地下结论。
4. **输入格式对不上。** 训练时提示词里没有事实卡，部署时有，模型学到的说话方式依赖它训练时见过的输入样子；这也是第 5.5 节强调“提示词要和训练时一致”的原因。

用代码的话说，训练是在学一个函数 `answer = f(question, facts, grade_band, history)`。如果训练时只给 `question`，学到的是 `f(question)`；部署时再多传一个它从没用过的参数 `facts`，它不会自动去用。

不用事实卡也能训练、也能回答，代价就是上面这些：编错了改不了、容易过度自信、换到基座不懂的领域要推倒重来。把“事实”和“说法”分开是本项目的设计取舍，不是唯一做法；它的收益最终要靠第 6 章的对照来验证。

#### 事实卡在哪里用到

**为什么单独存一份。** 60 张卡被 600 段对话按 `fact_ids` 引用（一段对话可引用多张），类似数据库里的外键：同一条事实只改一处，所有引用它的对话下次读入时都会用新内容。

**为什么也要按集合隔离。** 一张卡只能被同一个集合（train/val/test 之一）的对话引用。否则验证、测试题依据的资料，模型在训练时已经见过，评估结果会偏乐观。

| 环节 | 代码位置 | 怎样使用事实卡 |
|---|---|---|
| 读入校验（D1） | [data.py](../lab/data.py) `validate` | `id` 唯一；字段齐全；`source_url` 为 https；`kind` 只能是 fact/legend/current；对话的 `fact_ids` 必须都存在；同一张卡不能跨 train/val/test |
| 拼提示词（D3） | [common.py](../lab/common.py) `build_messages` | 按 `fact_ids` 取出卡片，只保留 `id/text/kind/scope`，以 JSON 写在 system 提示词的 `CURRENT REFERENCE FACTS:` 之后；来源与审核字段不进入模型 |
| Notebook 训练与验证样本 | Notebook 第 2 步 `prepare-data` 格 | 1150 条 train 样本和 115 条 val 样本都经 `build_messages` 带上各自的事实卡 |
| Notebook 观察题 | Notebook 第 4 步 `cases` 格 | 三道观察题各指定一个 `fact_id`，训练前后用同一张卡对比回答 |
| 命令行快照 | [prepare.py](../lab/prepare.py) | 原样写入快照的 `facts.jsonl`；few-shot 示例记录它们的 `fact_ids` |
| A/B/C 对照推理 | [infer.py](../lab/infer.py) | 从快照读 `facts.jsonl`，三组都附当前题目的同一张事实卡（第 6.4 节） |
| 盲评 | [evaluate.py](../lab/evaluate.py) `blind` | 评分表带 `fact_ids`，评分人对照事实卡填写 `fact_claims`/`supported`（第 6.6 节） |
| 部署后调用 | 第 5.5 节调用示例 | `read_dataset` 读出 facts，`messages_for(fact_id, ...)` 拼出和训练相同的 system 提示词 |

#### 来源与审核字段

`source_url` 是人工回查来源的入口，程序不会自动上网阅读。`checked_at` 只代表已阅读参考入口；`source_review` 为 `reference_read_claim_review_pending` 表示逐项断言仍待审核。`reuse` 是来源署名和原创改写说明，不代表来源机构认可本数据。NASA、NOAA、USGS 等官方科普和 OpenStax 教材是参考入口；正文为原创中文整理，比喻、儿童反馈和观察设计为合成示范。URL 存在不等于每句话有来源支持。

```json
    "day-night"

    "type": "synthetic",

```

孩子先问昼夜，再提出“太阳睡觉”的猜想。参考回答先解释现象，随后修正具体误解，并留下一个可选择继续思考的问题。不要只学“你真棒”等固定口头禅。

| 字段 | 是否进入模型、在哪里使用 |
|---|---|
| `id` | 生成 `day-night-01:0` 等样本编号，供追踪 |
| `group_id` | 同一科学主题统一分组；所有学段、路径、改写必须在同一 split |

| `grade_band` | **D3 写入 system 中的“小学学段”**，是可见输入 |
| `fact_ids` | D3 选择本文件中的事实卡，只传 id/text/kind/scope |
| `turns[].user` | 当前孩子的问题；此前问题进入 history |

把这张表记住一条就够：**模型看到的只有 system（角色 + 学段 + 事实卡）、history 和当前 user；它学的只有当前 assistant。** 第 2.5 节会把这句话变成真实的 Token 和掩码给你看。

### 2.4 一段对话按回答展开

`day-night-01` 有两轮，展开为两条样本：

| 样本 | 上下文 | 参与 Loss 的目标 |
|---|---|---|
| `day-night-01:0` | 角色 + 学段 + 昼夜资料 + 为什么白天亮晚上黑 | 第 1 个参考回答 + EOS |
| `day-night-01:1` | 同样角色、学段、资料 + 第 1 轮问答 + 太阳睡觉的猜想 | 第 2 个参考回答 + EOS |

第一条看不到第二轮。第二条的历史回答也不参与本轮 Loss。500 段 train 中，350 段两轮、150 段三轮，因此产生 **1150 条样本**。1150 不是 Token 数，也不是优化器步数。

**两轮对话是“训练两次”吗？** 不是同一份内容训两遍，而是这段对话贡献了两条独立样本，每条在 1 个 Epoch 里各训一次。1150 条样本进入训练器后会被打乱，每 16 条更新一次参数，`day-night-01:0` 和 `day-night-01:1` 通常落在不同的 step 里。第 1 个回答只在第 1 条样本里算 loss；在第 2 条里它只是历史。

**轮数更多时也是同一个规律**，就像一个 session 的完整聊天记录：第 k 条样本把前 k−1 轮问答全部当作历史，只学第 k 个回答。这和部署时的调用方式一致：服务端不记状态，客户端每次把完整历史发过去（第 5.5 节）。有两点区别要知道：

- 训练时历史里是**参考回答**，部署时历史里是**模型自己说过的话**，可能和参考回答不一样。第 6.5 节的连续对话模式专门检查这种差别。
- 越往后的样本越长，历史在每条样本里都要重算一遍。本项目的校验只接受 2～4 轮的对话，超过 4096 Token 会直接报错，不会悄悄截断。

### 2.5 掩码：模型实际学的是哪些 Token

用本项目的分词器把 `day-night-01:0` 渲染出来（下面是真实输出，system 中间的角色规则省略了几行）。整条样本 408 个 Token，其中只有最后 22 个参与 loss：

```text
mask │ 渲染后的文本
─────┼──────────────────────────────────────────────────────────
  0  │ <|im_start|>system
  0  │ 你是陪小学生探索科学的伙伴。用中文，先回应孩子真正的问题，再按需要解释。
  0  │ ……（角色规则共 10 行）
  0  │ 小学学段：1-2 年级。
  0  │ CURRENT REFERENCE FACTS:
  0  │ [{"id": "day-night", "text": "自转使地球表面……", "kind": "fact",
  0  │   "scope": "昼夜的入门解释；……"}]<|im_end|>
  0  │ <|im_start|>user
  0  │ 为什么白天亮、晚上黑？<|im_end|>
  0  │ <|im_start|>assistant
  1  │ 地球在不停转，我们住的地方转向太阳就是白天，转到背光的一面就是晚上。<|im_end|>
```

mask 为 0 的 386 个 Token 模型能看到，但不在这里算 loss；mask 为 1 的最后 22 个 Token 才是学习目标。事实卡就在这 386 个 Token 里：模型不背它，但要学会看着它回答，所以训练时也必须放（第 2.2 节问 2、问 3）。

最后一行切成 Token 是：`地球` `在` `不停` `转` `，` `我们` `住` `的地方` `转向` `太阳` `就是` `白天` `，` `转` `到` `背` `光` `的一面` `就是` `晚上` `。` `<|im_end|>`。训练时模型在这 22 个位置上各猜一次“下一个 Token”，猜错多少就是 loss；前面 386 个位置只提供上下文。

为什么不让模型也学 system 和 user 部分？因为部署后这些内容总是由调用方提供，模型只需要学会“看到这样的输入，该怎样回答”。如果把 user 也算进 loss，模型会花力气去模仿孩子提问，还可能学会自己编造下一轮问题。

`rows` 留有 `case_id/prompt/completion/input_ids/completion_mask`，方便查看。实际训练只收后两列。Notebook 会打印第一条的完整提示词、目标和真实 Token 长度；不要沿用旧场景的长度数字。

`completion_mask=0` 表示上下文，`=1` 表示当前回答及 EOS。TRL 将上下文和 padding 的 labels 设为 `-100`，不对这些位置直接计算损失，但模型预测答案时仍能看到上下文。

EOS 是 <code>&lt;&#124;im_end&#124;&gt;</code>，每个目标只出现一次，让模型学习结束；PAD 与 EOS 不同。超出 4096 Token 会报错，需改写样本，不悄悄截掉答案。

### 2.6 回顾：从一份 JSON 到参数更新的七步

前面五节按“数据长什么样 → 怎样拆 → 模型看到什么、学什么”讲完了数据。把它们串起来就是下面七步。Notebook 的代码注释用 D1～D7 标出每一步在哪一行，训练时对照着看，就知道哪一行在做本章讲的哪件事。

| 步骤 | 做什么 | 对应本章 |
|---|---|---|
| D1 读入 | 读 `dataset.json`，给每段对话标上所属集合，检查事实卡引用和跨集合隔离 | 第 2.1、2.2 节 |
| D2 拆分 | 只取 train，把每段对话按回答拆成样本，历史只含此前的轮次 | 第 2.4 节 |
| D3 拼输入 | 角色规则 + 学段 + 事实卡 + 历史 + 当前问题，拼成一组 messages | 第 2.2、2.3 节 |
| D4 标目标 | 套聊天模板、分词，把当前回答和 EOS 标为 mask=1 | 第 2.5 节 |
| D5 交给训练器 | 只把 `input_ids` 和 `completion_mask` 两列交给 TRL | 第 2.5 节 |
| D6 再核对 | 检查训练器实际生成的 labels：上下文和填充位置都是 -100（不算 loss） | 第 2.5 节 |
| D7 留底 | 保存本次数据副本和指纹，然后 `trainer.train()` 才真正更新参数 | 第 4 章 |

### 2.7 想改数据，或换成自己的数据

练习时不需要改数据，本节在你想动手改的时候再读。

**改现有数据。** 修改说法就改 `assistant`；增加一种新的反馈路径时，要同时调整前后轮，别让孩子引用模型根本没说过的话；改了某张事实卡，要复查所有引用它的对话。改完后先跑结构检查：

```bash
python -m lab.data --input data/dataset.json --allow-draft
```

应输出 `{'train': 500, 'val': 50, 'test': 50}`。它只检查结构：字段齐全、事实引用存在、同主题不跨集合、每个回答最多一个问号；不检查科学内容对不对。

**让修改生效。** 已经训练好的 adapter 不会因为你改了 JSON 而变化。在 Notebook 里把 `RUN_DIR` 换成新目录（例如 `runs/science-002`），从第 2 步重新执行即可。每次训练的运行目录里会自动留一份 `dataset.json` 副本，记录“这次训练用的是哪份数据”，日常不要编辑它。

**换成自己的数据。** 开源 SFT 数据常见的 Alpaca（instruction/output）、ShareGPT（conversations）格式，和本项目本质相同：都是“一组对话消息 + 哪一条是期望输出”，只是 JSON 排法不同。换数据时主要改两处：把你的数据整理成 train/val/test 三组对话；按需要改 D3 的 `build_messages`，决定 system 里放什么。

### 3.2 先读懂 nvidia-smi：驱动、CUDA 与显存

登录 GPU 主机后第一件事是运行 `nvidia-smi`。它的输出大致是：

```text
+-----------------------------------------------------------------------------------------+
| NVIDIA-SMI 560.35.03              Driver Version: 560.35.03      CUDA Version: 12.6     |
|-----------------------------------------+------------------------+----------------------+
| GPU  Name                 Persistence-M | Bus-Id          Disp.A | Volatile Uncorr. ECC |
| Fan  Temp   Perf          Pwr:Usage/Cap |           Memory-Usage | GPU-Util  Compute M. |
|=========================================+========================+======================|
|   0  NVIDIA GeForce RTX 4090        Off | 00000000:01:00.0 Off   |                  Off |
| 30%   35C    P8             20W / 450W  |       0MiB / 24564MiB  |      0%      Default |
+-----------------------------------------+------------------------+----------------------+
| Processes:                                                                              |
|  GPU   GI   CI        PID   Type   Process name                              GPU Memory |
|=========================================================================================|
|  No running processes found                                                             |
+-----------------------------------------------------------------------------------------+
```

| 位置 | 含义 | 你要关心什么 |
|---|---|---|
| `Driver Version` | 内核驱动版本，由平台镜像决定，普通用户改不了 | 决定了下面的 CUDA 上限 |
| `CUDA Version` | **这个驱动最高支持的 CUDA 版本**，不是已安装的 CUDA | PyTorch 的 `cu126` 要求它 ≥ 12.6；vLLM 0.21 的 `cu129` 要求 ≥ 12.9 |
| `Memory-Usage` | 已用 / 总显存 | 训练前应接近 0；训练时看它涨到多少；启动 vLLM 前确认训练内核已释放 |
| `GPU-Util` | GPU 算力利用率 | 训练和压测时应持续较高；长期为 0 说明程序卡在 CPU 或等待 |
| `Processes` | 哪些进程占着显存 | 找到忘记关闭的 Jupyter 内核 |

**驱动、CUDA、PyTorch 的关系：** 驱动装在操作系统里，和显卡绑定；CUDA 是 NVIDIA 的计算库，PyTorch 的 wheel 包自带它需要的那份（`torch==2.8.0` 的 `cu126` 后缀就是"内置 CUDA 12.6 的运行库"），所以不用自己装 CUDA 工具包；唯一的约束是驱动支持的版本不能低于 wheel 内置的版本。镜像名里的 `CUDA12.6` 说的是预装的工具包，和驱动上限是两回事，以 `nvidia-smi` 为准。

类比：驱动像操作系统内核版本，CUDA 运行库像应用自带的依赖，`nvidia-smi` 像 `top` 加 `free -h`。

显存和主机内存是两块独立的内存：模型权重、训练中间结果、KV Cache 都必须在显存里，主机的 100 GB 内存只用来中转和在 CPU 上做合并。显存不够时，报错是 `CUDA out of memory`，解决办法是减小占用（量化、更短的样本、更小的并发），不是加主机内存。

#### `trainer.train()` 里面发生了什么

第 7 格只有一行 `trainer.train()`，但它把第 1 章的概念全部串了起来。一个 step 的过程是：

```text
重复 16 次（梯度累积）：
    取 1 条样本的 input_ids（约 400 个 Token）
    前向：NF4 基座临时还原成 BF16 参与计算，LoRA 的 A、B 叠加在 7 类线性层上
          → 每个位置输出“下一个 Token”的概率
    loss：只在 completion_mask = 1 的位置（参考回答 + EOS）比较预测和答案
    反向：算梯度，但只算到 LoRA 的 A、B 上；基座参数冻结，没有梯度
          → 梯度累加起来，不立刻更新
AdamW 按累加的梯度更新 LoRA 参数一次（学习率按 warmup + cosine 变化）
step + 1；每 12 步在 115 条 val 样本上只做前向、算一次验证 loss；每 25 步存一次检查点
```

72 个 step 跑完，1150 条样本每条恰好被看过一次（1 个 Epoch）。整个过程中 40 亿个基座参数一个都没变，变的只有约 3300 万个 LoRA 参数，所以第 8 格会专门检查“LoRA 张量确实变了”。

### 4.2 为什么这样设置

| 设置 | 当前值 | 理由 |
|---|---|---|
| 基座 | Qwen3-4B-Instruct-2507，固定 revision | 固定比较对象 |
| 训练方式 | NF4 + BF16 计算 + LoRA | 在单张 24 GB 卡上只更新少量参数 |
| LoRA | rank 16、alpha 32、dropout 0.05 | 常见的练习起点 |
| 目标层 | q/k/v/o 与 gate/up/down 投影 | 覆盖注意力和前馈投影 |
| 微批次 / 累积 | 1 / 16 | 每次只放一条样本进显存，累积 16 条再更新一次 |
| 优化器 / 学习率 | AdamW / 1e-4 | 配合短 warmup 和 cosine 调度 |
| 长度 / 拼接 | 4096 / 不 packing | 不静默截断目标，便于检查监督范围 |
| 训练量 | 1 Epoch ≈ 72 步 | 全部训练样本过一遍，训练前后能看出差别；只想测链路可改为 10 |
| 验证 | 每 12 步算一次验证 loss | 用没参与训练的主题观察是否过拟合 |

每个配置参数的含义、为什么取这个值、改了会怎样，写在 Notebook 对应代码格下方的表格里（第 3、5、6 步），这里不重复。

### 4.3 训练时看 GPU：显存花在哪里


每 2 秒打印一行。对照下面的估算看数字怎么变化：

### 4.5 看懂 loss 曲线，再对比回答

`loss-curve.png` 的读法：训练 loss 总体下降，说明模型在拟合参考回答；验证 loss 同时下降，说明这种回答方式对没见过的主题也适用；训练 loss 还在降、验证 loss 却开始上升，就是过拟合。两条线都不动时，先查学习率、可训练参数和 mask。

下图是 2026-10-11 在 RTX 4090（24 GB）上按本章默认配置跑满 1 个 Epoch 的真实曲线，耗时约 26 分钟：

![RTX 4090 上 1 个 Epoch 的真实 loss 曲线：训练 loss 从约 6 快速降到 2.5 左右后缓慢下降，验证 loss 从 2.51 降到 1.96 后持平](../images/loss-curve-rtx4090-2026-10-11.png)

| Step | 12 | 24 | 36 | 48 | 60 | 72 |
|---|---:|---:|---:|---:|---:|---:|
| 验证 loss | 2.51 | 2.19 | 2.03 | 1.98 | 1.96 | 1.96 |

按这张图逐段读：

- **前 10 步：训练 loss 从约 6 陡降到 2.5 左右。** 原始模型习惯的说法和这些简短、口语化的参考回答差别很大，一开始很“意外”；LoRA 先学会了这种格式和语气。前几步学习率还在预热，所以第 1～3 步几乎没降。
- **第 10～48 步：两条线一起缓慢下降。** 这是真正在学“怎么说”的阶段。验证 loss 也在降，说明学到的说法在没见过的 5 个主题上同样适用。
- **第 48 步以后：验证 loss 持平在 1.96。** 1 个 Epoch 已经基本学到头，再多训，验证集上大概也不会更好。
- **蓝线的锯齿不用管。** 每个点只是一步 16 条样本的平均，碰到容易或难的一批就会跳；看整体走势。
- **蓝线最后略低于橙线（约 1.5 对 1.96）是正常的。** 验证集是没见过的主题，回答里有很多主题专属的内容，只学说话风格压不低这部分。

**对比一条不正常的曲线：** 如果没重启内核就再次执行训练格，会在已经训练过的模型上接着训，相当于多训了好几个 Epoch。那时的样子是：训练 loss 被压到 0.5 左右，验证 loss 却从 2.0 一路回升到 2.3。训练集越来越好、验证集越来越差，就是死记训练数据的过拟合。重新训练前一定先 **Kernel → Restart Kernel**，再从第 1 格开始执行。

第 9 步重新创建基座并读取磁盘 adapter，第 10 步打印训练前后的回答。1 个 Epoch 后通常能看到回答变短、结构更像训练数据。打开 `answer-review.json`，逐题判断：事实是否正确、是否遵守“一句话”“不追问”等要求、中文是否适合学段、探索建议是否具体安全，再填写更喜欢哪个回答及理由。

三个观察题来自训练主题，只能说明“学到了什么风格”。要回答“LoRA 是否比原模型加好提示词更好”，用第 6 章的验证集盲评。

训练出来的只是磁盘上的文件。这一章把它变成一个能被任何后端代码调用的 HTTP 服务，并测出它能承受多少并发。

!!! abstract "本章速览"
    - **本章做什么**：区分 adapter 和完整模型；理解 vLLM 怎样用显存；部署合并模型；从自己电脑通过 SSH 隧道调用（单轮、多轮、流式）；换成“基座 + 挂载 adapter”的方式部署并对比；压测

    - **做完得到**：一个在跑的 OpenAI 兼容服务；本地调用拿到的回答；一张填好的并发 1/4/16 延迟与吞吐表
    - **大约耗时**：装 vLLM 约 10 分钟；部署、调用和压测约 30～60 分钟

一次 API 请求从你的电脑出发，到拿到回答，经过这些环节：

```text
本地 Python 发出请求
  → 本地 127.0.0.1:18000
  → SSH 隧道
  → GPU 主机 127.0.0.1:8000 上的 vLLM
      ① 用模型目录里的 chat_template 把 messages 拼成一段文本（和训练时相同）
      ② 分词成 Token，进入调度队列，和其他请求拼成同一批
      ③ 模型逐个生成 Token，KV Cache 保存已处理部分，直到 EOS 或 max_tokens
      ④ Token 解码回文字，一次返回 JSON，或按 stream=True 分段推送
  → 原路返回：回答文本 + finish_reason
```

第 ① 步解释了为什么调用时要用和训练相同的提示词结构：vLLM 用的是同一份聊天模板，只要 messages 一样，模型看到的 Token 就和训练时一样。

### 5.3 vLLM 在 GPU 上做了什么

把 vLLM 想成一个**常驻显存的应用服务器**：启动时把模型权重装进 GPU，对外提供与 OpenAI 相同格式的 HTTP 接口（`/v1/chat/completions`、`/v1/models`）。所以任何会调 OpenAI API 的后端代码，改一下 `base_url` 就能调你自己的模型。

它比 Notebook 里的 `model.generate()` 快很多，主要靠两件事：

| 机制 | 类比 | 作用 |
|---|---|---|
| 连续批处理（continuous batching） | 请求随到随进同一个处理批次，像共享的线程池 | 多个请求同时生成，GPU 不空等；一个请求结束就立刻换进下一个 |
| PagedAttention 管理 KV Cache | 像操作系统按页分配内存，而不是给每个请求预留最大空间 | 请求实际用多少 Token 就占多少显存，能同时容纳更多请求 |

**KV Cache** 是生成时为每个已处理 Token 保存的注意力中间结果，用来避免每生成一个新字就把前文重新算一遍。它随“上下文长度 × 同时处理的请求数”增长，是推理显存除了权重之外的大头。

#### 先自己算一遍显存，再和日志对照

Qwen3-4B 的结构参数在 `models/qwen3-4b/config.json` 里：36 层、8 个 KV 头、每头 128 维。BF16 每个数 2 字节，所以：

```text
每个 Token 的 KV Cache = 2（K 和 V）× 36 层 × 8 头 × 128 维 × 2 字节
                       = 147,456 字节 ≈ 144 KiB
一条 4096 Token 的满长请求 ≈ 4096 × 144 KiB ≈ 576 MiB
```

| 显存预算（`--gpu-memory-utilization 0.85`） | 估算 |
|---|---|
| vLLM 可用总量：24 GB × 0.85 | ≈ 20.4 GiB |
| BF16 权重：约 40 亿参数 × 2 字节 | ≈ 7.5 GiB |
| 激活、CUDA Graph 等运行时开销 | ≈ 1～2 GiB |
| 剩下全部给 KV Cache | ≈ 11 GiB ≈ 7～8 万 Token ≈ 18～20 条满长请求 |

启动日志里的 `GPU KV cache size: ... tokens` 和 `Maximum concurrency for 4096 tokens per request: ...x` 就是 vLLM 实际算出的结果，把它们记下来和上表比较。差得多时，通常是其他进程（比如没关的训练内核）占了显存。

这里出现的 `--gpu-memory-utilization`、`--max-model-len`、`--max-num-seqs` 等启动参数，第 5.4 节在启动命令下面逐个解释。

#### 这条启动命令逐段在说什么

如果你启动过 Web 服务，这条命令并不陌生。它和用 uvicorn 启动一个 Python Web 应用是同一类东西：

```text
uvicorn app:app       --host 127.0.0.1 --port 8000 --workers 4
vllm serve <模型目录>  --host 127.0.0.1 --port 8000 --max-num-seqs 4 ……
```

区别只在于：vLLM 要“部署”的不是一段业务代码，而是一个模型目录；所以多了几个和模型、显存有关的参数。先认识命令里的三种 Shell 写法：

| 写法 | 意思 |
|---|---|
| 行首的 `HF_HUB_OFFLINE=1` | 只对这一条命令生效的环境变量，等同于先 `export` 再执行，但不影响终端里后续的命令 |
| `$PWD` | 当前目录的绝对路径。所以必须先 `cd` 到项目目录再执行 |
| 行尾的 `\` | 换行续写，告诉 Shell 下一行还是同一条命令。`\` 后面不能再有空格 |

下面按“谁来运行 → 加载什么 → 对外叫什么 → 在哪里监听 → 精度和长度 → 显存和并发 → 默认生成参数”的顺序，逐个解释：

| 参数 | 本教程的值 | 含义 | 为什么这样设 / 改了会怎样 |
|---|---|---|---|
| `HF_HUB_OFFLINE=1` | — | 只读本地文件，不访问 Hugging Face 网站 | 模型已经在本地；国内主机访问 huggingface.co 常常卡住，不加它可能卡在启动阶段 |
| `.venv-serve/bin/vllm serve` | — | 用推理专用环境里的 vLLM，启动一个 HTTP 服务 | 用 `.venv-serve` 而不是 `.venv-train`，两个环境的 torch 版本不同，混用会互相覆盖 |
| 第一个参数：模型目录 | `runs/.../merged-model` | 要加载的模型。传的是**目录**，和 `from_pretrained` 一样，vLLM 自己读里面的 `config.json`、分词器和权重分片 | 换成 `models/qwen3-4b` 就是部署原始模型；第 5.6 节演示另一种方式：加载原始模型，再挂上 adapter |
| `--served-model-name` | `science-explorer-lora` | 对外公布的模型名，客户端请求里 `"model"` 字段要填它，`/v1/models` 也列出它 | 只是一个别名，和加载哪个权重无关。类比服务对外的域名，和机器上的目录名无关。请求里填错会返回 404 |
| `--host` | `127.0.0.1` | 监听的网卡地址。`127.0.0.1` 表示只接受本机的连接 | 不暴露到公网，外部只能经第 5.5 节的 SSH 隧道访问。改成 `0.0.0.0` 会对所有网卡开放，此时必须加鉴权（第 5.8 节） |
| `--port` | `8000` | 监听的端口 | 端口被占用时换一个，比如 8001，后面的 `curl` 和 SSH 隧道也要一起改 |
| `--dtype` | `bfloat16` | 权重和计算用的数值精度 | 和第 4 章合并时保存的精度一致。部署时不量化，所以显存里的权重约 7.5 GiB，而不是训练时的 2.5 GiB |
| `--max-model-len` | `4096` | 单个请求的最大 Token 数，**输入和输出加在一起** | 和训练时的上限相同。超出的请求直接返回 HTTP 400。调大能接更长的对话，但每条满长请求占的 KV Cache 更多，能同时容纳的请求数会变少 |
| `--gpu-memory-utilization` | `0.85` | vLLM 启动时**一次性预留**整张卡多大比例的显存，用来放权重和 KV Cache | 所以服务刚启动、没有任何请求时，`nvidia-smi` 就显示用了约 85%，这是预分配，不是泄漏。调高能放更多 KV Cache；留 15% 是给 CUDA 上下文和别的进程。显存不足启动失败时，先把它调低 |
| `--max-num-seqs` | `4` | 同一时刻最多有几个请求在一起生成 | 类比 Web 服务的 worker 数或连接池大小：多出来的请求排队等待。调大提高总吞吐，但每个请求变慢；第 5.7 节压测会实际对比 4 和 16 |
| `--generation-config` | `vllm` | 请求里没写的生成参数（`temperature` 等）用 vLLM 自己的默认值，而不是模型目录里 `generation_config.json` 的值 | 那个文件里是 Qwen 默认的随机采样（`temperature 0.7` 等）。本教程每次请求都显式传 `temperature=0`，这个参数保证不会被模型目录里的默认值悄悄影响 |

**三个和显存有关的参数怎样配合：** `--gpu-memory-utilization` 决定 vLLM 一共能用多少显存（24 GB × 0.85 ≈ 20 GiB）；扣掉权重和运行开销，剩下的约 11 GiB 全部做 KV Cache。`--max-model-len` 决定一条请求最多占多少 KV Cache（4096 Token ≈ 576 MiB）；`--max-num-seqs` 决定最多同时跑几条。启动日志里的 `Maximum concurrency` 就是“KV Cache 总量能装下几条满长请求”，第 5.3 节有完整的估算过程。

**这条命令没写、使用默认值的：** 只用 1 张 GPU（`--tensor-parallel-size 1`）；不校验 API 密钥（`--api-key`，第 5.8 节）；接口是 OpenAI 兼容的 `/v1/chat/completions` 等。完整参数可以用 `.venv-serve/bin/vllm serve --help` 查看。

将路径中的 `science-001` 改成刚训练的实验名。`science-explorer-lora` 是 API 请求里填写的 model 名；真正加载的权重来自 `merged-model/`。启动日志里找 `GPU KV cache size` 和 `Maximum concurrency` 两行，教程第 5.3 节会用它们核对显存估算。等出现 `Application startup complete` 后，在另一个 GPU 终端检查：

```bash
curl --fail http://127.0.0.1:8000/health
curl --fail http://127.0.0.1:8000/v1/models
nvidia-smi --query-gpu=memory.used,memory.total,utilization.gpu --format=csv
```

`/health` 成功时返回 200、没有正文；`/v1/models` 返回类似：

```json
{"object": "list", "data": [{"id": "science-explorer-lora", "object": "model", "max_model_len": 4096, ...}]}
```

即使没有请求，显存也已占用约 85%：vLLM 启动时按 `--gpu-memory-utilization` 一次性预留权重和 KV Cache，这是预分配，不是泄漏。服务进程需保持运行。

`HF_HUB_OFFLINE=1` 让 vLLM 只读本地目录、不联网，避免在国内主机上卡在访问 huggingface.co。启动失败时按顺序查：训练内核是否已关闭（`nvidia-smi` 里有没有别的 Python 进程）、驱动 CUDA 版本、模型目录是否完整（有 `config.json`、分词器和全部 `*.safetensors`）。显存不足先降低 `--max-model-len` 或 `--gpu-memory-utilization`；不要把模型路径换回原模型来“修好”服务。

### 5.5 在本地电脑调用：三个单轮题与一个多轮题

先在 **本地电脑的终端** 建立 SSH 隧道。使用云平台给出的实际 SSH 地址与端口替换占位值，并保持此终端打开。这一步用于调用服务，不用于上传文件。

```bash
ssh -p <平台SSH端口> -N -L 18000:127.0.0.1:8000 root@<平台SSH地址>
```

隧道把本地 `127.0.0.1:18000` 转发到 GPU 主机的 `127.0.0.1:8000`。服务只监听 GPU 主机的本地回环地址，不暴露到公网，这是最简单的访问控制。在本地另一个终端运行 `curl --fail http://127.0.0.1:18000/v1/models`。如果平台只提供网页 Jupyter 而没有 SSH 转发，请先在平台开通转发或使用其带鉴权的端口代理；Jupyter 文件浏览器 URL 不是模型 API 地址。

#### 先用 curl 直接调用

下面的命令都在 **本地电脑的另一个终端** 执行，隧道终端保持打开。本地只需要 `curl`：macOS 和 Linux 自带；Windows 请用 Git Bash 或 WSL，PowerShell 的引号规则不同，直接粘贴会出错。

##### 1. 检查服务是否可达

```bash

```

`/health` 成功时没有输出，也不报错；`/v1/models` 返回的 JSON 里应有 `"id": "science-explorer-lora"`，也就是启动命令里 `--served-model-name` 的值。连不上时先检查隧道终端是否还开着。

##### 2. 最简单的一次对话

```bash
curl http://127.0.0.1:18000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model": "science-explorer-lora", "messages": [{"role": "user", "content": "为什么白天亮、晚上黑？"}], "temperature": 0, "max_tokens": 256}'
```

这就是 OpenAI 兼容接口的最小请求：`POST /v1/chat/completions`，请求体里写模型名、消息列表和生成参数。`temperature: 0` 表示每次选概率最高的 Token，同样的请求得到同样的回答；`max_tokens` 是这次最多生成多少个 Token。返回的 JSON 大致是：

```json
{"id": "chatcmpl-...", "object": "chat.completion", "model": "science-explorer-lora",
 "choices": [{"index": 0, "message": {"role": "assistant", "content": "……"}, "finish_reason": "stop"}],
 "usage": {"prompt_tokens": 15, "completion_tokens": ..., "total_tokens": ...}}
```

回答在 `choices[0].message.content`。`finish_reason` 为 `stop` 表示模型自己输出了结束标记，为 `length` 表示达到 `max_tokens` 被截断。`usage` 是输入和输出的 Token 数，按 Token 计费或做限流时就看它。

注意：这个请求只有一条 user 消息，**没有带训练时的角色提示词、学段和事实卡**，所以回答的风格可能和训练数据不一样。它只用来认识接口格式。

##### 5. 流式输出

```bash
curl -N http://127.0.0.1:18000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model": "science-explorer-lora", "messages": [{"role": "user", "content": "为什么白天亮、晚上黑？"}], "temperature": 0, "max_tokens": 256, "stream": true}'
```

加上 `"stream": true` 后，服务每生成一小段就推送一次；`curl -N` 让 curl 收到就立刻打印，不攒着。输出是 Server-Sent Events 格式，每行以 `data:` 开头，最后一行是 `data: [DONE]`：

```text
data: {"id":"chatcmpl-...","object":"chat.completion.chunk",...,"choices":[{"index":0,"delta":{"content":"地球"},...}]}
data: {"id":"chatcmpl-...","object":"chat.completion.chunk",...,"choices":[{"index":0,"delta":{"content":"在"},...}]}
...
data: [DONE]
```

每行的 `delta.content` 是新生成的一小段，前端把它们依次拼起来，就能做出“边生成边显示”的效果。

#### 用 Python 批量调用

以下 Python 示例在 **本地电脑的项目根目录** 运行，只需 Python 标准库和本仓库代码。它复用训练时的 `build_messages`，所以发给服务的 system 提示词、学段和事实卡格式与训练样本完全一致。不需要本地 GPU，也不需要 OpenAI 账号。

```python
import json
from urllib.request import Request, urlopen

from lab.common import build_messages
from lab.data import read_dataset

url = "http://127.0.0.1:18000/v1/chat/completions"
MODEL = "science-explorer-lora"
_, facts = read_dataset("data/dataset.json")


def ask(messages):
    body = {"model": MODEL, "messages": messages, "temperature": 0, "max_tokens": 256}
    request = Request(url, data=json.dumps(body).encode(),
                      headers={"Content-Type": "application/json"})
    with urlopen(request, timeout=120) as response:
        choice = json.load(response)["choices"][0]
    print("finish_reason:", choice["finish_reason"])
    return choice["message"]["content"]


def messages_for(fact_id, grade, user, history=()):
    # 与训练相同：角色提示词 + 学段 + 事实卡 + 历史 + 当前问题。
    case = {"fact_ids": [fact_id], "grade_band": grade, "history": list(history), "user": user}
    return build_messages(facts, case)


questions = [
    ("day-night", "1-2", "晚上是太阳关灯了吗？先用一句话回答，不要反问。"),
    ("buoyancy", "3-4", "为什么小铁块沉，大铁船却浮着？我猜是大东西更容易浮。"),
    ("moon-phase", "5-6", "月亮变弯是被地球影子挡住了吗？我想安全地观察一下。"),
]
for fact_id, grade, question in questions:
    print("问题:", question)
    print("回答:", ask(messages_for(fact_id, grade, question)), "\n")

# 多轮：服务不会记住上一轮，必须把实际生成的回答作为 history 传回去。
first_question = "轮船那么重，为什么不会沉？"
first = ask(messages_for("buoyancy", "3-4", first_question))
history = [{"role": "user", "content": first_question},
           {"role": "assistant", "content": first}]
print("多轮回答:", ask(messages_for("buoyancy", "3-4", "我还是不懂排开水，换个简单说法，先别考我。", history)))
```

每题会先打印 `finish_reason: stop`，再打印回答，形如：

```text
问题: 晚上是太阳关灯了吗？先用一句话回答，不要反问。
finish_reason: stop
回答: 太阳没有关灯。是我们住的地面转到了背向太阳的一侧。
```

`stop` 表示模型自己输出了 EOS 正常结束；`length` 表示输出达到 `max_tokens` 被截断，不能当完整回答。第一次请求会慢一两秒（vLLM 预热），之后单题通常 1 秒内返回。

依次观察：是否纠正错误猜想；能否换一种孩子听得懂的解释；观察是否安全具体；是否尊重“不考我”。

提示词要和训练时一致：模型是在“角色提示词 + 学段 + 事实卡”这种输入上学会回答方式的，换一套差别很大的提示词，效果可能明显变差。事实卡由调用方负责传入，微调不会让模型获得新知识或实时信息。

#### 用 OpenAI SDK 和流式输出

后端项目里更常见的是直接用 OpenAI 官方 SDK。在本地安装 `python3 -m pip install openai`，只需把 `base_url` 指向隧道地址；vLLM 默认不校验密钥，`api_key` 填任意非空字符串：

```python
from openai import OpenAI

from lab.common import build_messages
from lab.data import read_dataset

client = OpenAI(base_url="http://127.0.0.1:18000/v1", api_key="EMPTY")
_, facts = read_dataset("data/dataset.json")
messages = build_messages(facts, {"fact_ids": ["seasons"], "grade_band": "3-4", "history": [],
                                  "user": "为什么夏天热、冬天冷？"})

# stream=True：服务每生成一小段就推送一次，前端可以边生成边显示。
stream = client.chat.completions.create(model="science-explorer-lora", messages=messages,
                                        temperature=0, max_tokens=256, stream=True)
for chunk in stream:
    if chunk.choices and chunk.choices[0].delta.content:
        print(chunk.choices[0].delta.content, end="", flush=True)
print()
```

流式输出走的是 Server-Sent Events：同一个 HTTP 响应里连续推送多段 JSON。用户感受到的等待时间主要是“首个 Token 多久出来”（TTFT），而不是整段回答的总时长，第 5.7 节会测这个指标。

### 5.6 不合并：直接挂载 adapter，同一服务里对比原模型

合并不是唯一的部署方式。vLLM 可以加载**原始基座**，再把 LoRA adapter 作为一个额外的“模型名”挂上去。同一个服务里，请求 `qwen3-4b-base` 走原模型，请求 `science-lora` 走原模型 + LoRA。先按 `Ctrl+C` 停掉第 5.4 节的服务（端口和显存不能同时给两个服务），再启动：

```bash
HF_HUB_OFFLINE=1 .venv-serve/bin/vllm serve "$PWD/models/qwen3-4b" \
  --served-model-name qwen3-4b-base \
  --enable-lora --lora-modules science-lora="$PWD/runs/science-001/adapter" \
  --max-lora-rank 16 \
  --host 127.0.0.1 --port 8000 \
  --dtype bfloat16 --max-model-len 4096 \
  --gpu-memory-utilization 0.85 --max-num-seqs 4 \
  --generation-config vllm
```

`/v1/models` 现在会列出两个名字。把第 5.5 节示例里的 `MODEL` 依次改成 `qwen3-4b-base` 和 `science-lora` 各跑一遍，就是同一提示词下“微调前 vs 微调后”的对比。`--max-lora-rank` 必须不小于训练时的 rank（本教程是 16）。

| | 合并后部署（10.4） | 挂载 adapter（10.6） |
|---|---|---|
| 磁盘 | 每个版本一份约 8 GB 的完整模型 | 一份基座 + 每个版本约 130 MB 的 adapter |
| 推理速度 | 和原模型相同 | 每层多一次小矩阵计算，通常略慢 |
| 多个微调版本 | 每个版本一个服务、一份显存 | 一个服务同时挂多个 adapter，共享基座显存 |
| 更新模型 | 重新合并、重新启动 | 换 adapter 目录、重启服务即可 |
| 适合 | 只有一个版本、追求最低延迟 | A/B 对比、多租户、多版本灰度 |

### 5.7 压测：并发、延迟和吞吐

上线前要知道“一张 4090 能撑多少请求”。vLLM 自带压测工具，在 GPU 主机的**另一个终端**运行（服务保持运行，以第 5.4 节的合并模型服务为例）：

```bash
.venv-serve/bin/vllm bench serve --backend openai-chat \
  --base-url http://127.0.0.1:8000 --endpoint /v1/chat/completions \
  --model science-explorer-lora --tokenizer "$PWD/runs/science-001/merged-model" \
  --dataset-name random --random-input-len 512 --random-output-len 128 \
  --num-prompts 64 --max-concurrency 1
```

`random` 数据集按指定长度生成随机输入，只用来测性能，不看回答内容。参数名以本机 `vllm bench serve --help` 为准。把 `--max-concurrency` 依次改成 1、4、16，各跑一次，填下表：

| 客户端并发 | Request throughput (req/s) | Output token throughput (tok/s) | Mean TTFT (ms) | Mean TPOT (ms) |
|---:|---:|---:|---:|---:|
| 1 | | | | |
| 4 | | | | |
| 16 | | | | |

| 指标 | 含义 | 类比 |
|---|---|---|
| TTFT（Time To First Token） | 从发出请求到收到第一个 Token | 首字节时间 |
| TPOT（Time Per Output Token） | 之后平均每个 Token 的间隔 | 流式响应的推送间隔 |
| Output token throughput | 每秒总共生成多少 Token | QPS 的 Token 版本 |

你应该会看到：并发从 1 到 4，总吞吐明显上升，单请求 TPOT 只略微变慢，这是连续批处理的收益；并发到 16 时，服务端 `--max-num-seqs 4` 限制了同时生成的请求数，多出的请求在排队，TTFT 明显变长。停掉服务，把 `--max-num-seqs` 改成 16 重新启动，再跑并发 16，比较吞吐和 TTFT。这就是在“吞吐”和“单请求延迟”之间做取舍。

### 5.8 上线前还缺什么

本教程的服务只监听 `127.0.0.1`、通过 SSH 隧道访问，适合练习。要给别人用，至少还要补上：

| 方面 | 做法 |
|---|---|
| 鉴权 | 启动时加 `--api-key <密钥>`，客户端在 `Authorization: Bearer <密钥>` 里携带；或者放在已有鉴权的网关后面。不要不加鉴权就监听 `0.0.0.0` |
| 监控 | vLLM 在同一端口提供 Prometheus 格式的 `/metrics`（`curl http://127.0.0.1:8000/metrics`），包含排队请求数、KV Cache 使用率、Token 吞吐等，可接入现有监控 |
| 进程管理 | 用 systemd、Docker 或平台的服务功能托管，崩溃自动重启；模型加载需要几十秒，健康检查用 `/health` |
| 客户端 | 设置超时；只对连接失败和 5xx 有限次重试；HTTP 400 通常是输入超过 `--max-model-len`，重试没用 |
| 成本 | 服务空闲时显存也一直被占用，按量计费的实例不用时要停掉 |

## 6. 效果评估：微调到底有没有比提示词强

本章回答一个工程上很实际的问题：花 GPU 时间微调，比只写好提示词强多少？草稿数据可以直接做这组**探索性对照**，用来练习实验方法；要对外报告结论，先完成数据审核。

!!! abstract "本章速览"
    - **本章做什么**：让三组模型（原模型 + 简单提示、原模型 + 好提示词和示例、LoRA）回答同一批验证题；比较两个 rank；用盲评打分；选定候选后才用测试集
    - **需要准备**：第 3 章的 `.venv-train` 和基座；能连续使用 GPU 数小时；至少一位评分人（最好不是训练者本人）
    - **做完得到**：一份有原始输出、评分和不确定性区间的实验记录，能回答“微调值不值”
    - **什么时候做**：第 4～5 章主线跑通之后。本章 GPU 时间约 10～20 小时（含多次推理和两次训练），人工评分另计

为什么不能只看 loss？loss 只衡量“像不像参考回答”。参考回答本身也可能啰嗦、错漏；原模型配一份好提示词，也许已经说得够好。要判断微调有没有价值，必须在**没训练过的主题**上，让“好提示词”和“好提示词 + LoRA”回答**完全相同的输入**，再由人在不知道哪个是哪个的情况下打分。这和后端做 A/B 实验是一回事：控制变量、盲测、看置信区间。

本章分两半：6.1～6.4 准备数据并生成三组回答，6.5～6.8 评分、冻结和下结论。命令都在 GPU 主机的项目根目录执行。

### 6.1 现有数据规模与审核要求

当前已经有 500/50/50 段，无需再次扩到旧版的规模。每类 100/10/10 段，共 60 张事实卡。formal 是本教学实验的固定配额，不是 LoRA 通用最低要求。

所有同主题变体用同一个 group_id；事实引用也不能跨集合。每个验证、测试集合各只有 5 个独立主题，因此即使有 50 段，也不能当作 50 个互不相关的知识测试。

**什么算审核。** 正式审核逐段检查：来源是否支持事实、有没有过度拟人、孩子是否听得懂、比喻边界是否清楚、观察是否安全可行、是否尊重孩子不想被提问或想结束。审核直接在 `dataset.json` 里进行，用版本控制保留历史。只有真正审核过的条目才把 `review.status` 改成 `approved`，并填写实际的 `reviewer`、`reviewer_kind`、`notes`；不要批量改状态冒充审核。程序能查结构，查不了近重复、模板味和科学错误：10 类路径有意重复教学行为，同主题也复用部分回答，50 个 train 主题不等于 500 个独立主题；val/test 与训练主题隔离，但仍共享光、力、生命等基础概念。

草稿数据加 `--allow-draft` 即可完成本章第 6.1～6.6 节的验证集对照，产物 manifest 会记录 `draft: true`。冻结候选和测试集（第 6.7 节）仍要求审核后的数据，避免把草稿结果当成正式结论。

### 6.2 怎样继续改善数据

先按主题读完 10 条路径，检查孩子每次反馈是否引起对应改变。低年级若仍出现未解释术语，应重写；同一比喻不能反复替代具体解释；一个观察也不能证明与它无关的全部结论。

用验证集找到失败类型后补充训练示范，避免根据 test 的答案改数据。新增主题先分组再划分集合。当前十类路径是结构化合成，并非来自真实儿童互动；有条件时在监护人知情同意下收集匿名反馈，另评估理解与自愿探索，不以多聊几轮作唯一目标。

### 6.3 校验与准备

在 GPU 主机的项目根目录打开终端，先激活第 3 章安装的训练环境；以下命令需要 PyTorch 与 TRL：

```bash
source .venv-train/bin/activate

python -m lab.data \
  --input data/dataset.json --allow-draft --formal

python -m lab.prepare \
  --input data/dataset.json \
  --tokenizer models/qwen3-4b --allow-draft --formal --output data/processed/experiment-v1

python -m lab.audit --data data/processed/experiment-v1 \
  --output runs/formal-token-audit.json
```

`--formal` 核对 500/50/50 段、60 张事实卡及每类 100/10/10 的配额；`--allow-draft` 允许未审核的条目。两者是独立的检查：完成真实审核后去掉 `--allow-draft`，得到的就是正式数据版本（换一个输出目录，例如 `experiment-v2`）。

自动检查：配额、审核状态、来源 ID、完整对话组交叉、相同用户对话、控制符、非空目标、提问数量。近重复、语义错误、来源不支持等还需要审核，程序无法仅凭一个 URL 判断事实真伪。

### 6.4 三组基线与两个 rank

| 组别 | 权重 | 提示词与示例 |
|---|---|---|
| A | 原模型 | 基本提示词，不附示例 |
| B | 原模型 | 完整角色提示词 + 训练集选出的 3 个 few-shot |
| C | 原模型 + 本次 LoRA | 与 B 完全相同的提示词和 3 个 few-shot |

B、C 的 3 个 few-shot 由 `lab.prepare` 从 train 的开头、中间、结尾附近各选一段（尽量覆盖三个学段），只取第一轮问答，写进快照的 `fewshots.json`。few-shot 只在推理时使用；SFT 训练样本不插入示例，避免把样本自己的答案提前贴进输入。

三组都使用当前题目的同一事实卡、NF4 精度与贪心解码。默认读取 `val`，参考答案只用于后续评审；固定历史模式会把前轮参考回复作为上下文。本节 B/C 与 Notebook 的三个无 few-shot 观察题属于不同协议，不混合评分。

先运行验证集 A、B：

```bash
python -m lab.infer --data data/processed/experiment-v1 --variant A \
  --output runs/val-A.jsonl
python -m lab.infer --data data/processed/experiment-v1 --variant B \
  --output runs/val-B.jsonl
```

训练 r=16，1 Epoch：

```bash
python -m lab.train --data data/processed/experiment-v1 \
  --output runs/formal-r16 --allow-draft --epochs 1 --rank 16
python -m lab.infer --data data/processed/experiment-v1 --variant C \
  --adapter runs/formal-r16/adapter --output runs/val-C-r16.jsonl
```

只改变 rank 和对应的 alpha，重新从基座开始：

```bash
python -m lab.train --data data/processed/experiment-v1 \
  --output runs/formal-r8 --allow-draft --epochs 1 --rank 8
python -m lab.infer --data data/processed/experiment-v1 --variant C \
  --adapter runs/formal-r8/adapter --output runs/val-C-r8.jsonl
```

代码始终设置 alpha=2×rank，所以两轮缩放比都是 2。不要从 r16 的 adapter 接着训练 r8，并将其称为独立对照。

1150 条训练样本、有效 Batch≈16 时，1 Epoch 约 72 次优化器更新，和 Notebook 默认训练量相同。B 组已经有好提示词和 few-shot，C 组没有明显优势也很正常，这本身就是有价值的结论：说明这个任务用提示词就够了。

**验收：** 两轮的数据、提示词、生成参数和基座一致；能比较验证效果、训练时间、显存、adapter 大小；不以训练 Loss 单独选出“更好的探索伙伴”。

新开终端时先运行 `source .venv-train/bin/activate`，并确认第 6.3～6.4 节的数据快照与候选模型已经生成。

### 6.5 先固定历史，再连续对话

固定历史（默认 `--mode fixed`）使用数据里的参考历史。B/C 每条输入的哈希必须相同，适合定位某一轮表达差异。

连续对话使用模型自己的回答作为后续历史：

```bash
python -m lab.infer --data data/processed/experiment-v1 --variant B \
  --mode rollout --output runs/val-B-rollout.jsonl
python -m lab.infer --data data/processed/experiment-v1 --variant C \
  --adapter runs/formal-r16/adapter --mode rollout --output runs/val-C-rollout.jsonl
```

两组使用相同用户脚本，模型各自生成后续历史，因此后续 prompt 哈希可能不同。有的预设追问可能接不上生成回答，评分时要记录这种情况。真人根据回答追问属于另一种评测。

### 6.6 人工盲评

完整程序：[evaluate.py](../lab/evaluate.py)。

```bash
python -m lab.evaluate blind --base runs/val-B.jsonl \
  --tuned runs/val-C-r16.jsonl --output runs/blind-val-r16
```

生成 `ratings.jsonl`、`key.json` 和协议。评分时只看 ratings 与事实卡，不看 key；完成后再揭晓哪一侧是 LoRA。可以请未参与训练的人评分，减少作者对候选的偏好。

每条填写：`winner` 为 X/Y/tie、`reason` 写具体原因；分别填写 `fact_claims_X/Y` 和 `supported_X/Y`。无可核查事实时填 0，不把它当作“100% 正确”。issues 字段记录事实错误、中文超出学段或术语堆积、过度提问、忽略偏好、错误归因、假装看见孩子的观察等问题。

| 维度 | 0 分 | 1 分 | 2 分 |
|---|---|---|---|
| 事实 | 关键断言无依据/错误 | 部分不清楚或范围过宽 | 可核查断言均有依据，未知明确 |
| 学段适配 | 超出理解水平、术语堆积 | 能懂但解释未随反馈调整 | 具体简明，没懂时换解释 |
| 探索价值 | 套话、编造或强迫提问 | 有兴趣点但下一步模糊 | 具体、安全、可选择的观察或追问 |
| 互动 | 忽略明确选择 | 基本响应但重复 | 尊重选择、节奏合适 |
| 证据意识 | 把猜测或比喻当事实 | 有限定但不充分 | 区分观察、解释和比喻，承认信息不足 |

量表用于帮助判断 winner，分项可以写在 reason 中；不是自动关键词打分。一个有严重事实错误但更“好玩”的回答不应仅凭趣味取胜。

```bash
python -m lab.evaluate score --ratings runs/blind-val-r16/ratings.jsonl \
  --key runs/blind-val-r16/key.json --output runs/val-r16-score.json
```

胜计 1、平计 0.5、负计 0。脚本按 group_id 科学主题进行 bootstrap，避免把同主题十条路径和多轮当成独立样本；报告轮数、对话数及主题数。少于 2 个主题不输出区间。各 5 个验证/测试主题仍很少，区间不能支撑广泛结论。小样本区间只是探索性结果，不能消除评分偏差。

事实支持率=获得资料支持的断言数/可核查断言数；脚本不会自动核实这些断言。未填写全部事实审查项时标记 `factual_review_complete=false`，不能把局部比率当成完整质量结论。

### 6.7 冻结后才使用测试集

```python
"""The TRL path is shared by the CUDA lesson and the tiny CPU regression test."""
from trl import SFTConfig, SFTTrainer
from transformers import TrainerCallback


class StopAfter(TrainerCallback):
    """Deliberately interrupt a planned run without changing its LR schedule."""
    def __init__(self, step):
        self.step = step

    def on_step_end(self, args, state, control, **kwargs):
        if self.step and state.global_step >= self.step:
            control.should_save = True
            control.should_training_stop = True
        return control


def make_trainer(model, tokenizer, train, val, output, *, cpu=False, epochs=1,
                 max_steps=-1, accum=16, lr=1e-4, max_length=4096, seed=42, stop_after=0):
    args = SFTConfig(
        output_dir=output, num_train_epochs=epochs, max_steps=max_steps,
        per_device_train_batch_size=1, per_device_eval_batch_size=1,
        gradient_accumulation_steps=accum, learning_rate=lr,
        warmup_ratio=0.05, lr_scheduler_type="cosine", optim="adamw_torch",
        max_grad_norm=1.0, bf16=not cpu, fp16=False, use_cpu=cpu,
        gradient_checkpointing=not cpu,
        gradient_checkpointing_kwargs={"use_reentrant": False},
        max_length=max_length, packing=False, completion_only_loss=True,
        assistant_only_loss=False, eos_token=tokenizer.eos_token,
        eval_strategy="epoch" if val is not None else "no",
        save_strategy="steps", save_steps=5, save_total_limit=2,
        logging_steps=1, report_to="none", prediction_loss_only=True,
        seed=seed, data_seed=seed, dataloader_num_workers=0,
        dataloader_pin_memory=not cpu, push_to_hub=False)
    return SFTTrainer(model=model, args=args, processing_class=tokenizer,
                      train_dataset=train, eval_dataset=val,
                      callbacks=[StopAfter(stop_after)])


def check_supervision(trainer, rows, eos_id, count=10):
    # D6：上下文和 padding 的 labels 应为 -100，当前参考回答及 EOS 才参与损失。
    for i, row in enumerate(rows[:count]):
        item = trainer.train_dataset[i]
        batch = trainer.data_collator([item])
        actual = batch["labels"][0].tolist()
        expected = [token if mask else -100 for token, mask in
                    zip(row["input_ids"], row["completion_mask"])]
        if actual != expected or -100 not in actual or not any(x != -100 for x in actual):
            raise ValueError(f"supervision mismatch at row {i}")
        supervised = [x for x in actual if x != -100]
        if supervised[-1] != eos_id or supervised.count(eos_id) != 1:
            raise ValueError("supervision must include one final EOS")
```

```python
        return Dataset.from_list([{k: row[k] for k in ("input_ids", "completion_mask")} for row in items])
    trainer = make_trainer(model, tok, dataset(rows), dataset(val_rows) if val_rows else None, str(out),
        epochs=a.epochs, max_steps=a.max_steps, accum=a.accum, lr=a.lr,
        max_length=a.max_length, seed=a.seed, stop_after=a.stop_after)
    check_supervision(trainer, rows, tok.eos_token_id)
    out.mkdir(parents=True, exist_ok=True)
    manifest = {"contract": contract, "draft": bundle["draft"], "gpu": torch.cuda.get_device_name(0),
                "cuda": torch.version.cuda, "supervised_rows": len(rows),
                "trainable_parameters": sum(p.numel() for p in trainable.values())}
    write_json(out/"manifest.json", manifest)
    (out/"dependencies.txt").write_text("\n".join(sorted(
        f"{d.metadata['Name']}=={d.version}" for d in importlib.metadata.distributions())) + "\n")
    driver = subprocess.run(["nvidia-smi"], capture_output=True, text=True, check=False)
    (out/"nvidia-smi.txt").write_text(driver.stdout + driver.stderr)
    torch.cuda.reset_peak_memory_stats()
    started = time.monotonic()
    result = trainer.train(resume_from_checkpoint=a.resume)
    if trainer.state.global_step <= resume_step:
        raise RuntimeError("no new optimizer step; inspect resume/max-steps")
    if not math.isfinite(result.training_loss) or any(not torch.isfinite(p).all() for p in trainable.values()):
        raise RuntimeError("non-finite loss or adapter parameters; inspect data and precision")
    changed = [n for n,p in trainable.items() if not torch.equal(initial[n], p.detach().cpu())]
    if not changed:
        raise RuntimeError("no LoRA parameter changed")
    trainer.save_model(str(out/"adapter"))
    tok.save_pretrained(out/"adapter")
    shutil.copyfile(out/"manifest.json", out/"adapter"/"manifest.json")
    trainer.save_state()
    metrics = dict(result.metrics, elapsed_seconds=time.monotonic()-started,
                   peak_allocated_gib=torch.cuda.max_memory_allocated()/2**30,
                   peak_reserved_gib=torch.cuda.max_memory_reserved()/2**30,
                   changed_lora_tensors=len(changed), resumed_from_step=resume_step,
                   final_step=trainer.state.global_step)
    if val_rows:
        metrics.update(trainer.evaluate())
    write_json(out/f"metrics-step-{trainer.state.global_step}.json", metrics)
    print(json.dumps(metrics, indent=2))


if __name__ == "__main__":
    main()
```
